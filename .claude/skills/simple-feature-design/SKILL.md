# Простота по умолчанию (aiAdmin / SparkPanel)

В проекте есть две реализации одного и того же экрана: **старая**
(`webSite/frontend/to_delete/components/contentEditor/`, ~7900 строк ядра плюс 90–180 строк
контроллера на каждый раздел) и **новая** (`webSite/frontend/components/contentEditorNew/`,
~3550 строк ядра и 60–90 строк на раздел). Новая — образец, старая — то, как делать не надо.

Разница не в объёме кода, а в том, **кто что знает**. Ниже правила, которые дают эту разницу.
Пишешь новую фичу или ревьюишь чужую — сверяйся с ними.

## 1. Раздел отдаёт данные, а не управление

Универсальный компонент получает **где лежат данные** и **как они выглядят**. Он НЕ получает
«как собой управлять»: ни `save`, ни `valuesOf`, ни `onSubmit`, ни набора `actions`.

```tsx
// ТАК (новый редактор): раздел называет список, отдаёт Api и описание
<ContentEditor listKey={ListKey.pages} api={pagesApi} columns={PAGE_COLUMNS} fields={PAGE_FIELDS} />

// НЕ ТАК (старый): контроллер раздела на 150 строк, который возвращает
// функции save/valuesOf/options/actions/labels — раздел объясняет редактору, что делать
const controller = usePagesController();
<ContentEditor {...controller} />
```

Api раздела — тонкая обёртка (20–40 строк): `list` / `create` / `update` / `remove`.
Всё остальное — загрузку, состояние, черновики, сохранение, перечитывание — делает
общий слой сам.

## 2. Описание данными, а не разметкой

Колонки, поля, вкладки — обычные объекты. Из `logic/` и из описаний **JSX не возвращается**.

```ts
const PAGE_FIELDS: EditorFields = {
  name: { name: 'Название', isRequired: true },
  isActive: { name: 'Активность', type: FieldType.Switch, note: '…' },
};
```

Описания выносятся в константу модуля, а не пишутся литералом внутри компонента:
у литерала каждый рендер новая ссылка, и общий слой по ней пересобирает состояние.

## 3. Ключ вместо пробрасывания

Если значение выводится из стора по ключу — **выводи, а не прокидывай**. В новом редакторе
раздел даёт `listKey`, а таблица, карточка и настройки берут свою ячейку
`state.contentEditorNew[listKey]` сами. Один срез на все списки, а не срез на раздел.

Пропс оправдан только для: идентичности элемента, настройки вида, `children` и подключения
универсального компонента (Api + описание).

## 4. Сохраняет тот, кто правит

Форма не отдаёт черновик наверх, чтобы его сохранил список. Запись уходит на сервер по
своему ключу прямо из шторки. Общие действия сущности — маленький хук рядом с её
компонентами (`useRecord`, `useProperties`), а не цепочка колбэков через три уровня.

## 5. Одна сущность — один запрос, по своему номеру

- Правка одной записи не переписывает соседей: `PATCH /…/:id`, а не «сохранить список целиком».
- Адресуемся **номером** сущности, а не её кодом/именем: код правят, и значения,
  подписанные кодом, после переименования теряются.
- Частичная правка — `PATCH` и только изменённые поля. Тогда экран не может стереть то,
  чего он не показывал (а он всегда чего-то не показывает: поля в разработке, чужие вкладки).

## 6. Черновик локальный, в сторе — то, что в базе

Таблица показывает сохранённое. Черновик живёт в том компоненте, который правят, и умирает
вместе с ним. После записи — перечитать список, а не «домазать» ответ по сторам.

## 7. Повторяющийся кусочек интерфейса — один компонент

Значок действия, раскладка формы, пустое состояние. Иначе соседние окна выглядят вразнобой:
кнопка antd рядом с голым значком, вертикальная форма рядом с горизонтальной.
Примеры: `contentEditorNew/ui/ActionIcon.tsx`, `contentEditorNew/ui/formLayout.tsx`.

## 8. Имя файла = что он рисует, папка = часть экрана

```
contentEditorNew/
  ContentEditor.tsx   композиция
  table/              таблица
  drawer/             карточка записи
  settings/           окно настроек (внутри tabs/ и properties/)
  ui/                 общие мелочи
```

`PropertyList` — список свойств, `PropertyDrawer` — шторка одного свойства. Не `SettingsProperties`
рядом с `PropertySettings`: такие имена читать невозможно.

**Структура, маршрут и имя таблицы идут вместе.** Модуль переехал в `infoblocks/values/` —
значит маршрут `/api/infoblocks/:listKey/values` и таблицы `infoblock_values`. Расхождение
папки, URL и таблицы — источник вопросов «а почему это лежит здесь».

## 9. Чего в коде быть не должно

- Контроллера раздела, который возвращает функции в компонент.
- Функций в сторе (контроллер, колбэки, Api).
- Универсального слоя поверх универсального слоя (общая форма со своим контекстом **внутри**
  общего редактора) — один уровень обобщения за раз.
- Групп пропсов (`labels`, `actions`, `history`), которые повторяют то, что раздел и так знает.
- Веток «если это раздел X» внутри общего кода. Отличие раздела описывается данными,
  а не условием в общем слое.

## Чего эти правила НЕ означают

Разбор обеих реализаций (ядро 8595 → 3890 строк) показал: сжатие неравномерное, и часть его
оплачена не упрощением.

- **Меньше кода ≠ проще.** ~4700 ушедших строк — это вычтенные возможности: журнал, 8 типов
  поля из 14, каскады условности поля, переменные `#NAME#`, адрес открытой
  записи в URL. Долг, а не достоинство: возвращать придётся, и правила должны выдержать
  возврат. Если правило держится только потому, что фичи ещё нет, — это не правило.
- **Окно настроек списка — не образец.** 2314 → 1585 строк при том же наборе возможностей,
  47 % нового редактора. Способ другой, объём тот же. Копировать как образец стоит таблицу
  и карточку записи.
- **`unknown[]` в сторе и ручное приведение типов — не простота, а снятая типизация.**
  В старом был дженерик `EditorApi<T>` с опорой на DTO из `src/generated`; в новом — четыре
  функции приведения и касты `as never`. Это плата за «один срез на все списки», и её надо
  либо вернуть дженериком, либо осознанно держать.
- **Логика рядом с компонентами — отсрочка, а не решение.** 8 файлов редактора дёргают redux
  напрямую (пункт 2 чек-листа `frontend/CLAUDE.md`), ~775 строк чистых функций лежат в
  `components/`. Разрешено до тех пор, пока их немного; переезд в `logic/` будет тем дороже,
  чем дольше тянуть.
- **Невидимые правила опаснее сложности.** Пять типов свойств карточка показывает закрытыми
  и обязана отдавать их значения серверу как есть: забудешь эту ветку в сборке тела запроса —
  молча сотрёшь данные. Такие места либо убираются конструкцией, либо пишутся комментарием
  в самом коде, а не в документации.

## Чек-лист перед готовностью

1. [ ] Раздел дал только Api и описание; функций «как сохранять» в пропсах нет.
2. [ ] Ни один пропс не прокидывает то, что выводится из стора по ключу.
3. [ ] Правка одной сущности не переписывает соседние; адресация по номеру.
4. [ ] Черновик не живёт в сторе; после записи список перечитан.
5. [ ] Нет ветвлений по названию раздела внутри общего кода.
6. [ ] Имя файла говорит, что он рисует; папка соответствует части экрана.
7. [ ] Повторяющийся элемент интерфейса взят из общего `ui/`, а не собран на месте.
8. [ ] Комментарии объясняют **почему**, а не что (правило всего проекта).

## Когда правил мало

Если фича не ложится — **расширяй общий слой, а не пиши свой экран**. Так в редактор попали
поле выбора файла, колонка-превью и действие строки «открыть»: ими теперь пользуется любой
раздел. Свой экран оправдан, только когда у фичи другой жанр (вход в панель, дашборд).
