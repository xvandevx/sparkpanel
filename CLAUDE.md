# aiAdmin — правила работы с кодом

Приложение называется **SparkPanel** (раньше CoPanel; репозиторий и рабочая папка остались `aiAdmin`).
Логотип в SVG — [`brand/`](brand/): знак, вертикальный и горизонтальный варианты; в панели
его рисует `components/ui/BrandMark.tsx`. Тот, кто ставит панель, может заменить его своим
в «Настройках сайта» (ключ `logo`, [`docs/settings.md`](docs/settings.md)).

Проект — **админ-панель**. Инфраструктура, архитектурные правила и инструменты Claude Code
портированы из проекта `focuzy`; **код и реализация — свои**, ничего из focuzy не копируем.

## Структура репозитория

Git-корень — `aiAdmin/`, **один репозиторий на всё** (фронтенд и бэкенд вместе); веб-приложение
живёт в `webSite/` (основная рабочая папка). Готовится к публикации: лицензия — BSL 1.1
([`LICENSE`](LICENSE): в продакшене можно, продавать как облачный CMS-сервис нельзя,
версия через 4 года — Apache 2.0), лицо репозитория — [`README.md`](README.md) и
[`README.ru.md`](README.ru.md). Образ собирает `.github/workflows/image.yml`.

## Сейчас идёт перестройка редактора контента

Редактор контента переписывается с нуля (`components/contentEditorNew/`), и пока он
не дорос до прежнего, **всё, что им не пользуется, отложено в `to_delete/`** — отдельно
во `frontend/` и в `backend/`. Папки исключены из сборки (`tsconfig.json`,
`tsconfig.build.json`), код в них не трогаем: он вернётся по частям, раздел за разделом.

Что живо:

| Слой | Живое | В `to_delete/` |
|------|-------|----------------|
| backend | `auth`, `users`, `infoblocks/` (`pages`, `history`, `settings`, `values`, `drafts`, `backups`, `files`, `storages`, `domains`, `roles`, `products`, `forms`, `contents`), `settings`, `backups`, `storage`, `external-api`, `mcp` | `domains` (прежняя схема), `forms` (прежняя схема), `infoblocks` (сами списки) |
| frontend | «Главная», «Страницы», «Контент» (типы и их элементы), «Файлы», «Товары» (с «Категориями»), «Пользователи» (с «Ролями»), «Настройки» (с «Доменами», «API» и «MCP») | остальные экраны, старый редактор контента и общий слой формы, «Обратная связь» (`to_delete/feedback/`) |

Таблицы в базе от парковки не исчезают: модели просто не зарегистрированы, данные
инфоблоков, форм прежней схемы (`forms`, `form_fields`) и доменов прежней схемы (`domains`)
лежат на месте. Новые «Формы обратной связи» и «Домены» пишут в свои таблицы
(`infoblock_forms*`, `infoblock_domains`), старые не трогают.
Пока их нет, «привязка к контенту» в бэкенде выбирает только из живых разделов
(страницы, роли, категории товаров; формы и их поля — нет, пока «Обратная связь»
скрыта во фронтенде, хотя их записи `link-targets` отдаёт).

Раздел «HTML-блоки» (модуль `content/`, маркеры `#BLOCK:код#`, тип свойства
`html-blocks`) **удалён целиком**, а не отложен: таблица `content_blocks` в базе осталась,
кода к ней нет. Код, отложенный в `to_delete/`, на него ещё ссылается — при возвращении
эти куски убирают.

## Разделение кода — обязательно

Любая фича раскладывается по трём зонам ответственности, они не смешиваются:

| Зона | Где живёт | Что там |
|------|-----------|---------|
| **Отображение** | `frontend/components/`, `frontend/pages/` | только JSX, стили и локальный UI-стейт (открыт/ховер/черновик инпута) |
| **Бизнес-логика** | `frontend/logic/<feature>/` | хуки `use<Feature>()` / `use<Feature>Actions()`, чистые функции: расчёты, фильтры, сортировки, даты, форматирование |
| **Стор и данные** | `frontend/redux/` + `frontend/api/` | сущности, стейт экрана, флаги загрузки; thunks — единственное место вызова `api/` |

**Имена логических значений начинаются с `is`** — `isNested`, `isReadOnly`, `isActive`:
из имени должно быть видно, что это флаг, а не данные. Правило общее на фронт и бэкенд.

Запрещено: расчёты и `fetch` в компоненте, `useSelector`/`useDispatch` в компоненте напрямую,
бизнес-логика в редьюсере, презентационное форматирование в сторе.

**Простота — такое же правило, как слои.** В проекте лежат две реализации одного экрана:
новая (`components/contentEditorNew/`) и старая (`to_delete/components/contentEditor/`).
Новая — образец: раздел отдаёт **Api и описание данными**, всё остальное общий слой делает
сам. Старая — антипример: контроллер на раздел, функции в пропсах, обобщение поверх
обобщения. Правила, которые дают эту разницу, и чек-лист — в скилле
[`simple-feature-design`](.claude/skills/simple-feature-design/SKILL.md); сверяться при
**любой** новой фиче, а не только в редакторе.
Полные правила, примеры и чек-лист компонента — в [`webSite/frontend/CLAUDE.md`](webSite/frontend/CLAUDE.md).
Если код нарушает слой — его переписывают, а не «оставляют пока так».

## Локальный запуск

```bash
cd webSite
./scripts/dev.sh     # docker (nginx + postgres) + backend + frontend, одной командой
./scripts/stop.sh    # погасить всё (dev-серверы + контейнеры)
```

Приложение открывается на **http://localhost:3400** — всё идёт через nginx, как на проде.
Весь локальный стек намеренно живёт на портах `340x`: `4000/4001/4010/4432` занимает проект
focuzy, `3000` — ещё один проект, оба разрабатываются параллельно.

| Что | Где |
|-----|-----|
| Фронт | `http://localhost:3400` → nginx → Next (:3401) |
| API | `http://localhost:3400/api` → nginx → NestJS (:3402) |
| Swagger | `http://localhost:3400/api/docs` (JSON: `/api/docs-json`) |
| Postgres | `localhost:3403` (внутри контейнера 5432) |
| Файлы медиатеки | `http://localhost:3400/uploads/...` → nginx → NestJS → папка `backend/uploads` |

**Почему именно через nginx, а не по портам напрямую:**

- OAuth-колбэк Google регистрируется на `http://localhost:3400/api/auth/google/callback`,
  а бэкенд после логина редиректит на `/?token=...` — **относительно**. И то, и другое верно
  только если фронт и API на одном origin. Без nginx колбэк уходит в никуда.
- Один origin ⇒ фронт ходит в API относительными путями (`basePath: ""`) ⇒ **CORS не нужен**.

**Грабли:**

- Наружу postgres отдаётся на `3403` (5432 занят сторонним сервисом, плюс держим весь стек
  на 340x) — `docker-compose.yml`. Внутри контейнера порт прежний (5432) — на проде ничего
  не меняется. nginx внутри контейнера тоже слушает 80, наружу публикуется как 3400.
- `pkill -f "nest start"` убивает только обёртку; дочерний node продолжает держать порт 3402
  и отвечать **старым кодом**. Гасить надо по порту: `lsof -ti:3402 | xargs kill -9`
  (это уже делает `scripts/stop.sh`).
- **Порт превью — только тот, что держит сам стек, а не Docker.** Панель превью, останавливая
  сервер, бьёт по процессу, который слушает его порт. 3400 держит проброс портов Docker
  Desktop — остановка превью на 3400 роняла весь движок Docker (лечится перезапуском
  Docker Desktop). Поэтому у «stack» в `.claude/launch.json` порт 3402 (бэкенд, его
  поднимает `dev.sh`; заодно сигнал, что стек готов), а панель после старта переводится
  на `http://localhost:3400` — Next без nginx `/api` не проксирует. Конфиг «docker» в том
  же файле этим грешит по-прежнему: его порт держит Docker. Ещё панель выставляет `PORT`
  в окружение, поэтому `dev.sh` задаёт бэкенду `PORT=3402` явно: из окружения он сильнее
  `backend/.env`.
- **Статику фронтенда (`NEXT_OUTPUT=export`) не собирай в `frontend/`** — даже при
  остановленном dev: промежуточная сборка всё равно пишет в `.next`, `distDir` меняет
  только каталог выгрузки. Образ `headless/` собирает её в Docker, для пробы — копия папки.
  Подробности — [`webSite/headless/README.md`](webSite/headless/README.md).
- **Не запускай `npm run build` при работающем dev-сервере.** И `next build`, и `nest build`
  пишут в тот же каталог (`.next`, `dist/`), что и watch-режим: dev-сервер после этого отдаёт
  `500 MODULE_NOT_FOUND` из затёртого кэша. Лечится только перезапуском с чисткой
  (`rm -rf .next` / `rm -rf dist`). Сначала гаси dev (`./scripts/stop.sh`), потом собирай.

## Коммиты

Репозиторий публичный — история читается снаружи, из неё собираются заметки к выпускам.
Формат — [Conventional Commits](https://www.conventionalcommits.org/), **на английском**:

```
<тип>(<область>): <что сделано, повелительно, со строчной, без точки, до 72 символов>

<необязательно: зачем и что важно знать, строки до 72>
```

| Тип | Когда |
|-----|-------|
| `feat` | новая возможность для пользователя панели или API |
| `fix` | исправление ошибки |
| `docs` | только документация (`docs/`, README, `implemented/`, CLAUDE.md) |
| `refactor` | перестройка кода без изменения поведения |
| `perf` | быстрее, то же поведение |
| `test` | тесты |
| `build` | Dockerfile, зависимости, сборка |
| `ci` | `.github/workflows/` |
| `chore` | прочее служебное |

Область — раздел системы: `api` (внешнее `/api/v1`), `mcp`, `editor` (редактор контента),
`pages`, `contents`, `products`, `files`, `users`, `settings`, `domains`, `backups`, `auth`,
`db` (миграции), `headless` (образ), `prod`. Нет подходящей — без области.
Ломает совместимость API, образа или базы — `!` после области и абзац
`BREAKING CHANGE: …` в теле.

Примеры: `feat(api): expand linked records with ?expand=`,
`fix(editor): keep filter chips after page change`, `feat(db)!: share list settings across users`.

Один коммит — одно логическое изменение. Коммитить и пушить — только когда попросили.

Инфраструктура прода — в [`webSite/prod/`](webSite/prod/) (`docker-compose.yml`, nginx,

## Архитектура — backend (`webSite/backend/`)

NestJS 9 + `sequelize-typescript` + PostgreSQL. Точка входа — `src/main.ts`:
глобальный префикс `api`, порт из `PORT` (локально 3402, в контейнере 3010),
Swagger на `/api/docs`.

- **Глобальный JWT-гард.** `AuthGuard` подключается как `APP_GUARD` в `app.module.ts` —
  **все маршруты защищены по умолчанию**. Публичные помечаются декоратором `@Public()`.
  После проверки токена гард кладёт payload в `req.user`.
- **Контент общий, `userId` — автор.** Записи всех списков видят и правят все вошедшие
  (права по ролям — позже); `userId` записи — только кто её завёл, в карточке это строка
  «Автор». **`userId` берётся из JWT (`req.user.id`), НИКОГДА из тела запроса.**
  Расширение или сужение доступа — проверка роли из того же JWT в сервисе.
  Доменная модель — `src/DOMAIN.md`.
- **Схема БД — миграциями.** При старте схему приводит `MigrationsService` (у Sequelize
  `synchronize: false`), тремя шагами: таблицы, которых нет, — целиком; миграции; индексы
  моделей у существующих таблиц (`sync` без `alter`). Именно так, а не `sync` до миграций:
  тот досоздаёт индексы модели, и индекс на колонку, которую ещё не добавила миграция,
  ронял старт на старой базе (обновление до v0.2.0 пришлось доводить руками). Существующие
  таблицы сами не меняются: новая колонка, индекс, переименование, перенос
  данных — миграция `src/migrations/NNNN-суть.ts`, в конец списка `MIGRATIONS`
  (`migrations/index.ts`); применённые записаны в `schema_migrations`. Колонку и индекс
  можно объявить и в модели — новой установке их заведёт первый шаг; имя индекса тогда
  то же, что в миграции. Миграция переживает
  повторный запуск (`IF NOT EXISTS`, условия в `WHERE`): после восстановления копии сайта
  она прогоняется снова. Применённую не правят — исправляют следующей.
  **Любая правка модели или схемы БД — сначала спросить пользователя, нужна ли миграция**,
  и не править модель молча. Новую сущность нужно зарегистрировать в `models: [...]`,
  а её модуль — в `imports: [...]` (`app.module.ts`).
- **Один модуль = одна фича:** `<feature>/{model, dto, service, controller, module}`. PK — `SERIAL`
  (порядковый номер: он виден в админке и в адресе страницы), дерево — плоское через
  `parentId` + `sort`, а не вложенный `children[]`. **«Сортировка» (`sort`)** — стандартное
  поле каждого списка редактора, кроме файлов: `INTEGER NOT NULL`, по умолчанию 500,
  в DTO — общий декоратор `SortField()` (`infoblocks/record-sort.ts`; `null` — «не прислали»).
- **Auth:** вход по email и паролю (`auth/`): `POST /api/auth/login` → JWT, `GET /api/auth/me` —
  текущий пользователь по токену. **Локально — вход без пароля** под главным администратором:
  `DEV_LOGIN=true` в `backend/.env` даёт кнопку «Войти без пароля (dev)» на экране входа
  (`POST /api/auth/dev-login`); при `NODE_ENV=production` не работает даже с флагом.
  Так Claude сам заходит в панель превью и проверяет экраны. Пароли — bcrypt-хэш в `users.passwordHash`, наружу модель
  отдаётся только через `UserDto` (хэш физически не попадает в ответ).
- **Первичная настройка.** Регистрации в панели нет, и админ не задаётся через env. Пока в системе
  нет главного администратора (`users.isRoot`), `GET /api/auth/setup` отвечает `{ needsRoot: true }`, а страница
  `/admin` показывает экран создания главного администратора. `POST /api/auth/setup` создаёт его
  и сразу выдаёт токен. Эндпоинт публичный, поэтому **одноразовый**: как только root есть, он
  отвечает 409. Второго root не появится даже при гонке — на `users` висит частичный уникальный
  индекс `users_single_root` (`UNIQUE ("isRoot") WHERE "isRoot" = true`), проверки в сервисе для этого
  недостаточно.
  Конфиг БД и секреты — из env (`DATABASE_URL` одной строкой или пять `POSTGRES_*`;
  строка сильнее, `PRIVATE_KEY`), шаблон — `backend/.env.example`. Внешний адрес панели —
  `PUBLIC_URL` (не задан — из запроса, `external-api.controller.ts` → `originOf`).
  Google OAuth пока не подключён — задел под него остался в nginx/prod-конфигах.
- **Страницы сайта:** модуль `infoblocks/pages/` (дерево страниц) плюс `infoblocks/history/`
  (журнал изменений, общий на все разделы: `/api/infoblocks/history/:listKey`, таблица
  `history` — имя прежнее, чтобы не потерять записанное). Своих полей у страницы только стандартные — название, код, активность,
  сортировка; адрес — системное свойство «Адрес» (`url`, его проверяет раздел страниц),
  текст, мета и прочее — свойства списка (`infoblocks/settings`). Страница без родителя —
  главная, и таких может быть несколько (по одной на домен, на A/B-тест).
  Подробности — [`docs/pages.md`](docs/pages.md).
- **Настройки сайта:** модуль `settings/` — **строка на настройку** (`key` + `value`),
  без владельца: настройки общие на весь сайт, ключи и значения по умолчанию —
  `settings-values.ts` (`GET`/`PATCH /api/settings`): название сайта, `storageId` —
  хранилище для новых файлов (пусто — встроенное) и `logo` — логотип панели вместо
  SparkPanel, картинкой data URI прямо в строке (не в хранилище: копия сайта без файлов),
  `settings/logo.ts`. Логотип виден до входа, поэтому `GET /api/settings/brand`
  (название и `logoUrl`) и `GET /api/settings/logo` (картинка) — `@Public()`. Внешние хранилища — список редактора, поэтому
  модуль `infoblocks/storages/` (`infoblock_storages`, `/api/infoblocks/storages`),
  сколько угодно, тоже без владельца (список `isShared`). Своё у хранилища — название,
  активность, сортировка; подключение (адрес, бакет, ключи) — системные свойства списка,
  секретный ключ — скрытое свойство. Подключение сохраняется, только если хранилище с ним
  отвечает (`HeadBucket`, проверка значений раздела); выбранное или с файлами не удаляется,
  выбранное не выключается.
  Подробности — [`docs/settings.md`](docs/settings.md).
- **Домены сайта:** модуль `infoblocks/domains/` (`infoblock_domains`,
  `/api/infoblocks/domains`, ключ списка `domains`) — дерево «домен → поддомены»,
  2 уровня, без владельца (общие на сайт, как настройки) и без журнала; список общий
  (`isShared`), его свойства одни на всех. Запись хранит то, что набрали: у поддомена —
  **только его часть** (`ekb`), полный адрес (`ekb.farkop.ru`) сервер складывает по цепочке
  родителей и отдаёт полем `address` — переименовали домен, адреса поддоменов поменялись
  сами. Адрес уникален на весь сайт, имя нормализуется до хоста ещё в DTO; домен
  с поддоменами не удаляется (409). Подробности — [`docs/domains.md`](docs/domains.md).
  **Мультидоменное свойство** (`isMultiDomain` у свойства списка) хранит значение по
  группам доменов: общее для всех (с исключениями «кроме») плюс уникальные — каждое
  для одного или нескольких доменов; в `infoblock_values` это колонки `domainIds`
  и `exceptDomainIds`. Удалённый домен вычищается из значений сам (`forgetDomain`).
  Подробности — [`docs/infoblock-settings.md`](docs/infoblock-settings.md).
- **Пользователи:** модуль `users/` — учётные записи панели (`GET`/`POST /api/users`,
  `PATCH /api/users/{id}` + история). Сущность без `userId` (вторая — общие на сайт
  `settings`): она сама определяет тенанта, поэтому изоляции по нему нет, а её место занимает проверка роли:
  список видят все, правит только `root`. Удалить можно любого, кроме `root` (он приходит
  с `isBlocked`); забрать доступ, не удаляя, — флаг `isActive`.
  `users.isRoot` — только признак главного администратора (он же в JWT: `{ id, email, isRoot }`;
  токен без него — 401 «Сессия устарела»); роль из справочника назначают
  **системным свойством «Роль»** списка `users` (привязка к контенту из списка `roles`).
  Роли — модуль `infoblocks/roles/` (`infoblock_roles`, `/api/infoblocks/roles`), общие
  на панель, правит `root`; назначенная роль не удаляется (`isBlocked`, 409).
  Подробности — [`docs/users.md`](docs/users.md).
- **Товары:** модуль `infoblocks/products/` (`infoblock_products`, `/api/infoblocks/products`,
  ключ списка `products`) и вложенный `categories/` (`infoblock_products_categories`,
  `/api/infoblocks/products/categories`, ключ `product-categories`, дерево), оба с `userId`.
  Ключи списков — в `product-lists.ts`. Категории товару назначают **системным свойством
  «Категории»** (множественная привязка к контенту из `product-categories`); категория
  с привязками или вложенными не удаляется (`isBlocked`/409), удаление товара стирает его
  значения свойств. Подробности — [`docs/products.md`](docs/products.md).
- **Контент:** модуль `infoblocks/contents/` — типы контента (`infoblock_contents`,
  `/api/infoblocks/contents`, ключ списка `contents`), и вложенный `items/` — их элементы
  (`infoblock_contents_items`, `/api/infoblocks/contents/:contentId/items`, ключ
  `content-items.<номер типа>`); оба с `userId`, оба — деревья по `parentId` (глубина —
  настройка списка). У элементов каждого типа свои свойства и свой журнал (тип записи
  в журнале — полный ключ списка); элемент адресуется вместе с типом, тип с элементами
  не удаляется (`isBlocked`/409). **Название и код типа — имя и код списка его элементов**:
  сервис типов пишет их в настройки списка (`assignIdentity`), код типа обязателен.
  Подробности — [`docs/contents.md`](docs/contents.md).
- **Файлы:** разделы и файлы — списки редактора, поэтому оба в `infoblocks/files/`:
  разделы — `sections/` (`infoblock_files_sections`, `/api/infoblocks/files/sections`,
  ключ списка `file-sections`), файлы — сам модуль (`infoblock_files`,
  `/api/infoblocks/files`, ключ `files.<номер раздела>`). У файла нет ни владельца
  (файлы общие на сайт), ни адреса в базе — адрес собирается из ключа объекта
  и хранилища, а ключ — из номера файла и его кода: `00/00/78/voprosy-i-otvety.pdf`. `storage/` — хранилище файлов: встроенное — папка на диске (`UPLOADS_DIR`,
  локально `backend/uploads`, в образе — том `/data/uploads`), файл лежит по своему ключу;
  внешнее — S3 из настроек. Встроенное отдаёт по `/uploads/<ключ>` сама панель
  (`storage/serve-uploads.ts`; локально и на проде nginx передаёт ей этот путь), исполняемые
  типы (`.html`, `.svg`) — с `Content-Disposition: attachment`, по расширению.
  Файл лежит в разделе (`sectionId`) или, загруженный через свойство «Файл»/«Изображение»,
  помнит свойство (`propertyId`, список `property-files.<номер>`). **Разделов свойств
  в базе нет**: раздел свойства (`property-<номер>`) и группу его списка с путём
  в названии («Контент / SEO / Мета-теги», `group-…`) сервер собирает по файлам при выдаче
  (`sections/section-groups.ts`), наружу — `isReadOnly`, у группы ещё `isGroup`. **Привязка файла к записи — значение свойства**
  (`infoblock_values.number`), отдельной таблицы связей нет: один файл могут выбрать
  сколько угодно записей. **Значение может быть и внешним файлом** — адресом `https://…`
  в `infoblock_values.text` (картинки старого сайта без перекачки); сервер его не скачивает,
  а «Забрать в хранилище» (`POST /api/infoblocks/files/import`, без внутренней сети —
  `files/fetch-external.ts`) кладёт его к себе. Подробности — [`docs/files.md`](docs/files.md).
- **Формы обратной связи:** два списка редактора — формы (`infoblocks/forms/`,
  `infoblock_forms`, `/api/infoblocks/forms`, ключ `forms`) и поля форм
  (`infoblocks/forms/fields/`, `infoblock_forms_fields`, `/api/infoblocks/forms/fields`,
  ключ `form-fields`). **Владельца нет** — формы и поля общие на сайт, оба списка
  `isShared`. У поля своё только стандартное (код, название, активность), плейсхолдер —
  системное свойство «Плейсхолдер», остальное — свойства списка. Поле форме не принадлежит:
  форме поля подключают **системным свойством «Поля»** (множественная привязка к списку
  `form-fields`), одно поле — в любом числе форм, порядок — порядок значений. Коды формы
  и поля уникальны на сайт (индексы), подключённое поле и выбранная в привязке форма
  не удаляются (`isBlocked`, 409).
  Прежняя схема (`forms` + `form_fields`, поле внутри формы) лежит в `to_delete/forms/`.
  Подробности — [`docs/forms.md`](docs/forms.md).
- **Инфоблоки:** модуль `infoblocks/` — три сущности одной фичей: типы
  (`infoblock_sections`; в интерфейсе они «типы инфоблоков», в коде остались `section`),
  сами списки (`infoblocks`) и их записи (`infoblock_elements`).
  Удаление верхнего уровня уносит нижние в транзакции; ключ записи в журнале — с
  приставкой (`section-1`, `block-2`, `element-3`). Элемент адресуется вместе со своим
  инфоблоком (`/api/infoblocks/blocks/:blockId/elements/:id`), иначе по одному номеру
  элемента правились бы чужие списки. Подробности — [`docs/infoblocks.md`](docs/infoblocks.md).
- **Настройки списков:** модуль `infoblocks/settings/` — у любого списка редактора контента
  имя, код, уровни вложенности (1 — плоский список, больше — дерево; галочка
  «Древовидная структура» в окне — тот же `maxDepth`, своей колонки нет) и политика символьного кода записей (`infoblock_settings`),
  вкладки карточки (`infoblock_settings_tabs`), свойства записей (`infoblock_settings_properties`) с вариантами
  «Списка» (`infoblock_settings_property_options`). Чем эти свойства заполнили — соседний
  модуль `infoblocks/values/`: сами записи списка (`infoblock_records` — дерево)
  и значения их свойств (`infoblock_values`, **строка на значение**). Каждая сущность лежит своими
  строками: по значениям свойств нужно будет искать и сортировать записи, а значение
  привязано к номеру свойства, а не к коду — код правят. Список и запись адресуются строковыми
  ключами (`pages`, `infoblock-elements.3` / `element-7`); перечень видов —
  `infoblock-kinds.ts`, правки свойств пишутся в журнал раздела записи. Вкладки правятся
  сразу своими маршрутами (`/api/infoblocks/settings/:listKey/tabs`), остальное — одним
  `PUT /api/infoblocks/settings/:listKey`. Блоки, страницы и роли модуль только читает — для
  проверки ссылок и списка «привязки к контенту».
  **Вид таблицы** — какие колонки раздела и свойства видны, порядок, ширина — свой
  у каждого пользователя: `infoblock_settings_columns` (`userId` того, кто смотрит, даже
  у общих списков), строка на видимую колонку, строк нет — колонки по умолчанию;
  `GET`/`PUT`/`DELETE /api/infoblocks/settings/:listKey/columns`, без `ListEditGuard`.
  **Поля фильтра таблицы** — наоборот, одни на список для всех: `infoblock_settings_filters`
  (строка на поле, по `settingsId`, без `userId`), `GET`/`PUT …/:listKey/filters`, тоже без
  `ListEditGuard`; что в полях выбрано, в базе нет — это в адресе страницы.
  **Скрытое свойство** (`isHidden`, «Не отдавать через API») хранит значение, но наружу его
  не отдаёт ни один маршрут, в журнале — `••••••`; сервер читает такие значения
  `PropertyValuesService.codeValues`. **Свойство из внешнего источника** (`isExternal`,
  «Внешний источник») в карточке закрыто, а значения из панели (`PATCH …/values` без `via`
  в JWT) сервер не принимает — пишет их только внешняя система через внешнее API или MCP.
  **Внешний ID записи** (`externalId`, номер в системе-источнике) — у записи любого списка,
  колонкой общей строки `infoblock_records`, уникален в списке (частичный индекс); задаёт
  его тоже только интеграция (`PATCH …/values` с `via`), наружу его добавляет
  `RecordsService.rows`, карточка показывает его на просмотр. **Проверку значений** своего списка раздел добавляет
  `PropertyValuesService.registerCheck` — она идёт в транзакции сохранения (адрес страницы,
  подключение хранилища).
  **Системные свойства** (`isBlocked`: через API не меняются и не удаляются) перечислены
  в одном месте — `infoblocks/settings/properties/system-properties.ts`, по виду списка;
  при старте сервера их сверяет с базой `SystemPropertiesService`. **Общие списки**
  (`isShared`: `users`, `roles`, `domains`, `forms`, `form-fields`, `storages`) держат настройки одни на сайт (владелец `0`), а списки
  `isRootOnly` правит только `root` (`ListEditGuard` на контроллерах настроек и значений).
  **Символьный код записей** («Обязательный», «Обязательный и уникальный») проверяет
  и сервер: сервисы списков с кодом зовут `assertRecordCode` (`settings/record-code.ts`)
  при создании и правке — `400` пустой, `409` повтор.
  Подробности — [`docs/infoblock-settings.md`](docs/infoblock-settings.md).
- **Страница записей для таблицы:** модуль `infoblocks/records/` —
  `GET /api/infoblocks/records/:listKey` у любого списка редактора: страница, поиск,
  фильтр (поля записи и значения свойств), сортировка → `{ items, total, values }`
  (значения свойств — только записей страницы; значений всего списка маршрутом нет). Записи
  берёт у сервиса раздела (реестр `RecordsService`), отбирает общей чистой функцией
  `pageRecords` (`records-page.ts`); у дерева страница — записи верхнего уровня со всеми
  ветками. Без `sort` — по полю «Сортировка», равные — новые сверху. Модуль импортирует модули всех разделов, его — никто (иначе кольцо). Новый
  список редактора — строка в реестре. Пока отбор в памяти: записи раздела читаются
  целиком, наружу уходит страница. Подробности — [`docs/infoblock-settings.md`](docs/infoblock-settings.md).
- **Черновики записей:** модуль `infoblocks/drafts/` (`infoblock_drafts`,
  `/api/infoblocks/drafts/:listKey/:recordId`) — **отложенное сохранение** записи любого
  списка, кроме пользователей, ролей, доменов, типов контента и файлов (`isDraftless`, в экранах — `blockedSettings.isDraftEnabled: false`): изменённые поля записи (как тело `PATCH` раздела) и свойства
  (как тело `PATCH …/values`) JSON-ом. Таблицы разделов и значения черновика не видят —
  в них опубликованное. Публикует фронтенд обычным сохранением раздела и значений, потом
  `POST …/publish` снимает черновик; `isNew` — запись заведена черновиком, на сайте её нет.
  Включается настройкой списка `isDraftEnabled`; страница таблицы ищет и сортирует
  с черновиками поверх (`withDrafts`), отдаёт опубликованное и `drafts` рядом.
  Подробности — [`docs/drafts.md`](docs/drafts.md).
- **Резервные копии списков:** модуль `infoblocks/backups/` (`infoblock_backups`,
  `/api/infoblocks/backups/:listKey`) — снимок одного списка JSON-ом (правила записей,
  вкладки, свойства с вариантами, поля фильтра, строки таблицы раздела, значения,
  черновики) и возврат к нему: заменой целиком или «только вернуть удалённые».
  Перед восстановлением сама снимается копия текущего; всё в одной транзакции,
  мимо сервисов разделов. Номера записей, вкладок, свойств и вариантов сохраняются —
  поэтому чужие номера в файле копии дают 409; защищённые записи (`isBlocked`, берутся
  у `RecordsService.rows`) не удаляются. Списки с копиями — `BackupsService.sources`:
  страницы, элементы типов контента, товары, категории, пользователи и роли (последние
  два — только root, и на чтение). Подробности — [`docs/backups.md`](docs/backups.md).
- **Копии всего сайта:** модуль `backups/` (`site_backups`, `/api/site-backups`, только
  root, и на чтение) — вся база, кроме самих копий, без файлов: строки каждой таблицы
  схемы (`json_agg`), сжатые gzip в `BYTEA`. Схемы в копии нет. Восстановление — одна
  транзакция: копия текущего, `TRUNCATE` всех таблиц, заливка по порядку внешних ключей
  (`json_populate_recordset`, только колонки, что есть и в копии, и в базе), счётчики
  номеров за последний, потом сверка системных свойств. Не легло — 400, база прежняя.
  Подробности — [`docs/backups.md`](docs/backups.md#копия-всего-сайта).
- **Внешнее API:** модуль `external-api/` — `/api/v1` для сайта и интеграций по заголовку `X-Api-Key`
  (маршруты `@Public()` + `ApiKeyGuard`, в Swagger панели их нет): у каждого списка
  `items`, `items/{idOrCode}`, `items/external/{externalId}`, `properties`, `facets`; списки — `/pages`,
  `/contents/{код типа}`, `/catalog/products`, `/catalog/categories`, `/domains`
  (`api-lists.ts`). Свойства — объектом по коду, «Список» — кодом варианта, скрытые —
  никогда; отбор — общий `pageRecords`, `filter[код]` переводит `external-values.ts`; значения
  читаются только нужные (свойства фильтра, записи страницы), привязки сужаются в базе
  по индексу `infoblock_values_property_link`.
  **Спецификацию OpenAPI сервер собирает из настроек списков** (`openapi-spec.ts`,
  `/api/v1/openapi.json`) — руками документацию не пишем. Ключи — `api_keys` (хэш SHA-256,
  ключ виден один раз); управляет ими root (`/api/external-api`, `RootOnlyGuard` из `common/`).
  **Запись** (`write/`): права ключа задаются при создании и не меняются — `isWritable`
  и `writeLists` (null — все списки), иначе 403; `POST`/`PATCH`/`DELETE …/items`, upsert
  `PUT …/items/external/{externalId}` и пакет `POST …/items/batch` (до 500, ошибка одной
  записи не держит остальные). Свойства — по кодам, «Список» — номером или кодом, привязка —
  номером, кодом или `{ externalId }`. Пишет, как MCP, **маршрутами панели** через
  `PanelClient` (`common/`) от имени создателя ключа с `via` «API «ключ»»: проверки и журнал —
  панели; поля и свойства — две транзакции, не легли свойства — запись откатывается вручную.
  Запись по номеру, коду и внешнему ID ищется запросом по индексу (`record-lookup.service.ts`).
  Подробности — [`docs/external-api.md`](docs/external-api.md).
- **MCP:** модуль `mcp/` — сервер MCP для ИИ-ассистентов, `POST /api/mcp` (Streamable HTTP
  без сессий, JSON-RPC написан руками, без SDK), по личному токену `spm_…` в
  `Authorization: Bearer` (`@Public()` + `McpTokenGuard`). Ассистент работает **от имени
  владельца токена, со всеми его правами**: инструменты (`mcp-tools.ts`) ходят **в маршруты
  панели**, а не в сервисы разделов — `PanelClient` (`common/`) выпускает JWT владельца на минуту и
  вызывает `/api/…` на своём порту, поэтому гарды, DTO, правила разделов и журнал те же,
  что в браузере. В этом JWT — `via` («MCP «токен»»): `historyAuthor` несёт его дальше,
  и история подписывает правку «Иван · MCP «…»». Черновики поддержаны: запись отдаётся
  с `draft` рядом, `save_record` пишет в `draft` или `published` (внешний ID — сразу,
  мимо черновика). Списки MCP — `mcp-lists.ts`
  (пользователей, ролей, хранилищ и форм нет). Токены — `mcp_tokens`, журнал вызовов —
  `mcp_calls` (30 дней, всё, кроме полей отбора, — JSON `details`); root видит все, остальные —
  свои (`/api/mcp/tokens`, `/api/mcp/calls`). Тело любого маршрута — до 25 МБ, как у nginx
  (`main.ts`: MCP и внешнее API пишут маршрутами панели, предел у всех один; свой
  JSON-парсер отменяет парсер Nest, поэтому он поставлен явно).
  Подробности — [`docs/mcp.md`](docs/mcp.md).
- **Грабли JWT:** `JwtModule` подключается через `registerAsync` + `ConfigService`. Синхронный
  `register({ secret: process.env.PRIVATE_KEY })` не работает: метаданные `AuthModule`
  вычисляются при импорте, раньше чем `ConfigModule.forRoot()` прочитает `.env`, и логин падает
  с `secretOrPrivateKey must have a value`.

## Архитектура — frontend (`webSite/frontend/`)

Next.js 14 (pages router) + Redux (thunks) + **Ant Design** (v6, **стандартная тема**; Tailwind
оставлен как утилиты раскладки, preflight выключен — он ломает стили antd). **Строгая слоистость** —
полные правила и чек-лист компонента в [`webSite/frontend/CLAUDE.md`](webSite/frontend/CLAUDE.md)
(обязательны к соблюдению):

```
pages/ → components/ → logic/ → redux/ → api/ → src/generated/
```

Что уже есть:

- **Доступ.** `components/layout/AdminLayout.tsx` — гард на каждой странице админки: пока идёт
  проверка — индикатор, без авторизации — экран входа или первичной настройки
  (`components/admin/`), иначе — приложение. JWT хранится в cookie `access_token`; при загрузке
  сессия восстанавливается запросом `/api/auth/me`, а если входить не под кем — проверяется
  `/api/auth/setup`. Анимированный фон экрана входа — `components/ui/VantaHalo.tsx`.
- **Приложение.** `components/layout/AppShell.tsx` — левое меню (`sidebar/`) + область раздела.
  Учётная запись и выход — внизу левого меню (`sidebar/SidebarUser.tsx`). Отдельной шапки
  с названием раздела нет: название есть на самом экране (в редакторе контента это название
  пункта меню), а где пользователь находится, видно по подсветке в меню.
  Разделы перечислены **одним списком** в `config/navigation.ts`
  (главная, страницы, контент, товары, обратная связь, файлы, пользователи, настройки); из него строятся меню,
  заголовки заглушек и подсветка активного пункта (`logic/navigation/useNavigation.ts`).
  Пункт может разворачиваться в подменю. Статическое — `children` у раздела в конфиге:
  такой пункт только группа, своей страницы у него нет («Пользователи» → «Пользователи»,
  «Роли»). Подменю из данных — `childrenSource` у раздела: «Контент» раскрывается в дерево
  типов контента (`logic/contents/useContentsMenu.ts`), сам пункт ведёт на список
  типов. Так же было у инфоблоков — вернётся вместе с разделом из `to_delete/`.
  Страницы разделов — `pages/admin/*.tsx`; нереализованные пока показывают заглушку
  `components/section/`.
- **Форма, описанная данными.** `components/editorForm/` + `logic/editorForm/` — поля, группы
  и состояние формы. Экран перечисляет поля данными, разметку не пишет; на этом слое сидят
  и шторка редактора контента, и отдельные экраны вроде «Настроек», поэтому поля везде
  выглядят одинаково. Контракт — [`docs/editor-form.md`](docs/editor-form.md).
- **Редактор контента.** `components/contentEditor/` + `logic/contentEditor/` — универсальная
  связка «таблица + шторка» для всех разделов со списками: дерево, вкладки, история изменений,
  подстановка переменных. Раздел отдаёт ему **Api** (где лежат записи) и **описание**
  (колонки, поля, вкладки) и не пишет свой экран. Загрузку, сохранение и удаление ведёт
  сам редактор: данные всех списков — в одном срезе `state.lists`, состояние редактора
  (что открыто, что набрано в форме) — в `state.contentEditor`.
  Контракт — [`docs/content-editor.md`](docs/content-editor.md).
- **Настройки списков.** `components/contentEditor/settings/` + `logic/listSettings/` +
  `logic/contentEditor/useListProperties.ts` — кнопка «Настройки» у каждого экрана редактора
  контента: имя, код, древовидная структура, вкладки карточки записи
  и свойства записей (строка, число, текст, HTML — визуально (TipTap) или кодом (CodeMirror), список, файл,
  изображение, привязка к записям контента, привязка к типу контента, привязка
  к значениям списка, таблица). Свойства раскладываются
  по вкладкам; символьный код — не свойство, а настройка списка.
  Параметры типа и вкладка свойства — отдельными окнами из меню его строки;
  множественность можно включить любому типу, кроме таблицы. Контроллер раздела называет только ключ списка (`settings: { key: ListKey… }`),
  поля свойств, вкладку «Свойства», дерево и сохранение значений редактор подмешивает сам.
  Выбор файла медиатеки — общее поле формы `media` (`components/editorForm/media/` +
  `logic/mediaLibrary/`). Подробности — [`docs/infoblock-settings.md`](docs/infoblock-settings.md).
- **Страницы сайта.** `components/pages/` + `logic/pages/` — дерево страниц на редакторе
  контента. Открытая страница живёт в адресе (`/admin/pages?id=2`) — как и открытая запись любого списка на новом редакторе, у новой идентификатора
  ещё нет — он появляется после сохранения. Подробности — [`docs/pages.md`](docs/pages.md).
- **Новый редактор контента.** `components/contentEditorNew/` — пишется с нуля вместо
  старого, на нём живут «Страницы», «Контент», «Товары», «Файлы», «Пользователи» и «Роли». Раздел
  называет код списка, отдаёт **Api** (`list`, а `create`/`update`/`remove` — если список
  это умеет: чего Api не умеет, того редактор не показывает) и описывает данными колонки таблицы и поля
  карточки; таблицу, карточку записи, настройки списка со свойствами и журнал ведёт сам
  редактор. Данные всех списков — в одном срезе `state.contentEditorNew` по коду списка.
  Что из настроек списка раздел не отдаёт пользователю, он закрывает (`blockedSettings`).
  Первая колонка любой таблицы — ID записи (по умолчанию; в «Колонках таблицы» её можно
  спрятать и переставить), за колонками раздела — «Создано» и «Изменено» (даты записи
  отдаёт DTO каждого списка; «Изменено» — с правкой свойств), они же внизу вкладки
  «Запись» в карточке. Ширины колонок точные, тянется одна — первая после ID. Таблицу отбирают поиском (по ID, коду записи
  и колонкам с `isSearch`) и **фильтром** по колонкам раздела и свойствам записей
  (`contentEditorNew/filters/`) — оба в плашке над таблицей, поле фильтра — чип,
  выбор по виду колонки, у «Списка»,
  привязки и логических колонок — варианты. Набор полей фильтра общий и на сервере,
  выбранное — в адресе (`?f.name=…`). **Таблица — страницами с сервера** (20/50/100):
  поиск, фильтр, сортировку и страницу ведёт `GET /api/infoblocks/records/:listKey`,
  один на все списки; у дерева страница — записи верхнего уровня со всеми ветками.
  Кнопка «Экспорт» выгружает отобранное таблицей в CSV — поля записи и свойства
  галочками (`contentEditorNew/export/`). Кнопка «Резервные копии» (раздел включает
  её `settings.isBackupShown`) — шторка копий списка и окно восстановления
  (`contentEditorNew/backups/`, [`docs/backups.md`](docs/backups.md)).
  В запись можно перейти (`recordPath="/admin/files/:id"`), защищённую от удаления
  запись сервер помечает `isBlocked`, свойства «Файл»/«Изображение» правятся полем
  с загрузкой, обе привязки (к записям и к типу контента) — выбором записи
  (`FieldType.Link`), «Таблица» — сеткой ячеек (`FieldType.Table`).
  Контракт — [`webSite/frontend/CLAUDE.md`](webSite/frontend/CLAUDE.md).
- **Контент.** `components/contents/` + `logic/contents/` — пункт меню «Контент»
  после «Страниц»: `/admin/contents` — типы контента на новом редакторе контента,

  контента (список `content-items.2`), имя и код списка — название и код типа
  (в окне настроек их нет ни у одного списка). Устроено как «Файлы».
  Подробности — [`docs/contents.md`](docs/contents.md).
- **Формы обратной связи** — раздел скрыт из панели до возвращения: экраны, логика
  и сетевой слой лежат в `to_delete/feedback/` (там же README, как вернуть), бэкенд
  работает. Подробности — [`docs/forms.md`](docs/forms.md).
- **Пользователи.** `components/users/` + `logic/users/` — пункт меню с подменю
  «Пользователи» (`/admin/users`) и «Роли» (`/admin/users/roles`), оба на новом редакторе
  контента. Главного администратора не удалить (замок, `isBlocked`), у его email — метка; роль назначают в карточке

- **Инфоблоки.** `components/infoblocks/` + `logic/infoblocks/` — три уровня, три

  ключ — один раз в окне создания), «Документация» — спецификация с сервера во встроенном

`/admin/infoblocks` (плюс вложенные `/[sectionId]` и `/[sectionId]/[blockId]`),
`/admin/contents` (плюс вложенный `/[contentId]`),
`/admin/files` (плюс вложенный `/[sectionId]`),
`/admin/products` (плюс вложенный `/categories`), `/admin/users` (плюс вложенный `/roles`)
и `/admin/settings` (плюс вложенные `/storages`, `/domains`, `/api`, `/mcp` и `/backups`) (реализованы), `/admin/mail` — заглушка.

Зависимости только вниз. Ключевое:

- Компоненты **не** импортируют `api`/`redux`/`src/generated` напрямую и **не** прокидывают
  горы пропсов — берут данные и колбэки из хуков `logic/` (`use<Feature>()` / `use<Feature>Actions()`).
- Сеть — только в `api/` (обёртки над сгенерированным клиентом; конфиг — `src/api/client.ts`).
  `basePath: ""` ⇒ относительные `/api`-пути ⇒ тот же origin через nginx ⇒ без CORS.
- **`src/generated/` — авто-генерация из Swagger, руками НЕ редактируем.** Поменялся бэкенд →
  `npm run generate-api`. См. skill `frontend-api-client` и `frontend/API_CLIENT_README.md`.
- **Ant Design требует двух настроек в этом стеке** (обе уже сделаны, не удалять):
  `transpilePackages` в `next.config.js` — иначе ESM-пакеты `antd`/`rc-*` роняют SSR;
  сборка стилей в `pages/_document.tsx` — иначе первый рендер приходит без оформления.
