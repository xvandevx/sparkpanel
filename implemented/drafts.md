# Черновики записей

## 2026-10-29 — черновики для любого списка редактора контента

**Что сделано**

- Таблица `infoblock_drafts` и модуль `infoblocks/drafts/`: `GET`/`PUT`/`DELETE`
  `/api/infoblocks/drafts/:listKey/:recordId` и `POST …/publish`.
- Настройка списка `isDraftEnabled` («Черновики») и `hasDrafts` в DTO настроек;
  у файлов черновиков нет (`isDraftless` в `infoblock-kinds.ts`). Выключить при
  существующих черновиках — `409`.
- Страница таблицы (`records/`): поиск, фильтр и сортировка с черновиками поверх
  (`withDrafts`), параметр `isDraft` для вида «Черновики», в ответе `drafts`
  и `draftsCount`. Удаление записи стирает и её черновик (`PropertyValuesService.remove`).
- Фронтенд: `components/contentEditorNew/drafts/` (наложение, действия, метка, блок),
  вид «Все записи / Черновики N / История изменений», метка и значок публикации
  в строке, «Опубликовать» в панели отмеченных, переключатель «Черновик / Опубликовано»
  в карточке, блок черновика, отметки изменённых полей и вкладок, галочка в настройках.

**Ключевые решения**

- **Черновик — отложенное сохранение**, одна общая таблица. В нём те же два тела
  запроса, что шлёт «Сохранить» (поля записи и значения свойств), только изменённое.
  Публикация — то же сохранение маршрутами раздела и значений, поэтому проверки,
  журнал и запись в таблицы разделов не пишутся заново. Отклонены:
  - строка-черновик в таблице раздела (`isDraft` + `draftId`): каждый запрос каждого
    раздела пришлось бы учить пропускать черновики (утечка на сайт при любом пропуске),
    уникальные индексы (`users.email`, коды форм, адреса доменов) — делать частичными,
    у черновика свой номер — журнал и значения при публикации переносить;
  - таблица черновиков рядом с каждой таблицей раздела: 11+ таблиц и дублирование
    моделей, а свойства этим не решаются;
  - `isDraft` в `infoblock_values` + черновик полей в `infoblock_records`:
    `infoblock_records` — мост «запись ↔ значения», а не данные записи.
- Черновик хранит и поля записи (название, код, активность, сортировку, родителя),
  а не только свойства, как в farkopru: у пользователей, например, почти всё —
  собственные поля.
- Поля и свойства черновика — JSON. Пока таблица отбирает записи в памяти, это
  не мешает; когда отбор переедет в SQL, фильтр по свойствам черновика потребует
  запросов к JSON — тогда свойства черновика можно перевести в строки.
- Запись, заведённая черновиком, получает строку в таблице раздела сразу (иначе нет
  номера) и черновик с `isNew`. Отдельного «не опубликована» не заводили: сначала
  обсуждали обойтись «Активностью», но заказчику нужно создавать запись черновиком.
- Публикация из «Опубликовано» черновик не трогает (решение заказчика).
- Страница таблицы отдаёт опубликованное, а черновики — рядом: карточке нужны обе
  версии, а таблица накладывает черновик сама.
- Родитель из черновика в таблице не применяется — дерево по опубликованному.

**Отступления от задания** (farkopru `content/`): черновик там — JSON-колонка
`dataDraft` у записи и только данные без служебных полей; здесь — отдельная таблица
и вся запись.

**Не сделано**

- Сохранение черновика в журнал не пишется — журнал получает правки при публикации.
- Кнопки «Опубликовать все» в шапке нет: публикуют из вида «Черновики» отметкой строк.
- У изменённого поля только отметка; подписи «На сайте: …» со значением нет.
- Внешнего API сайта нет — правило «пропускать `isNew`» и предпросмотр появятся с ним.

**Доработка того же дня.** Публикуется только сохранённый черновик: «Опубликовать
черновик» закрыта, пока черновика нет или в карточке несохранённые правки (сначала
сохранить или отменить) — публиковать то, чего никто не сохранял и не видел в таблице,
нелогично. Добавлена «Отменить» в шапке карточки: поля возвращаются к показанной версии.
Исправлено: карточка, открытая по ссылке, собирала форму из опубликованного, пока черновик
догружался, — теперь форма собирается заново вместе с выбором версии.

**Доработка 2026-10-30.** У пользователей, ролей, доменов и типов контента черновиков
тоже нет (как у файлов): это устройство панели и сайта (типы — структура разделов),
а не контент; у элементов типов черновики остаются. На сервере — `isDraftless`
у `users`, `roles`, `domains` и `contents`
(включить нельзя, сохранить черновик — `400`), в интерфейсе — общий механизм закрытых
настроек: `blockedSettings.isDraftEnabled: false` в экранах пользователей, ролей, доменов,
типов контента, разделов и файлов, переключатель «Черновики» в окне виден, но закрыт с «Задано разделом».

**Проверено**

- `npm test` в `backend/` — 125 тестов, в том числе `withDrafts` (`records-page.spec.ts`).
- API руками: сохранение при выключенных черновиках — `400`, поиск по названию
  из черновика находит запись и отдаёт опубликованную, `isDraft=true`, выключение
  при черновиках — `409`, удаление черновика.
- В браузере (`/admin/products`): черновик названия и цвета, метка и значок в таблице,
  счётчик вида «Черновики», карточка в обоих режимах, публикация из карточки (запись,
  значение и две строки журнала), новая запись черновиком («Только черновик»),
  удаление записи стирает её черновик. Тестовые правки откатаны.
