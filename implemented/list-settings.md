# Настройки списков

## 2026-10-28 — без имени и кода в окне настроек, история закрывается разделом

**Почему.** Заказчик: имя и код списка всё равно почти везде закрыты разделом —
убрать их из окна; заголовок должен совпадать с пунктом меню; запрет «Истории
изменений» у файлов решать так же, как остальные закрытые настройки, — на фронте.

**Что сделано**

- В окне настроек нет полей «Имя списка» и «Код списка». `PUT /api/infoblocks/settings/:listKey`
  принимает `name`/`code` необязательными; без них оставляет прежние (новым настройкам —
  имя по виду списка и ключ списка кодом). Код элементов типа контента по-прежнему
  пишет сервис типов (`assignIdentity`).
- Заголовок над таблицей (`ListTitle`) — название открытого пункта меню
  (`useNavigation().currentSection`), а не имя из настроек.
- `BlockedSettings` без `name`/`code`, зато с `isHistoryEnabled`: «Файлы» (разделы
  и файлы раздела), «Хранилища» и «Домены» закрывают историю `false`, переключатель
  подписан «Задано разделом и не меняется». Фронт больше не читает `hasJournal`
  (сервер его отдаёт и по-прежнему сам не журналирует такие списки).
- В локальной базе коды `domains`, `file-sections`, `users` приведены к ключу списка:
  раньше их подменял раздел при сохранении окна (`site-domains`, `media-sections`,
  `panel-users`), теперь окно код не шлёт.

**Проверено**

- `tsc --noEmit` в `backend/` и `frontend/` — чисто; клиент API перегенерирован.
- В браузере: «Файлы» — заголовок из меню, в окне нет имени и кода, история закрыта
  разделом; сохранение глубины без имени и кода — 200, имя в базе прежнее; «Роли» —
  переключатель истории открыт; «Контент» — заголовок «Контент».

## 2026-10-27 — свои поля списков: только стандартные, остальное — свойства

**Почему.** Заказчик попросил найти у списков поля, заведённые колонками таблицы
мимо механизма свойств, и решить по каждому. Решено: у записи только стандартные
поля, всё прочее — свойства; служебное, без чего не работает код, остаётся колонкой.

**Что сделано**

- **Галочка свойства «Не отдавать через API»** (`isHidden` у
  `infoblock_settings_properties`, окно свойства — с подсказкой «почему»). Значение
  пишется, но не читается ни одним маршрутом (`valueItems`), в журнале — `••••••`;
  сервер берёт его `PropertyValuesService.codeValues`. В карточке такое поле — пароль,
  всегда пустое и необязательное: пустое не уходит, значит «прежнее».
- **Проверки раздела над значениями свойств**: `PropertyValuesService.registerCheck(kind, check)` —
  раздел в `onModuleInit` вешает проверку на свой вид списка; она получает значения
  записи после правки (по кодам, со скрытыми) и коды присланных, падает — откат.
- **Страницы**: колонка `url` и её уникальные индексы убраны, адрес — системное свойство
  «Адрес» (`url`). Формат, «вложенная — не пустой», уникальность среди соседей —
  `PagesService.checkUrl` при сохранении значений и при переносе страницы.
  `path` сервер собирает по-прежнему, из значений.
- **Хранилища**: подключение (`endpoint`, `region`, `bucket`, `accessKey`, `secretKey`,
  `publicUrl`) — шесть системных свойств, `secretKey` скрытый; список стал общим
  (`isShared`). HeadBucket — проверкой раздела при сохранении значений. Добавлен
  `isActive`: выключенное не выбрать для новых файлов, выбранное не выключить (409).
- **Роли**: `description` — обычное свойство «Описание» (заведено в настройках списка,
  значение перенесено); добавлен `isActive`.
- **Пользователи**: `users.role` (`root`/`user`) → `isRoot` (boolean), индекс
  `users_single_root` — по нему. JWT несёт `isRoot`; токен без него гард отклоняет (401).
- **Файлы**: `description` удалено совсем (колонка, DTO, карточка, поиск в выборе файла).
- **`sort` — стандартное поле всех списков, кроме файлов**: колонка с умолчанием 500
  (`record-sort.ts`: `DEFAULT_SORT`, декоратор `SortField` — `null` значит «не прислали»),
  поле «Сортировка» в карточке и колонка в таблице (`standardFields.sort`,
  `standardColumns.sort`). Порядок по умолчанию — по `sort`, равные — новые сверху
  (у файлов, где поля нет, — просто новые сверху).

**Ключевые решения**

- **Описание роли — обычное свойство, а не системное**: на него ничего в коде не опирается,
  его можно переименовать или удалить. Адрес страницы и подключение хранилища — системные:
  без них не работает сервер.
- **Признак root остался колонкой** (`isRoot`), а не свойством: на нём вход, права root
  и уникальный индекс «root ровно один» — свойству такую гарантию база не даст.
- **Проверки — регистрацией, а не импортом**: модуль значений о разделах не знает
  (разделы импортируют его), иначе кольцо модулей.
- **Скрытое свойство необязательно в карточке**: у сохранённой записи пустое поле
  значит «прежнее», и обязательность не дала бы сохранить запись, не набрав секрет заново.
- **Сортировка существующих страниц не тронута** (0, 100, 200…): ставилась вручную,
  500 — только новым.
- **Перенос данных — разовый, локально**, без миграции в коде: данные, которые нужно
  сохранить, есть только в локальной базе (ответ заказчика).

**Не сделано**

- Новая вложенная страница существует без адреса, пока не сохранятся значения (второй
  запрос карточки): адрес приходит свойством, проверить его при создании записи нечем.
- Сиды (`scripts/seed/`) отстали от API ещё до этой правки (страницы — прежняя схема,
  описание при загрузке файла); поправлен только `token.mjs` под `isRoot`.

**Как переносили данные.** Dev-сервер в watch-режиме подхватил новые модели раньше
переноса, и `sync({ alter: true })` удалил колонки `url`, `description`, `role`.
Данные вернули из снятой до правок выборки: 32 адреса страниц — значениями свойства
«Адрес», описание роли «Редактор» — свойством «Описание», `isRoot` — пользователю 3.
Урок: переносить данные до того, как правишь модель, — `alter` снимает колонку
при первом же перезапуске.

**Проверено** — `tsc` бэкенда и фронта, `jest` (114 тестов); запросами: полные адреса
страниц, отказ на повтор / неверный формат / пустой адрес вложенной, хранилище на
локальном MinIO (неверный ключ — 400, секрета нет в ответах, правка региона проходит
с сохранённым секретом), выбор выключенного и выключение выбранного, порядок по
умолчанию у ролей, пользователей, страниц. В панели: роли (активность, сортировка,
«Описание» свойством, сохранение), карточка хранилища с системными свойствами и
подсказками, карточка страницы с «Адресом», галочка «Не отдавать через API».

## 2026-10-25 — сервер проверяет «Символьный код записей»

**Почему.** Флаги `codeRequired`/`codeUnique` соблюдала только карточка в панели:
запросом в обход неё запись сохранялась с пустым или повторяющимся кодом.

**Что сделано**

- `infoblocks/settings/record-code.ts`: `codeError` (правила без базы) и
  `assertRecordCode(settings, code, isTaken)` — `400` на пустой обязательный,
  `409` на занятый уникальный. Уникальность — только вместе с обязательностью,
  как в окне настроек; уровень записи в дереве не важен.
- Вызов в create/update сервисов: страницы, товары (модулю добавлена модель
  `InfoblockSettings`), категории товаров, типы контента, элементы контента
  (уникальность в пределах типа). Проверяется итоговый код записи.

**Ключевые решения**

- **Функция, а не сервис модуля настроек**: `InfoblockSettingsModule` импортирует
  `FileSectionsModule`, обратный импорт дал бы кольцо модулей. Тот же приём, что
  у предела вложенности (`depthError`).
- **Роли, формы, поля форм — без вызова**: `@IsNotEmpty` в DTO и уникальный индекс
  на коде уже строже любой настройки.
- **Уникальность — запросом, без индекса**: индекс зависел бы от настройки, которую
  меняют в любой момент. Одновременные сохранения могут разминуться — принято.

**Проверено** — `tsc` бэкенда, `npm test` (103 теста, из них новые
`record-code.spec.ts`); бэкенд поднялся, маршруты отвечают. Запросами с токеном
не проверялось — нужен вход в панель.

## 2026-10-25 — редактор свойства «HTML»: TipTap + CodeMirror, картинки

**Что сделано**

- Поле «HTML» в карточке (`drawer/html/`): переключатель «Визуально / HTML».
  Визуально — TipTap 3 (StarterKit, Image, TableKit) с панелью кнопок на antd:
  начертание, H2/H3, списки, цитата, ссылка, изображение, таблица, отмена/повтор.
  HTML — CodeMirror 6 (`@uiw/react-codemirror`, `@codemirror/lang-html`), разметка как есть.
- Изображения: «Загрузить с диска» (только картинки, `uploadError`) или «Выбрать
  из загруженных» (`FilePickerDrawer`); файл ложится в раздел свойства в «Файлах»
  (сервер заводит его при первой загрузке по номеру свойства), в текст — `<img>`.
- Пакеты: `@tiptap/{react,pm,core,starter-kit,extension-image,extension-table}` 3.32.0,
  `@uiw/react-codemirror` 4.25.12, `@codemirror/lang-html` 6.4.12 — все MIT.

**Ключевые решения**

- **TipTap, а не Quill** (стоит в проекте): Quill пересобирает разметку под свою модель
  и режима «код» у него нет. TinyMCE/CKEditor — GPL, тяжёлые и не в стиле antd.
- **Защита от потерь**: TipTap держит HTML по схеме и чужое выбрасывает. Значение с такой
  разметкой открывается в «HTML»; переход в визуальный — после предупреждения с перечнем
  (`unsupportedMarkup`). Открытие без правок значение не меняет.
- Пустой визуальный документ отдаётся пустой строкой — иначе `<p></p>` считался бы значением.

**Не сделано**

- Вставка картинки перетаскиванием и из буфера — только кнопкой.
- Картинки внутри HTML не попадают в «где используется» у файла и не защищают его от удаления.

**Проверено**

- `tsc --noEmit` — чисто.
- Браузер, «Страницы» → карточка: визуальный режим с панелью, жирный текст → в «HTML»
  виден `<p><strong>…</strong></p>`, запись помечена изменённой; `div class` в «HTML» →
  предупреждение «пропадёт: div» и режим остаётся; загрузка PNG в «Боковую колонку» →
  `<img src="/uploads/…">` в тексте. Карточка закрыта без сохранения, тестовый файл удалён
  (раздел свойства «Боковая колонка» в «Файлах» остался — он и так понадобится).

## 2026-10-25 — привязка к значениям списка, обязательный источник, записи по спискам

**Что сделано**

- **Новый тип «Привязка к значениям списка»** (`list-option-link`): свойство смотрит
  на свойство-«Список» любого доступного списка (`optionsPropertyId` в `params`),
  значение — номер его варианта в `optionId`. Сервер подставляет привязке варианты
  источника при чтении (`withSourceOptions`), поэтому дальше она — обычный «Список»:
  поле карточки, ячейка, фильтр, проверка значения. Источники — `GET
  /api/infoblocks/settings/option-sources`.
- **Источник у привязки к записям обязателен**, «Любая запись панели» убрана.
- **`link-targets` отдаёт записи только запрошенных списков** (`?listKeys=`): поле
  грузит свой список, таблица — списки видимых колонок, проверка ссылок и привязки
  файлов — только нужные. Раньше любой выбор тянул все записи панели.
- В привязку добавлены **товары** (раньше были только категории).
- ID в выборе — в формате «Название #11».

**Ключевые решения**

- Варианты привязки не копируются, а читаются у источника: поменяли варианты
  в «Списке» — выбор в привязке тот же; удалили вариант — значения уходят каскадом
  по внешнему ключу `optionId`.
- «Список», на который смотрит привязка, нельзя удалить или увести с типа «Список»
  (409) — иначе привязка молча осталась бы без вариантов.
- У 30 свойств-привязок, заведённых раньше, источника нет (значений у них не было).
  Их не трогали: в карточке такое поле пустое с подсказкой выбрать список, а сохранить
  свойство без источника нельзя.

**Проверено**

- `jest` — 98 тестов (обязательный источник, варианты чужого свойства), `tsc` — чисто.
- API: `option-sources`, `link-targets` без списков — пусто, с `products` — только товары;
  400 на привязку без источника и на источник не-«Список»; значение-вариант сохраняется,
  чужой номер — 400; удалить «Список»-источник — 409.
- Браузер: в карточке товара привязка показывает «Статическая», категории — «Фаркопы1 #3»,
  у «Марки» без источника — подсказка; в настройках источник — «Тип страницы #223».
- Временное свойство и его строка журнала удалены.

## 2026-10-25 — «Таблица» в карточке, привязка к записям и к типу контента

**Что сделано**

- **«Таблица»** правится в карточке записи: `drawer/TableField.tsx` (сетка antd `Table`,
  поле ввода в ячейке, «Добавить строку», корзина у строки) и `drawer/tableValue.ts`
  (строки по числу столбцов, тело запроса без пустых строк с конца). Сервер таблицу уже
  умел — менять его не пришлось.
- **«Привязка к контенту» стала «Привязкой к записям контента»** (тип тот же,
  `content-link`, значения не трогали). В выбор и в источники добавлены элементы каждого
  типа контента: источник «Контент: Новости» — список `content-items.8`.
- **Новый тип «Привязка к типу контента»** (`content-type-link`): значение — та же
  ссылка `{ listKey: 'contents', recordId }`, хранится в `json`, проверяется на
  существование тем же `LinkTargetsService`. Источник не задают — он всегда `contents`.
- `link-targets` отдаёт ещё элементы контента (группа «Контент: <тип>») и типы
  («Типы контента»); `link-sources` — каждый тип контента отдельным источником.

**Ключевые решения**

- **Тип-привязка — та же ссылка, а не номер типа.** Так он целиком переиспользует

- **Типы контента не попадают в «любую запись панели»** у привязки к записям: тип —

  не предлагает.
- Удаление типа контента или элемента, на которые ссылается привязка, не блокируется —

- **Набор уходит с задержкой 400 мс** — поля отмечают по нескольку подряд, а пишется

- **Выбранное держит и хук, а не только адрес.** `router.replace` применяется

- **Вид поля — из колонки, а не из адреса**: адрес правят руками, непонятное значение

**Не сделано** — набор полей, поменянный другим пользователем, приходит при следующей

**Ключевые решения**

- **Вид свой у каждого пользователя, и у общих списков тоже** (`userId` — кто смотрит).
  Колонки — вкус, а не устройство списка: спрятанная колонка не должна пропадать
  у соседа. Поэтому без `ListEditGuard`: не-`root` настраивает таблицу «Пользователей»,
  которую сам только смотрит.
- **Хранятся только видимые колонки**, порядок — `position`. «По умолчанию» = строк нет,
  сброс их стирает, а не пишет копию колонок раздела: новая колонка раздела тогда
  появится сама у всех, кто таблицу не настраивал. Отклонено: хранить и спрятанные
  с флагом — правило «что делать с колонкой, которой нет в сохранённом» всё равно нужно,
  а строк вдвое больше.
- **Вид пишется целиком (`PUT`)**, а не по колонке: порядок — свойство всего набора.
  Правило «одна сущность — один запрос» здесь не нарушено: вид таблицы одного
  пользователя и есть одна сущность, соседей он не переписывает.
- **Ключ свойства — `property-<номер>`**, как у поля в карточке: код у свойства правят.
  Сервер проверяет только вид ключа — какие поля есть у записей раздела, знает фронт.
  Колонку, которой больше нет, таблица пропускает; не осталось ни одной — показывает
  колонки раздела.
- **Пока вид не пришёл, таблица в загрузке** — иначе колонки по умолчанию мелькали бы
  и сменялись сохранёнными. Не пришёл из-за ошибки — колонки по умолчанию, не вечный спиннер.
- **Кнопка — в заголовке столбца действий**, а не в шапке рядом с «Настройками»: шапку
  разделы прячут (`isListSettingsHidden`, «Файлы»), а таблицу настраивать можно везде.
- **Логика рядом с компонентами** (`table/columns/useColumns.ts`, `columnView.ts`), как

## 2026-10-06 — вкладки карточки и мета записи вместо свойства «мета»

**Что сделано**

- У списка появились **вкладки карточки записи**: в настройках заводится список вкладок
  (название + код), у каждого свойства — выбор вкладки. Свойства без вкладки остаются на
  общей «Свойства», она идёт первой; дальше вкладки в порядке из настроек.
- Тип свойства **«мета» убран**. Вместо него — галочка списка **«Мета записи»**: включена —
  в карточке каждой записи появляется вкладка «Мета» с H1, Title и Description.
- В `list_settings` добавлены `tabs` (JSONB) и `useRecordMeta` (boolean); у свойства — `tab`.

**Ключевые решения**

- **Мета записи лежит среди значений свойств**, под служебным ключом `_meta`. Отдельной
  таблицы нет — её только что убрали у страниц, заводить снова незачем. Коллизии
  невозможны: коды свойств начинаются с буквы, `_meta` пользователю недоступен.
- **Выключенная галочка стирает значения меты** — так же, как удалённое свойство. Иначе
  в базе копились бы невидимые данные, которые однажды «вернутся» при повторном включении.
- **Удаление вкладки не теряет свойства**: они возвращаются на общую «Свойства».
  Альтернатива (запрещать удаление непустой вкладки) раздражала бы на ровном месте.
- **Код сохранённой вкладки закрыт** — на него ссылаются свойства, как код свойства
  закрыт из-за значений.
- **Пустая вкладка не показывается** в карточке: завели вкладку, но не положили на неё
  свойства — пользователю видеть нечего.

**Интерфейс вкладок** — вкладки настраиваются вкладками: в окне настроек свойства
разложены по тем же вкладкам, что потом в карточке, переключение показывает свойства
только своей, «+» на панели открывает попап, где вводится **только название**. Решения по дороге:

- **кода вкладки пользователь не видит.** Сначала его просили вводить в попапе — это была
  ошибка: вкладка существует только в карточке записи, сайт о ней ничего не знает и читает
  значения по кодам свойств. Код генерируется транслитерацией названия («Характеристики» →
  `harakteristiki`) и остаётся внутренним ключом: по нему свойство привязано к вкладке
  и переживает переименование;

- **внутри окна свойство ссылается на вкладку по `uid`, а не по коду**: код незасохранённой
  вкладки ещё правят, и свойства от неё бы оторвались. В код это переводится при сохранении;
- **«выше/ниже» двигают свойство в пределах его вкладки** — в окне видны только её свойства,
  и меняться местами должно с тем, что видно выше, а не с соседом из другой вкладки;
- **новое свойство заводится на открытой вкладке** — там его и ждут увидеть;
- **Enter в попапе заводил сразу две вкладки.** На подтверждение было навешано два
  обработчика — `onPressEnter` у поля и `onFinish` у формы, — и в очередь попадали два
  `setTabs` подряд. Оставлен один обработчик; заодно новая вкладка готовится **до**
  `setTabs`, а не внутри его апдейтера: обновление состояния должно быть чистым.

**Параметры свойства вынесены в отдельное окно** (`PropertyConfigDialog`) — колонки
«Параметры» в таблице больше нет. Строка с вариантами списка, форматами, весом,
разрешением и размером таблицы разъезжалась и перетягивала таблицу в горизонтальную
прокрутку, при том что настраивают это редко и по одному свойству за раз. Открывается
шестерёнкой в строке; у типов без параметров (строка, число, текст, HTML, блоки,
привязка) кнопка не нажимается — так видно, что параметров нет, а не что их спрятали.
Своего «Сохранить» у окна нет: правки ложатся в тот же черновик свойства.
Колонка «Несколько» переименована в «Множественное».

**Свойства: множественность, варианты с кодом, свободная таблица, источник привязки**
(заход 2026-10-07). Решения по дороге:

- **Множественность — у всех типов, кроме таблицы.** У строки, числа, текста и разметки
  появился общий список значений («Добавить значение» / «Убрать»), у выбора её по-прежнему
  рисует сам Select. Таблицу оставили одиночной намеренно: строки у неё теперь и так
  добавляются сколько угодно, а вторая таблица в значении (`string[][][]`) от лишних строк
  первой (`string[][]`) неотличима — разбор значения стал бы гаданием.
- **Вариант списка — код плюс название.** В значении записи хранится код: он уходит на сайт
  и переживает переименование варианта. Старые настройки (вариант — просто строка) читаются
  как `{ code: строка, name: строка }`, а **не** транслитерацией: значения записей уже
  сохранены по этой строке, и перевод кода в латиницу молча оторвал бы их от вариантов.
  Поэтому формат кода варианта не ограничен — у старых списков он кириллический.
- **У таблицы задаются только столбцы и заголовки.** Строк в настройках больше нет: их
  добавляет карточка записи. Пустые строки с конца не хранятся, потолок — 50 строк
  (столько же, сколько разрешала прежняя настройка).
- **Привязка к контенту знает свой список.** В параметрах свойства выбирается
  список-источник (`linkList`), в карточке — запись из него. Под это добавлен
  `GET /api/list-settings/link-sources`: инфоблок должен быть в выборе, даже когда записей
  в нём ещё нет, а `link-targets` строится из записей и пустой инфоблок бы не показал.
- **Колонка «Вкладка» убрана в меню строки** («Сменить привязку») — туда же, где
  «Параметры свойства». Две колонки занимали место у каждой строки, а трогают их редко.
- **Порядок свойств — колонка «Сортировка», а не стрелки «выше / ниже».** Числом свойство
  сразу встаёт куда нужно, стрелками его пришлось бы перещёлкивать по шагу. Номера идут
  с шагом 10 (между соседями есть куда вписать новое) и живут только в окне: на сервер
  порядок уходит порядком массива, поэтому перед отправкой свойства сортируются.

**Символьный код записей — настройка списка.** Три флага (`useCode`, `codeRequired`,
`codeUnique`) в интерфейсе одним выпадающим списком: по отдельности они бессмысленны
(уникальность без обязательности нечего проверять), а тремя галочками занимали пол-окна.
Правила применяет сам редактор (`logic/contentEditor/codePolicy.ts`), а не каждый раздел:
поля `name` и `code` есть у записи любого раздела. **Код собирается из названия везде** —
общая транслитерация `logic/slug.ts`, одна на записи, вкладки карточки и варианты списка.
У сохранённой записи код подставляется, только если его ещё нет: менять код сохранённой
записи нельзя, по нему её открывает сайт.

**Ключевые решения**

- **Значения — в отдельной таблице, а не в таблицах разделов.** Иначе пришлось бы
  менять модели, DTO, сервисы и снимки истории десяти списков — и свойства всё равно
  были бы привязаны к разделу. Отдельная `property_values` даёт свойства любому списку,
  включая будущие, а редактор контента подмешивает их сам. Цена — второй запрос при
  сохранении и уборка при удалении (см. «Не сделано»). Поле `props` у `infoblock_elements`
  оставлено как было.
- **Список — строковый ключ** (`infoblock-elements.3`), запись — её ключ в админке и в
  журнале (`element-7`). Так настройки у каждого инфоблока свои, а ссылки журнала и
  значения совпадают без перевода. Перечень видов закрытый на сервере — писать в
  «произвольный» список нельзя, а вид знает, в чей журнал писать правки.
- **Правки свойств — в журнал раздела записи**, с ключами `props.<код>` и `tree.parentId`:
  история записи одна, и «Цена» видна рядом с «Названием». Код и название записи для
  такой строки берутся из её последней строки в журнале, а не из тела запроса.
- **Код свойства после сохранения закрыт.** Значения хранятся по коду; переименование
  означало бы перенос значений у всех записей. Удаление свойства или смена типа стирает
  значения сразу — иначе свойство, заведённое заново с тем же кодом, «воскресило» бы их.
- **Пока настройки не загрузились, строк нет.** Запись, открытая по адресу, иначе
  прочиталась бы без свойств, и «Сохранить» стёрло бы их значения.
- **Свойства не прошли — запись всё равно сохранена.** Новая запись открывается в любом
  случае: повторное «Сохранить» не должно создать её дважды. Форма остаётся изменённой.
- **«Древовидная структура» — настройка списка, а не тип свойства.** Родитель лежит
  в `property_values.parentId`: деревом становится любой плоский список без правки его
  таблицы. Удаление записи не уносит вложенные (их удалял бы чужой раздел) — сервер
  поднимает их к её родителю. У «Страниц» и «Веб-форм» вложенность своя — переключатель
  у них закрыт.
- **Привязка к контенту — из одного списка «целей» на сервере** (`link-targets`): страницы,
  записи всех инфоблоков, HTML-блоки, формы. Один запрос вместо загрузки всех разделов
  во фронт, и тот же список проверяет привязку при сохранении.
- **Файл и изображение — один механизм с разными ограничениями.** Формат и вес видны по
  карточке медиатеки и проверяются на сервере; разрешение — только в браузере, загрузив
  картинку (в карточке его нет, а читать файл из хранилища ради проверки — дорого).
- **Quill — общее поле формы `richtext`**, а не компонент свойства: его можно поставить
  и на поля контента страниц и записей. Подгружается только в браузере и сам владеет
  своей частью DOM — иначе SSR падает, а повторное монтирование дублирует панель.
- **Медиатека для выбора — свой срез стора**, а не `files`: там лежат файлы одного
  открытого раздела, и выбор файла из шторки не должен их подменять. Перечитывается при
  каждом открытии окна выбора.
