# Веб-формы

## 2026-10-13 — формы и поля общие на сайт, у поля только стандартное плюс «Плейсхолдер»

**Что сделано**

- Формы и поля потеряли `userId`: из моделей, сервисов, контроллеров и выборки
  `link-targets`. Колонки `userId` и индексы с ним ушли при старте сервера сами
  (`sync({ alter: true })`), уникальные индексы теперь на один `code` —
  `infoblock_forms_code`, `infoblock_forms_fields_code`.
- Оба вида списка стали общими (`isShared` в `infoblock-kinds.ts`): настройки и свойства
  одни на сайт. Настройки списка `forms` главного администратора (со свойствами
  «Документы», «Связанная страница» и т. д.) сервер при старте сделал общими сам
  (`SystemPropertiesService.ensureShared`); строку настроек второго пользователя,
  заведённую вчерашней проверкой, удалил руками.
- У поля осталось только стандартное — код, название, активность; тип, подсказка,
  варианты и обязательность удалены из модели, DTO и экрана. Экран полей больше
  не описывает ни поля карточки, ни колонки — редактор ставит стандартные.
- Плейсхолдер — системное свойство списка `form-fields` (`placeholder`, строка)
  в `system-properties.ts`; его заводит и сверяет `SystemPropertiesService`.
- Код поля проверяется тем же правилом, что код формы (строчные буквы, цифры, дефис).
- Фронтенд: удалён `logic/forms/fieldLabels.ts`, перегенерирован клиент (удалены
  устаревшие `FormFieldType`-файлы, которые генератор сам не стирает).

**Ключевые решения**

- **Без владельца**, потому что формы — контент одного сайта: с `userId` второй админ
  не видел форм первого, а свойства списка у каждого были свои. Журнал по-прежнему
  пишется под автором правки, как у ролей и учётных записей.
- **Поле — стандартная запись**: что у поля есть кроме кода, названия и активности,
  решают свойствами списка, а не колонками таблицы. Плейсхолдер — системным свойством,
  чтобы он был у списка всегда и его нельзя было удалить.
- Код поля с подчёркиванием (`user_phone`) больше не принимается — правило кода одно
  на оба списка.

**Не сделано**

- Страницы, HTML-блоки и товары по-прежнему с `userId` — их не трогал, правило
  мультитенантности в `CLAUDE.md` остаётся как было.
- Перенос старых `forms`/`form_fields` — по-прежнему отдельным шагом.

**Проверено**

- `npx tsc --noEmit` в `backend/` и `frontend/` — без ошибок; `jest src/infoblocks/settings` — 51/51.
- База после перезапуска: у `infoblock_forms` и `infoblock_forms_fields` нет `userId`,
  индексы `UNIQUE (code)`; настройки `forms` — владелец `0`, со всеми прежними свойствами;
  у `form-fields` общие настройки с системным «Плейсхолдером».
- API под двумя пользователями (root и обычный): поле root видит второй, форму второго —
  root; тот же код формы у другого пользователя — 409; лишнее поле `type` в теле — 400;
  код с подчёркиванием — 400; свойства списка у обоих одинаковые; плейсхолдер, записанный
  root, читает второй; второй подключает поле root к своей форме — поле блокируется,
  удаление 409; системное свойство не удаляется (409); после удаления формы поле удаляется.
  Тестовые записи удалены.
- Интерфейс в этот раз не проверялся: сессия браузера вышла из панели, а пароль вводить
  нельзя.

## 2026-10-12 — «Формы обратной связи» на новом редакторе: формы и поля — два списка, связь системным свойством

**Что сделано**

- Меню: пункт «Обратная связь» с подменю «Формы» (`/admin/forms`) и «Поля форм»
  (`/admin/forms/fields`), между «HTML-блоками» и «Файлами».
- Бэкенд, формы: модуль `infoblocks/forms/` — таблица `infoblock_forms` (код, название,
  активность), `/api/infoblocks/forms` (`GET`/`POST`/`PATCH`/`DELETE`), журнал `forms`.
  Удаление формы стирает значения её свойств (`values.remove`), выбранная в чьей-то
  привязке форма приходит с `isBlocked` и не удаляется (409).
- Бэкенд, поля: модуль `infoblocks/forms/fields/` — таблица `infoblock_forms_fields`
  (код, подпись, тип `FormFieldType`, подсказка, варианты, обязательность, активность),
  `/api/infoblocks/forms/fields`, журнал `form-fields`. Подключённое поле — `isBlocked`, 409.
- Связь: системное свойство «Поля» у списка `forms` (код `fields`, привязка к контенту,
  множественная, `linkList: 'form-fields'`) — `system-properties.ts`. Формы и поля
  добавлены в `link-targets`/`link-sources` и в реестр видов (`infoblock-kinds.ts`).
- Фронтенд: `components/forms/` (`FormsScreen`, `FieldsScreen`), `logic/forms/` (Api
  обоих списков, типы поля и подписи для таблицы), `api/forms.ts`, `api/formFields.ts`,
  страницы `pages/admin/forms/{index,fields}.tsx`, ключ `ListKey.formFields`.
- Тесты: `settings.spec.ts` — виды `forms`/`form-fields` и системное свойство «Поля».

**Ключевые решения**

- **Поле — самостоятельная запись, а не часть формы.** Так заказано: «у каждой формы
  будет множественная привязка к полям через стандартный механизм привязки свойств».
  Одно поле («Телефон») подключают к любому числу форм; связь — значения системного
  свойства, отдельной таблицы связей нет, как у роли пользователя и категорий товара.
  Порядок полей в форме — порядок значений свойства (`infoblock_values.sort`).
- **Код поля уникален у пользователя, а не в форме.** Поле подключают к разным формам;
  уникальность только внутри формы пришлось бы проверять в общем модуле значений
  веткой «если это список форм» — а это запрещено правилами простоты. Нужен вариант
  того же вопроса с другими правилами — заводят второе поле со своим кодом.
- **Тип, варианты и обязательность — колонки поля, а не свойства списка.** Без них поле
  на сайте не нарисовать, и проверять их (варианты у «Списка») должен сервер.
  У формы своего — только код, название, активность: остальное, как у товаров, —
  свойства списка.
- **Новые таблицы, а не `forms`/`form_fields`.** В старых лежат 8 форм и 49 полей прежней
  схемы. Модель с той же таблицей при `sync({ alter: true })` снесла бы колонки `formId`,
  `position`, `notifyEmail` и т. д. Старые данные не тронуты.
- **Код списка, вложенность, мета и символьный код закрыты разделом** (`blockedSettings`):
  оба списка плоские, без меты, код «Обязательный и уникальный» — на коде держатся
  уникальные индексы, пустой код их бы ломал.
- **Подпись в меню — «Обратная связь»**: «Формы обратной связи» не помещается в меню
  шириной 232px (обрезается на 17px), так же сокращены «HTML-блоки».
- Свойства, заведённые у списка `forms` ещё старым редактором (документы, связанная
  страница, срок ответа, «Кто обрабатывает», метка в CRM), подхватились карточкой сами:
  ключ списка тот же.

**Отступления от задания**

Задания в `planned/` не было — раздел заказан фразой в чате. Допущения: состав поля
(подпись, тип из шести, подсказка, варианты, обязательность, активность) взят из прежней
схемы раздела; получатель заявок и текст после отправки оставлены свойствами списка.

**Не сделано**

- **Перенос данных из старых `forms`/`form_fields`** в новые таблицы — нужен отдельный
  шаг с решением, как склеивать одинаковые поля разных форм (коды `name`, `phone`
  повторяются, а в новой схеме код поля уникален).
- **Перетаскивание полей внутри формы**: порядок меняется перевыбором в поле привязки.
- **Условное поле «Варианты»** (только у «Списка»): условных полей новый редактор не
  умеет, поле видно всегда с пояснением, сервер стирает варианты у других типов.
- **Приём заявок** с сайта — как и раньше, вне раздела.

**Проверено**

- `npx tsc --noEmit` в `backend/` и `frontend/` — без ошибок; `jest src/infoblocks/settings` — 50/50.
- API (curl, локальный стек): создание формы и полей; 400 на «Список» без вариантов,
  на неверный код поля и на форму без кода; 409 на повтор кода формы и поля; варианты
  чистятся от пробелов и повторов; смена типа `select → text` стирает варианты, обратно
  без вариантов — 400; привязка полей к форме через `/values` сохраняет порядок;
  привязка к несуществующему полю — 400; подключённые поля приходят с `isBlocked`,
  удаление — 409; удаление формы стирает привязки и снимает блокировку; журнал поля
  с автором из JWT; `link-targets`/`link-sources` отдают формы и поля; изоляция —
  чужие формы и поля не видны, правка и удаление — 404, тот же код у другого
  пользователя разрешён; без токена 401.
- Интерфейс (браузер, `http://localhost:3400`): пункт меню с подменю и подсветкой,
  таблица форм, карточка формы со свойством «Поля» (поля в заданном порядке) и прежними
  свойствами списка, таблица полей с типом словами и замком у подключённых, заведение
  поля через карточку (обязательные «Подпись», «Код», «Тип»).
- Тестовые записи удалены: `infoblock_forms` и `infoblock_forms_fields` пусты, старые
  `forms` (8) и `form_fields` (49) на месте.

## 2026-09-16 — раздел «Веб-формы»: формы обратной связи и их поля

**Что сделано**

- Бэкенд: модуль `backend/src/forms/` — таблицы `forms` и `form_fields`, контроллер
  `FormsController` (CRUD формы, CRUD поля внутри формы, журнал изменений раздела и история
  одной записи), сервис со всей логикой, DTO в `dto/`. Модели и модуль зарегистрированы
  в `app.module.ts`.
- Фронтенд: раздел `/admin/forms` на универсальном редакторе контента —
  `logic/forms/` (дерево, описание полей, значения ↔ запрос, контроллер редактора),
  `components/forms/FormsScreen.tsx`, страница `pages/admin/forms.tsx`,
  сеть `api/forms.ts`, стор `redux/reducers/formsReducer.ts` + thunks.
- Пункт «Веб-формы» в левом меню (`config/navigation.ts`), между «Контентом» и «Почтой».
- Документация: [`docs/forms.md`](../docs/forms.md), сущности в `backend/src/DOMAIN.md`.

**Ключевые решения**

- **Поля формы — отдельная таблица, а не массив в форме.** У поля есть свой порядок, код,
  активность и история изменений, и правят их по одному. Массивом остались только варианты
  списка (`options`): у варианта нет собственных полей и живёт он только вместе с полем.
- **Один экран на обе сущности.** Форма и поле показаны одной таблицей: поле — вложенная
  строка. Отдельный экран «поля формы» означал бы второй список ради сущности, которая без
  родителя не существует. Редактор контента такую вложенность уже умеет — раздел отдаёт ему
  контроллер и своего экрана не пишет.
- **Ключ записи с приставкой (`form-1`, `field-3`).** Две таблицы в одном списке и в одном
  журнале дали бы одинаковые номера у разных записей. Приставка решает это разом для строки
  таблицы, адреса страницы и `entityId` в `change_history` — история строки запрашивается её
  же идентификатором. Строковый ключ журнала под это и был рассчитан изначально.
- **Поле не переносится в другую форму.** Перенос сломал бы уже собранные заявки (ключи
  значений принадлежат форме), а пользы в нём нет: поле создают там, где оно нужно.
  В шторке форма показана, но не редактируется.
- **Варианты списка — обязательны у типа «Список» и очищаются при смене типа.** Список без
  вариантов на сайте не нарисовать; оставшиеся от прежнего типа варианты всплыли бы при
  возврате к списку. Проверка в сервисе, а в форме поле «Варианты списка» просто не
  показывается у других типов (скрытые поля редактор не проверяет).
- **Получатель заявок необязателен**, но проверяется по формату — как домен в «Настройках»:
  пустое значение разрешено отдельной веткой в регулярном выражении, а не отключением проверки.

**Попутный рефакторинг (без изменения поведения)**

`usePageRoute` и перевод журнала (`pagesHistory.ts`) лежали в `logic/pages/`, хотя оба ничего
о страницах не знают. Перенесены в `logic/contentEditor/` (`useRecordRoute.ts`, `historyDto.ts`)
и используются обоими разделами; раздел «Страницы» переключён на них, копий не осталось.

**Отступления от задания**

Задания в `planned/` не было — раздел заказан одной фразой: «веб-формы, там должна быть
возможность добавлять формы обратной связи». Принятые допущения:

- состав формы = поля + настройки отправки (получатель, подпись кнопки, сообщение после
  отправки). Это минимум, без которого форма обратной связи не собирается;
- типы полей: строка, e-mail, телефон, текст, список, флажок — то, из чего состоят обычные
  формы обратной связи; вложений и капчи нет;
- приём заявок с сайта в раздел не входит (см. ниже).

**Не сделано**

- **Приём заявок**: публичного эндпоинта отправки, таблицы заявок и отправки писем нет.
  Панель пока описывает формы, а сайта, который бы их показывал, в репозитории нет;
  `notifyEmail` и `successMessage` — заготовки под эту часть.
- **Перетаскивание полей мышью**: порядок меняется числом в поле «Порядок», как и в других
  разделах панели.
- **Условная логика полей** (показать поле в зависимости от другого) — за рамками.

**Проверено**

- `npx tsc --noEmit` в `backend/` и `frontend/` — без ошибок.
- API (curl, локальный стек, токен тестовый): создание формы и полей; нормализация почты
  (`  Sales@Example.COM ` → `sales@example.com`); `409` на повтор кода формы и кода поля;
  `400` на неверную почту и на «Список» без вариантов; смена типа `select → text` очищает
  варианты; история записи и журнал раздела с автором из JWT; удаление поля и удаление формы
  вместе с полями; изоляция по пользователю — чужая форма даёт `404` на чтение, правку и
  удаление, одинаковый код у разных пользователей разрешён; без токена `401`.
- Интерфейс (браузер, `http://localhost:3400/admin/forms`): пункт меню, создание формы через
  шторку, проверка почты не даёт сохранить, добавление поля кнопкой «внутрь», появление
  «Вариантов списка» при типе «Список», дерево «форма → поле» в таблице, вкладка «История» и
  «Журнал изменений» с русскими подписями полей, удаление формы с подтверждением.
- Тестовые данные удалены, таблицы `forms` и `form_fields` пусты, записи журнала по
  разделу убраны.
