## 2026-10-12 — «Пользователи» и «Роли» на новом редакторе, роль — системным свойством

**Что сделано**

- Меню: пункт «Пользователи» с подменю «Пользователи» (`/admin/users`) и «Роли»
  (`/admin/users/roles`). Подменю-группа без своей страницы — `children` у раздела
  в `config/navigation.ts`, `isGroup` у пункта (`logic/navigation`, `Sidebar`).
- Бэкенд, роли: модуль `infoblocks/roles/` — таблица `infoblock_roles`,
  `/api/infoblocks/roles` (`GET`/`POST`/`PATCH`/`DELETE`), журнал `roles`; правит только
  `root`; назначенная роль приходит с `isBlocked` и не удаляется (409). Роли — источник
  и цель «Привязки к контенту» (`LinkTargetsService`).
- Бэкенд, системные свойства: колонка `isBlocked` у `infoblock_settings_properties`,
  перечень `infoblocks/settings/properties/system-properties.ts` (сейчас одно: «Роль»
  у `users` — привязка к списку `roles`) и сверка с ним `SystemPropertiesService` при
  старте сервера и при появлении настроек нового списка. `PATCH`/`DELETE` системного
  свойства — 409.
- Бэкенд, списки: виды `users` и `roles` — общие (`isShared`: настройки одни на сайт,
  владелец `0`) и только для `root` (`isRootOnly` + `ListEditGuard` на контроллерах
  настроек, вкладок, свойств и значений). `ensureSettingsId` — через `findOrCreate`.
- Фронт, общий слой редактора: `update` и `remove` у `EditorListApi` необязательны
  (без них карточка на просмотр, нет корзины и «Удалить»); поле `FieldType.Link` —
  «Привязка к контенту» стала правиться (`drawer/LinkField.tsx`, `logic/contentLinks/`);
  системное свойство в окне настроек — замок и шторка на просмотр.
- Фронт, раздел: `api/users.ts`, `api/roles.ts`, `logic/users/` (Api на правку и на
  просмотр, `useUsersAccess`), `logic/auth/useIsRoot.ts`, `components/users/`
  (`UsersScreen`, `RolesScreen`), страницы `pages/admin/users/{index,roles}.tsx`.

**Ключевые решения**

- **Роль — значение свойства, а не колонка `roleId`** (задание: «стандартный механизм
  привязки по свойству»). Связь живёт в `infoblock_values`, как любая привязка; поэтому
  «назначена ли роль» ищется по самим значениям, а не по свойству «Роль».
- **Одна роль на пользователя** (`multiple: false`). Задание этого не уточняло; права
  проще складывать из одной роли. Нужны несколько — одна строка в перечне системных
  свойств: при следующем старте сверка переключит множественность у всех.
- **Перечень системных свойств — по виду списка**, а не по ключу: у вложенного вида
  (`infoblock-elements`) свойство получат все его списки — это и есть «добавлять
  стандартные свойства в других инфоблоках».
- **Сверка при старте, а не отдельная команда** — как и схема базы (`sync: alter`):
  поправили перечень — перезапуск привёл базу к нему. Чужое свойство с тем же кодом
  и типом становится системным вместе со значениями; другого типа — не трогается.
- **`isBlocked` — «нельзя ни менять, ни удалять» целиком**, включая вкладку и сортировку:
  правило одно и без исключений. Значения свойства у записей правятся как обычно.
- **Общие настройки у `users`/`roles`.** Настройки списков были у каждого пользователя
  свои, а учётные записи и роли — общие: роль одного человека у каждого смотрящего была
  бы своей. Владелец `0`, а не `null` — на `(userId, listKey)` уникальный индекс.
  Прежние настройки списка `users` (у `root` были заведены 6 свойств) сверка забрала
  в общие целиком.
- **Право на правку — гардом, а не в сервисах**: правило одно на четыре контроллера,
  роль есть только в JWT. Без него любой пользователь назначил бы себе роль, поправив
  значение свойства.
- **Только просмотр для не-`root` — через Api, а не флаг `readOnly`**: Api на просмотр
  содержит один `list`, и редактор сам убирает то, чего Api не умеет. Так же «Файлы»
  убрали «Добавить» (необязательный `create`).
- **Ключ поля свойства в карточке — `property-<номер>`.** С голым номером объект ставил
  поля по возрастанию номеров, а не по сортировке, и «Роль» (сортировка 0, но свежий
  номер) уезжала в самый низ. Стор и API по-прежнему по номерам — переводят на краях
  (`fieldValuesOf` / `propertyValuesOf`).

**Не сделано**

- Права по ролям: роль пока только назначается — что она разрешает, не проверяется.
- Колонки «Роль» в таблице пользователей нет: таблица показывает поля записи, а не
  значения свойств; нужна колонка-свойство в общем слое.
- Значения свойств удалённой роли (если у ролей заведут свои свойства) не стираются —
  как и у остальных разделов нового редактора.

**Проверено**

- Бэкенд: `tsc` чистый, jest 54/54 (новые тесты: общий владелец настроек, вид списка,
  годность перечня системных свойств).
- API вручную (`curl` с dev-токенами `root` и обычного пользователя): роль — 403 для
  не-`root`, 201/409 на повтор кода; `PATCH`/`DELETE` системного свойства — 409;
  назначение роли через значения — 200, у не-`root` — 403; назначенную роль удалить — 409,
  свободную — 204; журнал `/api/history/roles` пишется.
- Браузер (`localhost:3400`): подменю и подсветка; карточка пользователя — «Роль» первой
  среди свойств, смена роли сохраняется (в журнал — «было/стало» по `props.role`);
  «Роли» — замок у назначенной, создание роли из карточки; «Настройки» — системное
  свойство с замком, шторка на просмотр; под обычным пользователем — без шапки,
  без корзин, карточка закрыта.

## 2026-09-16 — раздел `/admin/users` на редакторе контента

**Что сделано**

- Бэкенд: `UsersController` (`GET /api/users`, `GET /api/users/{id}`, `POST /api/users`,
  `PATCH /api/users/{id}`, `GET /api/users/{id}/history`, `GET /api/users/history`),
  управление учётными записями в `UsersService`, DTO `CreateUserDto` / `UpdateUserDto`,
  поле `users.passwordChangedAt`, `createdAt` и `passwordChangedAt` в `UserDto`.
- Фронт: `api/users.ts`, `redux/{reducers/usersReducer,action-creaters/users}.ts`,
  `logic/users/` (контроллер редактора, описание полей, действия, загрузка),
  `components/users/UsersScreen.tsx`, страница `pages/admin/users.tsx`.
- Общие слои: тип поля `password` в `logic/editorForm/` + разметка в `components/editorForm/`;
  флаг `readOnly` в контракте редактора контента (`logic/contentEditor/types.ts`),
  он убирает кнопки «добавить» и «сохранить».
- Документация: `docs/users.md`, раздел `users` в `DOMAIN.md`.

**Ключевые решения**

- **Кто правит.** Список видят все авторизованные, правит только `root` (решение заказчика).
  Проверка роли — в сервисе, роль берётся из JWT: так же, как `userId` в остальных разделах,
  и по тем же соображениям. У остальных раздел открывается на просмотр — отсюда `readOnly`
  в редакторе контента; отдельного экрана «только для чтения» не появилось.
- **Журнал — вместе с правами на правку.** Нет права править — нет ни вкладки «История»,
  ни переключателя «Журнал изменений»: контроллер просто не отдаёт `loadRecordHistory`
  и `loadJournal`, а бэкенд отвечает на них 403.
- **Пароль в форме, а не отдельной кнопкой** (решение заказчика). У существующей записи
  пустое поле = «не менять»; заполненное = заменить. Пустая строка на бэкенд не уходит
  вовсе — иначе валидация отвергла бы её как слишком короткий пароль.
- **`passwordChangedAt` — новое поле в таблице.** Пароль хранится хэшем, «было/стало»
  сравнивать нечего, а факт смены в журнале виден быть обязан. Альтернатива — писать
  в снимок кусок хэша — отклонена: журнал не место для материала пароля.
- **Роли нет в теле запроса.** Ни в `CreateUserDto`, ни в `UpdateUserDto`. Инвариант
  «root ровно один» держится индексом `users_single_root`, но давать API повод его нарушить
  незачем: через раздел заводятся только обычные пользователи.
- **`HistoryService` перестал зависеть от `UsersModule`.** Ему нужно от него ровно одно —
  имя автора, — а раздел «Пользователи» сам пишет в журнал, и взаимный импорт модулей
  Nest не собрал бы. Теперь `HistoryService` инжектит модель `Users` напрямую.
  Альтернатива `forwardRef` отклонена: цикл остался бы, просто перестал бы падать.
- **Учётные записи — без `userId`.** Единственная сущность панели, где изоляции по тенанту
  нет: они тенант и определяют. Её место занимает проверка роли — записано в `DOMAIN.md`,
  чтобы не выглядело как забытый фильтр.

**Отступления от задания**

Задания в `planned/` не было — раздел реализован по устной постановке
(«страница пользователей на том же ContentEditor»). Модель доступа и способ смены пароля
выбраны заказчиком отдельным вопросом.

**Не сделано**

- **Удаления учётной записи нет** — ни в API, ни в интерфейсе. Запись владеет своими
  данными (страницы, мета, настройки, авторство в журнале), а `userId` в этих таблицах —
  колонка с индексом, без внешнего ключа: удаление строки молча оставило бы сиротами всё
  остальное. Доступ забирают выключателем `isActive`. Чтобы сделать настоящее удаление,
  нужно сначала решить, что происходит с данными тенанта, — и это решение придётся
  повторять для каждой новой сущности (инфоблоки, формы, файлы), поэтому каскад «сноса
  тенанта» должен жить не в `UsersService`.
- Обычный пользователь не может поменять себе имя или пароль: раздел правит только `root`,
  а личного профиля в панели пока нет.
- Роль существующей записи не меняется ничем, кроме прямой правки в БД.

**Проверено**

Вручную, на локальном стенде (`http://localhost:3400/admin/users`), под `root`:

- список рисуется, колонки и подсказка у главного администратора на месте;
- шторка существующей записи: поле пароля пустое, «Доступ в панель» у `root` заблокирован
  (`ant-switch-disabled`), роль только для чтения;
- проверки формы: пустой email → «Поле «Email» обязательно»; пароль `123` →
  «Минимальная длина пароля — 6 символов»;
- создание записи: появилась в таблице и в БД, `passwordChangedAt` проставлен;
- вкладка «История»: «Создание» с полями email/имя/роль/доступ/пароль изменён и
  «Изменение» с одним полем «Пароль изменён» — в БД у записей журнала автор и IP из запроса,
  пароля нет;
- повторное открытие записи по прямому адресу (`?id=4`): поле пароля пустое, «Сохранить»
  заблокировано — молча переписать пароль открытием формы нельзя;
- `npx tsc --noEmit` чистый и на бэкенде, и на фронте; Swagger отдаёт все шесть маршрутов.

Тестовая учётная запись и её записи журнала после проверки удалены из локальной БД.

**Не проверено вживую:** режим «только просмотр» у обычного пользователя. Чтобы его
пройти, нужно войти под не-`root` учётной записью, то есть ввести пароль в форму входа, —
этого я не делаю. Логика проверена по коду: `readOnly` убирает кнопки, поля гасятся
`disabled`, `loadRecordHistory`/`loadJournal` не отдаются, бэкенд отвечает 403.

## Удаление учётных записей и метка главного администратора — 2026-10-28

**Что сделано.** `DELETE /api/users/{id}` (только `root`, 204): удаляет любую запись, кроме
главного администратора (409 «Главного администратора удалить нельзя»). Вместе с ней
стираются значения её свойств (роль) и её вид таблиц; удаление пишется в журнал раздела.
`UserDto` отдаёт `isBlocked` (= `isRoot`) — у главного администратора в таблице замок вместо
корзины. Во фронте у Api раздела появился `remove`, а у email главного администратора —
золотая метка «Главный администратор»: в редакторе колонка получила `badge`
(`{ key, name, color }` — метка `Tag` при включённом логическом поле записи).

**Решения.** Метка — у email, а не только в колонке «Администратор»: колонку прячут в виде
таблицы, и у текущего вида она была спрятана. Данные тенанта (страницы, товары и т. д.
с `userId` удалённого) удаление не трогает: сейчас все они у `root`, у обычных пользователей
своих записей нет. Каскад «сноса тенанта», о котором говорилось выше, остаётся задачей
на будущее, если у обычных пользователей появятся свои данные.

**Проверено** на локальном стенде под `root`: в таблице у всех корзина, у `root` — замок
и метка; `DELETE /api/users/3` (root) → 409; тестовая запись, заведённая через API,
удалена корзиной в таблице с подтверждением — из базы ушла, в журнале «Создание»
и «Удаление». `npx tsc --noEmit` чистый на бэкенде и фронте.
