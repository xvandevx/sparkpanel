# Страницы

## 2026-10-27 — адрес страницы стал свойством

Колонка `url` убрана: адрес — системное свойство «Адрес», проверки — при сохранении
значений и при переносе. Новым страницам `sort` = 500 вместо шага 100.
Подробно — `list-settings.md`, запись того же дня.

## 2026-10-25 — адрес отдельным полем, код как у всех списков

**Почему.** В «Категориях» товаров запись верхнего уровня сохранялась без кода, хотя
в настройках стоял «Обязательный и уникальный». Причина — правило страниц, жившее
в общем редакторе: «у записи верхнего уровня в дереве код не обязателен» (главная —
адрес `/`). Оно срабатывало для любого дерева.

**Что сделано**

- У страницы новое поле `url` — сегмент адреса. Пусто — главная (только в корне),
  иначе полный адрес складывается по дереву. Уникальные индексы переехали с `code`
  на `url` (`infoblock_pages_sibling_url`, `infoblock_pages_root_url`), проверка
  «пустой адрес только в корне» — тоже (`assertUrl`).
- `code` у страниц теперь обычный символьный код записи: к адресу не относится,
  в `CreatePageDto` необязателен, «Символьный код записей» разделом не закрыт
  (сохранённая настройка `pages` переведена в «Необязательный»).
- Из общего редактора убрано исключение для корня (`isRootRecord`): «Обязательный»
  обязателен на любом уровне любого дерева.
- «Родитель» в карточке записи — выбор деревом (`TreeSelect`, `parentOptions` отдаёт узлы).

**Перенос данных.** Миграций в проекте нет, а уникальный индекс по `url` при пустой колонке
не создался бы (соседи с одинаковым `''`), поэтому до перезапуска бэкенда выполнено вручную:

```sql
ALTER TABLE infoblock_pages ADD COLUMN IF NOT EXISTS url varchar(255) NOT NULL DEFAULT '';
UPDATE infoblock_pages SET url = code;
DROP INDEX IF EXISTS infoblock_pages_sibling_code;
DROP INDEX IF EXISTS infoblock_pages_root_code;
UPDATE infoblock_settings SET "codeRequired" = false, "codeUnique" = false WHERE "listKey" = 'pages';
```

На любой другой базе с данными (прод) — то же самое до выкатки бэкенда.

**Проверено** — `tsc` бэкенда и фронта; бэкенд поднялся, в Swagger у `PageDto` есть `url`,
в базе новые индексы на месте, старые сняты.

## 2026-10-06 — по итогам ревью

- **Проверка кода стала проверять итог, а не тело запроса.** `PATCH` без поля `code`
  переносил корневую страницу с пустым кодом внутрь другой — проверка не вызывалась
  вовсе, и две страницы получали один адрес. Теперь `assertCode(dto.code ?? page.code, parentId)`.
- **Вернулась уникальность кода среди корневых** — частичным индексом `pages_root_code`
  (`WHERE parentId IS NULL AND code <> ''`). Обычный `pages_sibling_code` корни не
  покрывает: `NULL` в `parentId` Postgres считает различными, и два корня с кодом `news`
  давали один адрес. Пустой код из-под правила выведен — это и есть несколько главных.
- Поправлены Swagger-описания (остались от `isHome` и меты) и докстринг `PagesScreen`;
  из сгенерированного клиента удалены осиротевшие `meta-dto.ts` / `meta-input-dto.ts`.

**Проверено** — перенос корня с пустым кодом без `code` → 400 и страница на месте,
с кодом → проходит; второй корень с тем же непустым кодом → 409; несколько корней
с пустым кодом по-прежнему создаются.

## 2026-10-06 — страница стала обычной записью списка

**Что сделано**

- Убран признак `isHome` и вся его обвязка: частичный индекс `pages_single_home`,
  автосоздание главной, запреты «главную не удалить / код и родителя не менять».
  Главная теперь — это просто страница без родителя, и **их может быть несколько**
  (по одной на домен, на A/B-тест).
- Убрано поле `kind` (`static` / `dynamic`) — тип страницы станет свойством списка.
- Убрана сущность меты целиком: таблица `page_meta`, модуль `meta/`, поля `meta.*`
  и `metaTemplate.*` в форме, вкладка «Мета» и переменные шаблона
  (`logic/pages/pageVariables.ts`). Мета вернётся отдельным функционалом через свойства.

В модели страницы осталось: `parentId`, `position`, `code`, `name`, `isActive`, `content`.

**Ключевые решения**

- **Уникальность кода для корневых не действует.** Индекс `pages_sibling_code` остался
  `(userId, parentId, code)`; Postgres считает `NULL` различными, поэтому несколько
  корневых с пустым кодом сосуществуют. Это не недосмотр, а требование: главных несколько,
  и разводит их домен, а не код.
- **Пустой код допустим только в корне** — у вложенной страницы адрес совпал бы
  с родительским. Проверка в двух местах: поле формы (`validate`) и сервис (400).
- **`parentId: null` отправляется явно** — это осознанный перенос страницы в корень,
  а не «поле не меняли». В DTO `null` проходит через `@ValidateIf`.

**Отступления от задания** — нет.

**Не сделано** (следующий заход, обсуждается)

- Табы в настройках списка (создавать несколько вкладок свойств).
- Галочка «Использовать мету записи» вместо свойства типа «мета».

**Проверено** — `tsc --noEmit` на бэкенде и фронте; схема в БД (`\d pages`) без `isHome`
и `kind`, `page_meta` удалена. Через API: создание двух корневых страниц с пустым кодом
подряд (раньше запрещал индекс), удаление корневой (раньше 400), вложенная без кода → 400.
В браузере: дерево и колонки без «Тип», в карточке нет вкладки «Мета», «Родительская
страница» пустая со значением «В корне сайта», очистка кода у вложенной страницы
блокирует сохранение (в базе код остался прежним).

**Попутно** — незакоммиченный экспериментальный экран `/admin/pages-new` опирался
на `kind`; из его таблицы убрана колонка «Тип», остальное не трогал.

## 2026-09-16 — дерево страниц и универсальный редактор контента

**Что сделано**

- Бэкенд: модули `pages/` (таблица `pages`), `meta/` (таблица `page_meta`), `history/`
  (таблица `change_history`). Эндпоинты `GET/POST/PATCH/DELETE /api/pages`,
  `GET /api/pages/:id/history`, `GET /api/pages/history`.
- Фронтенд: универсальный редактор контента (`logic/contentEditor/` +
  `components/contentEditor/`) — таблица-дерево, шторка на 70% ширины, вкладки,
  история изменений, подстановка переменных в шаблонах.
- Раздел «Страницы» (`/admin/pages`): контроллер редактора в `logic/pages/`,
  экран в `components/pages/`. Заглушка раздела заменена.
- Оформление переведено на стандартную тему Ant Design.

Подробности — [`docs/pages.md`](../docs/pages.md) и [`docs/content-editor.md`](../docs/content-editor.md).

**Ключевые решения**

- **Редактор контента универсальный с самого начала.** Раздел отдаёт ему контроллер
  (данные + описание полей + операции), редактор о разделе не знает. Так «Страницы»,
  инфоблоки и контент получают один экран, а не три похожих. Альтернатива — написать
  экран страниц напрямую и обобщать потом — отклонена: обобщать пришлось бы через
  копипасту, а задание на редактор (`planned/content-editor.md`) уже было.
- **Колонки и поля описываются данными, не разметкой.** `EditorColumnDef.variant`/`value`/`hint`
  вместо `render: () => JSX` — иначе logic-слой начал бы возвращать JSX, что запрещено
  правилами `frontend/CLAUDE.md`.
- **Дерево хранится плоско** (`parentId` + `position`), собирается на фронте. Адрес страницы
  в базе не хранится: он вычисляется из кодов родителей, и при переносе ветки не пришлось бы
  переписывать адреса у всего поддерева.
- **Мета — отдельная таблица, но сохраняется вместе со страницей.** В шторке одна кнопка
  «Сохранить», поэтому `PATCH /api/pages/:id` принимает и мету; `page_meta` при этом остаётся
  самостоятельной сущностью с собственным сервисом.
- **Шаблон меты вместо второй страницы.** У динамической страницы `scope = template` — набор
  полей с переменными `#NAME#`; подставляются они одной чистой функцией и в предпросмотре
  админки, и (в будущем) на сайте.
- **Журнал изменений общий на все разделы** (`entity` + `entityId`), а не таблица на каждый:
  журнал везде читается одинаково, а редактор один. Отдельного контроллера у него нет —
  историю отдаёт раздел, чтобы права на неё совпадали с правами на раздел.
- **`update` без изменений в журнал не пишется** — иначе его заполнили бы «открыл и сохранил».
- **Главная страница создаётся сама** при первом `GET /api/pages`: дереву нужен корень, а
  задавать его вручную или через env — лишний шаг настройки.

**Отступления от задания**

- **Шторка выезжает справа, а не слева**, как было записано в `planned/page-pages.md`, —
  по уточнению заказчика в ходе работы (справа — поведение antd по умолчанию).
- **Идентификатор — порядковый номер, а не UUID.** Задание формата не задавало, сделали
  по общему правилу проекта (`src/DOMAIN.md`: PK — UUID), заказчик попросил простые номера.
  Правило в `DOMAIN.md` обновлено.
- **Тема — стандартная Ant Design** вместо тёмной фирменной: по просьбе заказчика, как в
  панели farkop (стоковый antd: тёмный `Sider` + `Menu theme="dark"`, светлое содержимое).
- Добавлены поля, которых не было в задании: «Порядок» (иначе нечем управлять порядком
  соседей) и «Активна» (страница в админке есть, на сайте её нет).

**Не сделано**

- **Перетаскивание строк мышью.** Порядок и вложенность меняются полями «Порядок» и
  «Родительская страница» — этого хватает, drag&drop в задании не было.
- **Контент — простой текст**, как и просили в задании. Визуальный редактор будет отдельной
  задачей.
- **Элементы динамических страниц** пока не заводятся: задана только мета и её шаблон.
- **Экспорт/импорт XLS и черновики** из исходного компонента farkop не переносились —
  в задании на минимальную версию редактора их нет.

**Проверено**

- Бэкенд: `npx tsc --noEmit`; сценарии через API на живом стеке — создание вложенных
  страниц, дубль кода (409), недопустимый код (400), запрет удаления главной, запрет переноса
  страницы внутрь собственной ветки, удаление поддерева (`removed: 2`), снятие шаблона меты
  при переходе в статичную, история записи и общий журнал.
- Найдено и исправлено при проверке: мета читалась вне транзакции записи, из-за чего ответ
  на создание/изменение возвращал прежние значения, а правки меты не попадали в журнал.
- Фронтенд: `npx tsc --noEmit`; ручной прогон в браузере на `http://localhost:3400/admin/pages` —
  дерево с главной и вложенной страницей, создание страницы (адрес админки получает `?id=2`
