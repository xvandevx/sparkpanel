# Файлы (медиатека)

## 2026-11-04 — внешние файлы в свойствах «Файл» и «Изображение»

**Что сделано**
- Значение «Файла»/«Изображения» — номер своего файла **или адрес внешнего** (`https://…`),
  у множественного — вперемешку. Адрес лежит в `infoblock_values.text`, номер — как раньше
  в `number`; миграции нет — колонки уже были. Сервер адрес не скачивает, сверяет только
  расширение с `formats` (`externalRuleError`), адрес без расширения пропускает.
- Карточка: третья кнопка «Вставить ссылку»; у внешнего файла — превью по адресу, имя
  из адреса, метка «Внешняя ссылка · сайт», «Заменить ссылку», «Забрать в хранилище»,
  «Убрать ссылку». Поле переехало в `drawer/file/`, функции значения — `logic/files/fileValue.ts`.
  Ячейки таблицы и CSV показывают внешний файл по адресу.
- `POST /api/infoblocks/files/import` (`{ url, sectionId | propertyId }`) — сервер скачивает
  внешний файл (до 20 МБ, 30 с, до 5 переадресаций) и кладёт как загрузку; загрузка
  и забирание делят `FilesService.store`.
- Внешнее API: чтение отдаёт внешний файл той же формой `File` (`id`, `mimeType`, `size` —
  null, `isExternal: true`; своим файлам — `isExternal: false`); запись принимает адрес
  и объект `File` из чтения; спецификация OpenAPI это описывает.
- MCP: подсказка к значению в `describe_list` говорит про адрес; `upload_file` принимает
  `url` вместо base64 — забирает через тот же маршрут панели.

**Ключевые решения**
- Адрес — строкой в том же значении, а не отдельным типом свойства или объектом `{ url }`:
  одно свойство «Логотип» держит и старую картинку, и новую загруженную, тип менять не надо.
  Номер и адрес не спутать: адрес начинается с `http(s)://`.
- Внешний файл в API — той же формой `File`, чтобы сайту не ветвиться: `url` есть всегда.
- Скачивание по адресу раньше сознательно не делали (сервер ходил бы куда скажут). Теперь
  оно есть, но во внутреннюю сеть не ходит: каждый адрес, и после переадресации тоже,
  разрешается в IP и сверяется с loopback, частными сетями, link-local, CGNAT
  (`fetch-external.ts`). Остаётся окно DNS-rebinding между проверкой и запросом — принято:
  маршрут закрыт JWT.
- «Забрать в хранилище» значение записи не меняет само: номер ставит карточка, сохраняют
  как обычно — та же модель, что у загрузки с диска.

**Не сделано**
- Смена типа заполненного свойства «Строка» → «Изображение»/«Файл» (если все значения —
  адреса): данные фаркопа перельются заново, правило смены типа осталось простым.
- Пакетное «забрать все внешние файлы списка».
- Заглушка у битого внешнего превью: antd показывает свою «сломанную картинку».

**Проверено**
- Jest: 215 тестов бэкенда, новые — нормализация адреса и смешанных значений,
  `referencedIds` без адресов, формат по расширению, имя из адреса, `apiValue` внешнего,
  запись адреса и объекта `File` во внешнем API, `isPrivateAddress`.
- Живой стек: адрес сохранился в `text` и вернулся; `logo.png` — 400; забирание картинки
  с `s3.twcstorage.ru` — файл в хранилище; `localhost` и `169.254.169.254` — 400, 404
  источника — 400. `/api/v1` по ключу отдаёт `isExternal: true`, принимает `{ url }` и номер.
- Панель (браузер): внешняя картинка в карточке категории с превью и меткой; «Заменить
  ссылку» — неверный адрес с ошибкой, верный — заменился; «Забрать в хранилище» → «Сохранить» —
  в базе номер файла; «Убрать» → «Вставить ссылку» → «Сохранить» — в базе адрес.
  Пробная категория, файлы и ключ удалены.

## 2026-11-01 — встроенное хранилище — папка на диске вместо MinIO

**Что сделано**
- Встроенное хранилище — папка (`UPLOADS_DIR`: локально `backend/uploads`, в образе
  headless — том `/data/uploads`, на нашем проде — `prod/docker/uploads`). Файл лежит
  тем же путём, что ключ объекта (`00/00/78/otchet.pdf`). `StorageService.put/remove`
  для встроенного пишут и удаляют файл, для внешнего S3 — как раньше.
- `/uploads/<ключ>` отдаёт сама панель (`storage/serve-uploads.ts`, `express.static`):
  тип и «показать или скачать» — по расширению (`file-disposition.ts`), вечный кэш,
  `nosniff`, Range/ETag/304. Локально и на проде nginx передаёт этот путь бэкенду.
- MinIO убран отовсюду: локальный compose, nginx, `dev.sh`/`stop.sh`, прод (compose,
  nginx, `.env.example`, README), образ headless (compose, `.env.example`). Переменные
  `S3_*` и `S3_PUBLIC_PREFIX` больше не читаются — адрес встроенного всегда `/uploads`.

**Ключевые решения**
- Сначала было сделано иначе — MinIO остаётся, NestJS проксирует `/uploads` из бакета
  (образу без nginx нужна была своя раздача). Затем решили: по умолчанию всё работает
  через простую папку, кому нужен S3 — добавляет его в «Настройках → Хранилища».
  Установка образа — два сервиса, бэкап файлов — архив тома, отдача с диска быстрее.
- Раздача одна на все поставки — из NestJS; nginx только передаёт путь. Иначе правило
  «`.html`/`.svg` — только скачивать» пришлось бы повторять в конфиге nginx.
- Тип и `Content-Disposition` — по расширению при отдаче, а не из базы: в базу за каждым
  файлом не ходим. Имя при скачивании — код файла, а не исходное имя.
- Миграции БД нет: `storageId = null` по-прежнему «встроенное».

**Не сделано** — пустые папки ключей после удаления файлов не убираются.

**Проверено** — `npm test`: раздача из временной папки (тип, inline/attachment для
`.svg`, кэш, 206, 304, `..` и список папки — 404) и запись/удаление по ключу. Вживую —
настоящий бэкенд на временном Postgres (Docker не отвечал) со статикой панели
(`FRONTEND_DIR`, как в образе), всё на одном порту: загрузка `.png`/`.svg`/`.mp4` кладёт
файлы по ключам, `.png` — `inline`, `.svg` — `attachment`, `Range` — 206, `ETag` — 304,
`..`, список папки и чужой путь — 404, удаление стирает файл с диска, превью в «Файлах»
рисуется. Образ Docker и локальный nginx не проверены: Docker Desktop не отвечал.

## 2026-10-28 — ключ объекта из номера файла и кода

- Ключ объекта — папки из номера плюс код: `00/00/78/voprosy-i-otvety-desktop.pdf`
  (`objectKeyOf`). Колонки `objectKey` больше нет, вместо неё `code` — имя в адресе
  латиницей с расширением (`fileCode`, считается при загрузке и не меняется). `name`
  остался: имя в панели и при скачивании.
- **Почему так.** Путь не хранится — его собирают из номера, рассинхрона «в базе один
  ключ, в бакете другой» не бывает; папки ровные (до сотни на уровень), у каждого файла
  своя — туда же лягут его варианты (превью, webp). Случайный хвост не нужен: уникальность
  даёт папка. Код в адресе вместо `file.pdf` — понятные ссылки и не перебрать файлы
  подряд, не зная имени (при закрытом листинге бакета; встроенный так и открыт —
  только `s3:GetObject`).
- **Код не следует за именем**: переименование в панели не меняет адрес, иначе сломались
  бы ссылки, вставленные в HTML и шаблоны. Имя при скачивании — исходное, из
  `Content-Disposition` при загрузке.
- **Отступление от farkop:** раздела в ключе нет — файл переносят между разделами.
  Нумерацию с 10000 не включали: номер и так дополняется нулями до 6 цифр.
- Загрузка теперь сначала пишет строку (номер нужен для ключа), потом объект; хранилище
  не приняло — строка удаляется.
- **Перенос**: 58 файлов (56 во встроенном MinIO, 2 в timeweb) скопированы на новые
  ключи временным кодом на старте сервера (`CopyObject`, метаданные — от исходного
  объекта), старые объекты удалены, код взят из прежнего ключа без hex-хвоста. Потом
  перенос и колонка `objectKey` убраны. Старые адреса нигде не были вшиты (проверены
  текстовые колонки базы). На проде такого переноса не будет — данных там нет; если
  появятся до выкладки, перенос нужно повторить.
- Проверено: `npm test -- files` (17), `tsc` бэкенда и фронтенда; все 58 файлов отвечают

## 2026-10-28 — разделов свойств в базе нет: файл помнит свойство

**Что сделано**

- У файла новое поле `propertyId`: загруженный через свойство «Файл»/«Изображение»
  файл помнит свойство, `sectionId` у него null; загруженный в раздел — как прежде,
  `sectionId`. Задано ровно одно (так и было в теле загрузки).
- Разделов свойств в `infoblock_files_sections` больше нет (колонка `propertyId`,
  её индекс, `ensureForProperty`, `releaseProperty` и вызовы из сервиса свойств убраны).

  каждое свойство с файлами, группа `group-<ключ списка>` с путём в названии на список.
- Файлы свойства — свой список редактора `property-files.<номер свойства>` (вид
  в `infoblock-kinds.ts`, загрузчик в `RecordsService`, `fileListKey` для значений
  при удалении файла); `GET /api/infoblocks/files?propertyId=`.
- Фронт: `/admin/files/property-6` — раздел свойства, загрузка в нём уходит
  со свойством (`useFileSection` → `target`, `listKey`). В редакторе контента флаги
  записи разделены: `isReadOnly` — карточки, правки, номера и галочки нет, но перейти
  можно (раздел свойства); `isGroup` — ещё и без ссылки (группа). Записи только
  для показа в «Родителе» больше не предлагаются вовсе — особый случай «запись внутри
  закрытой» ушёл.

**Ключевые решения**

- **Предложение заказчика**: хранить разделы свойств незачем — всё про них выводится
  из файлов, а хранимая копия требовала заводить, освобождать и чистить её.
- **Свойство без файлов раздела не даёт** — раздел появляется с первым файлом и пропадает
  с последним.
- **Удалённое свойство файлы не уносит**: они остаются с `propertyId` и видны
  в разделе «Удалённое свойство #N» без группы — оттуда их удаляют. Удаление свойства
  ничего не делает с «Файлами».

**Перенос данных (локальная база)** — файл раздела свойства 29 (73) получил
`propertyId` 239 и `sectionId` null, разделы свойств 29, 37, 38 удалены; затем колонку

  Его читают и раздел (отбирает свои), и поле карточки (показывает выбранный, даёт

- **Загрузка из карточки уходит сразу**, а не по «Сохранить»: значение поля — номер
  файла, и до загрузки его нет. Цена — непривязанный файл, если карточку закрыли без
  сохранения; он виден в разделе свойства и удаляется.
- **Ограничения свойства проверяются при сохранении значения, а не при загрузке**:
  файл выбирают и из уже загруженных. Карточка проверяет до загрузки ещё и разрешение
  картинки — серверу его не узнать.
- **Раздел — список редактора контента**, а файлы — нет: у файла нет карточки
  и свойств, он только загружается и удаляется. Поэтому таблица файлов своя, но
  собрана из тех же кусков (`ActionIcon`, `FileThumb`, поиск над таблицей).
- **`recordPath` — данные, а не функция**: шаблон адреса с `:id`. Раздел не
  объясняет редактору, как переходить, — только куда.
- **`isBlocked` — поле самой записи**, его ставит сервер. Редактор не знает, почему
  запись защищена, и не ветвится по разделу.
- **Хранилище и адрес запоминаются у файла**: переключение хранилища в настройках
  не ломает ссылки на уже загруженное, а удаление идёт туда, где файл лежит.
- **Редактор перечитывает записи при каждом показе раздела** (`useLoadEditor`):
  иначе новый раздел свойства и выросший счётчик файлов появлялись бы только после
  перезагрузки страницы. Настройки, вкладки и свойства по-прежнему грузятся один раз.

**Попутно исправлено**

- `GET /api/infoblocks/pages/values` отвечал 400: `GET :id` у страниц перехватывал
  «values» как номер — значения свойств страниц в карточку не приходили вовсе.

## 2026-10-03 — раздел переехал на редактор контента

**Что сделано**

- Раздел разложен на два уровня, как «Инфоблоки»: `/admin/files` — разделы медиатеки,
  `/admin/files/2` — файлы раздела. Оба экрана — универсальный редактор контента
  (таблица + шторка), своей вёрстки списка и формы у раздела больше нет.
- Загрузка переехала в шторку: «Загрузить файлы» открывает форму с полем выбора файлов,
  описанием и разделом. Сохранение такой формы и есть загрузка; можно выбрать пачку.
- Удалены свои компоненты раздела (две панели, таблицы, модалка раздела, строка
  с инлайн-описанием) и хуки под них — `components/files/` теперь два экрана-композиции.

**Ключевые решения**

- **Два уровня, а не дерево в одной таблице.** Вложенные строки (как у «Веб-форм»)
  показали бы разделы и файлы вместе, но раскрытый раздел с сотнями файлов — это сотни
  строк без собственной постраничности. Уровни-страницы берут это на себя и дают
  тот же способ навигации, что в «Инфоблоках».
- **Запись заводится самим файлом.** Поэтому в общий слой формы добавлен тип поля
  `file`: без него «добавить» в шторке нечем было бы заполнить. Файл уходит на сервер
  в `save` раздела, а не в самом поле — слой формы остаётся без сети.
- **Превью осталось.** Для этого у колонок появился вариант `image`; пустое значение
  означает «нарисуй значок файла», поэтому у pdf и архивов не висит битая картинка.
- **Кнопка «открыть» в строке** — новая иконка у `rowAction` (`open`): у файла внутри
  ничего нет, зато его самого нужно открыть одним кликом.
- **`LevelGate` и `LevelCrumbs` переехали в `components/shared/`** — их используют
  два раздела (инфоблоки и файлы); заголовок отказа загрузки стал пропом.
  Туда же, в `logic/plural.ts`, переехал счётчик с русскими окончаниями.

**Отступления от задания**

на `ContentEditor`. Три расширения общего слоя (поле `file`, колонка `image`, действие

## 2026-09-16 — раздел «Файлы»: разделы, загрузка в S3, раздача через nginx

**Что сделано**

- Бэкенд: модуль `files/` — таблицы `file_sections` и `files`, контроллеры
  `/api/file-sections` (CRUD разделов со счётчиком файлов) и `/api/files`
  (список, multipart-загрузка, правка описания и переноса, удаление).
- Бэкенд: модуль `storage/` — обёртка над S3 (`@aws-sdk/client-s3`): положить объект,
  удалить, сказать публичный адрес. Бакет и политику анонимного чтения заводит сам
  при старте.
- Инфраструктура: MinIO в локальном и прод docker-compose, `location /uploads/` в обоих
  nginx, `S3_*` в `.env.example`, том и бэкап описаны в `prod/README.md`.
- Фронт: раздел `/admin/files` — `components/files/` + `logic/files/` + слайс `redux/files`,
  пункт «Файлы» в меню.

**Ключевые решения**

- **Одна медиатека на файлы и изображения.** Картинка отличается только MIME-типом
  (`isImage` в DTO); отдельная сущность под изображения означала бы второй такой же
  экран и второй API.
- **Плоский справочник разделов, а не дерево папок.** Файлы группируют по назначению
  (`banners`, `docs`), а не по структуре сайта; дерево потребовало бы переносов веток,
  запрета циклов и хлебных крошек — ради группировки, которой хватает в один уровень.
- **Файлы в S3 (MinIO в docker), а не на диске бэкенда и не в базе.** Выбор заказчика:
  своё S3 в контейнере. Попутно это снимает вопрос тома, общего у бэкенда и nginx,
  и оставляет дорогу к внешнему S3 — меняется только `S3_ENDPOINT`.
- **Раздаёт nginx, а не бэкенд.** `/uploads/<ключ>` проксируется прямо в бакет: тот же
  origin (ссылки относительные, CORS не нужен), Node в раздаче картинок не участвует.
- **Ключ объекта без раздела:** `<userId>/<год>/<месяц>/<hex>-<имя>`. Файл можно
  перенести в другой раздел, и ключ, собранный из раздела, после переноса врал бы.
- **Исполняемые типы отдаются `attachment`.** Файлы лежат на origin панели, значит
  открытый `.html` или `.svg` выполнился бы рядом с cookie `access_token`. `inline`
  оставлен растровым картинкам, pdf, видео и аудио — превью в админке от этого
  не страдает (`<img src>` рисует картинку независимо от заголовка).
- **Раздел с файлами не удаляется** (409). Альтернатива — удалять содержимое вместе
  с разделом — слишком дорогая ошибка для одного клика.
- **Экран написан свой, редактор контента не использован.** Редактор — это «таблица
  записей + шторка с формой»; здесь две связанные панели, где выбор раздела слева меняет
  содержимое справа, а вкладки редактора умеют показывать только поля формы.
  Форма самого раздела при этом — общая (`logic/editorForm`), своей разметки полей нет.
- **Имя файла из multipart перекодируется из latin1.** Иначе кириллица в имени
  приезжает крокозябрами: multer читает имя как latin1.

**Отступления от задания**

Задания в `planned/` не было — раздел сделан по образцу страницы `pages/images` из
проекта farkopru (справочник разделов слева, файлы справа) с уточнениями заказчика:
одна медиатека на файлы и изображения, плоские разделы, своё S3 в docker,
изображения не обрабатывать.

Отличия от образца:

- код и название раздела правятся в окне с общей формой, а не инлайном в таблице:
  инлайн-правка тянет в компонент состояние, которому место в logic-слое;
- просмотр картинки во весь экран — штатный просмотрщик antd, а не своё модальное окно;
- добавлен перенос файла в другой раздел и копирование ссылки — оба нужны, чтобы
  вставлять файлы в контент.

**Не сделано**

- **Обработка изображений** (превью, конвертация в WebP, ширина/высота) — по решению
  заказчика: храним как есть. В админке превью — уменьшенный оригинал, так что на
  разделе в сотни тяжёлых картинок список будет грузиться заметно дольше; появится
