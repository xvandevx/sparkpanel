## 2026-10-12 — сколько угодно внешних хранилищ

**Что сделано**

- Таблица `infoblock_storages` (модуль `infoblocks/storages/`, `/api/infoblocks/storages`):
  внешние S3-хранилища списком, без владельца — как и настройки. Список, создание,
  сохранение целиком (`PUT`), удаление.
- В настройках вместо ключей `storage` и `s3*` — один ключ `storageId`: какое
  хранилище берёт новые файлы, пусто — встроенное. `SettingsDto` — `{ siteName, storageId }`.
- У файла `storage` (`builtin`/`external`) заменён на `storageId` (null — встроенное):
  файл удаляется из того хранилища, куда его положили.
- Вкладка «Файлы»: выбор хранилища и кнопка «Хранилища» — шторка со списком
  на `ContentEditor` (без журнала, настроек списка и поиска). Вид списка `storages`
  добавлен в `infoblock-kinds.ts` и `ListKey`.
- В общий слой редактора добавлен тип поля `FieldType.Password` — секрет набирается скрыто.

**Ключевые решения**

- **Модуль в `infoblocks/`, а не в `settings/`.** Хранилища — список редактора
  контента, а все такие списки (`pages`, `files`) лежат в `infoblocks/`: папка, маршрут
  и таблица идут вместе. Сначала модуль был положен в `settings/storages/` по смыслу
  («это настройка») и перенесён — таблица `settings_storages` к тому времени была пуста.
- **Хранилище проверяется при сохранении**, а не при выборе только: в список не попадает
  хранилище, которое не отвечает. При выборе — ещё раз: ключи могли отозвать.
- **Занятое хранилище не удаляется** — выбранное (`isBlocked`) или с файлами: иначе
  файлы нечем было бы удалить. Замок в строке даёт тот же `isBlocked` редактора.
- **Хранилище правится целиком** (`PUT`): карточка редактора присылает все поля;
  пустой секрет — «прежний», потому что наружу он не отдаётся.
- **Список хранилищ — ячейка редактора `storages`**: её же читает выбор на вкладке,
  поэтому добавленное в шторке сразу появляется в выборе. Сохранили другой выбор —
  список перечитывается, чтобы замок переехал.

**Перенос данных** — строка `storage = builtin` в `settings` удалена (её место занял
`storageId`, пусто — встроенное). Колонку `files.storage` синхронизация схемы заменила
на `storageId`; все 53 файла были во встроенном, им достался `null`. На базе, где есть
файлы во внешнем хранилище (`storage = 'external'`), так делать нельзя: сначала завести
хранилище строкой в `infoblock_storages` и проставить файлам его номер.

**Проверено**

- `tsc --noEmit` на обеих частях, `jest` — 49 тестов; клиент API перегенерирован.
- API: неверные ключи → 400, без секрета → 400, создание, правка с пустым секретом
  (секрет остался), выбор хранилища, выбор несуществующего → 404, загрузка ушла
  в выбранное (`storageId` у файла), удаление выбранного и с файлами → 409, удаление
  файла убрало объект из бакета, после этого хранилище удаляется.
- Браузер: вкладка «Файлы», шторка «Хранилища», добавление через карточку, выбор
  в списке и сохранение — у хранилища появился замок, в карточке нет «Удалить»;
  переименование без секрета, новое имя сразу в выборе.
- Тестовое хранилище, бакет и выбор после проверки убраны.

## 2026-10-12 — настройки строкой на ключ, без владельца

**Что сделано**

- Таблица `settings` переделана из «строка на пользователя, колонка на настройку»
  в «строка на настройку»: `id`, `key`, `value`. Колонки `userId` больше нет —
  настройки общие на весь сайт. Уникальный индекс `settings_key`.
- Ключи и значения по умолчанию — один список `SETTINGS_DEFAULTS`
  (`settings/settings-values.ts`): новая настройка добавляется ключом в него,
  без новой колонки. Нет строки — значение по умолчанию.
- Сохранение пишет только изменённые ключи — `upsert` по `key` в одной транзакции.
- `SettingsService` и его вызовы из `files/` больше не принимают `userId`.
- API и форма не изменились: `SettingsDto` прежний, клиент не перегенерировался.

**Ключевые решения**

- **Значение — `TEXT`.** Все настройки сегодня строки; типизация — в
  `SETTINGS_DEFAULTS`, а `storage` с незнакомым значением читается как `builtin`.
- **Незнакомые ключи в базе не читаются**: строка, оставшаяся от удалённой
  настройки, ни на что не влияет.

**Перенос данных (разово, локальная база)** — заполненные значения прежней строки
стали строками-настройками, копия прежней таблицы — `zz_legacy_settings`:

```sql
CREATE TABLE zz_legacy_settings AS TABLE settings;
DROP TABLE settings;
CREATE TABLE settings (id SERIAL PRIMARY KEY, key VARCHAR(64) NOT NULL,
  value TEXT NOT NULL DEFAULT '', "createdAt" TIMESTAMPTZ NOT NULL, "updatedAt" TIMESTAMPTZ NOT NULL);
CREATE UNIQUE INDEX settings_key ON settings (key);
INSERT INTO settings (key, value, "createdAt", "updatedAt")
SELECT kv.key, kv.value, s."createdAt", s."updatedAt"
FROM zz_legacy_settings s
CROSS JOIN LATERAL (VALUES ('siteName', s."siteName"), ('storage', s.storage),
  ('s3Endpoint', s."s3Endpoint"), ('s3Region', s."s3Region"), ('s3Bucket', s."s3Bucket"),
  ('s3AccessKey', s."s3AccessKey"), ('s3SecretKey', s."s3SecretKey"),
  ('s3PublicUrl', s."s3PublicUrl")) AS kv(key, value)
WHERE kv.value <> '';
```

Если на базе строк настроек несколько (несколько пользователей), `INSERT` упадёт
на уникальном ключе: тогда сначала решить, чьи настройки остаются, и оставить
в копии одну строку. Локально строка была одна.

**Не сделано**

- Права на правку: менять настройки может любой вошедший пользователь панели,
  хотя теперь правка касается всех.

**Проверено**

- `tsc --noEmit`, бэкенд стартует без правок схемы.
- API: чтение (значения из строк + по умолчанию), правка названия обновляет свою
  строку, новые ключи ложатся новыми строками, неполное внешнее хранилище → 400,
  секрет в ответе — только `isS3SecretKeySet`, без токена → 401.
- Загрузка и удаление файла берут хранилище из новых настроек.
- Тестовые значения после проверки удалены.

## 2026-10-10 — вкладки «Общие» и «Файлы», внешнее хранилище

**Что сделано**

- Модуль `settings/` вернулся из `to_delete/` и расширен: в `settings` — выбор
  хранилища (`storage`) и ключи внешнего S3 (`s3Endpoint`, `s3Region`, `s3Bucket`,
  `s3AccessKey`, `s3SecretKey`, `s3PublicUrl`). Таблица прежняя, новые колонки
  с значениями по умолчанию — синхронизация схемы добавила их сама.
- `storage/` вернулся и умеет класть объект и во встроенное хранилище, и во внешнее
  (`StorageTarget`), а также проверять внешнее (`HeadBucket`).
- Экран `/admin/settings`: вкладки «Общие» (название сайта) и «Файлы»
  (встроенное / внешнее S3), один черновик и одна кнопка «Сохранить».

**Ключевые решения**

- **Секрет наружу не отдаётся**: в ответе `isS3SecretKeySet`, пустой секрет в запросе —
  «не менять». Форма прежнего ключа не знает и стереть его случайно не может.
- **Внешнее хранилище проверяется при сохранении**, если его выбрали или поменяли
  ключи: о неверном ключе лучше узнать здесь, чем на первой загрузке из карточки.
  Не ответило — не сохраняется ничего. Название сайта без проверки сохраняется всегда.
- **Бакет внешнего хранилища не трогаем**: не создаём, политику чтения не ставим —
  он чужой. Публичный адрес задаётся отдельно, на случай CDN или домена бакета.

**Отступления от задания**

- Доменов на странице больше нет: модуль `domains` лежит в `to_delete/`.

**Не сделано**

- Ключи внешнего хранилища хранятся в базе открытым текстом.
- Адрес внешнего хранилища не ограничен по сетям: бэкенд постучится на любой `http(s)`.

**Проверено**

- API: неполные ключи → 400, адрес не `http(s)` → 400, неверные ключи → «нет доступа
  к бакету», нет бакета → «бакет не найден»; после ошибки настройки не изменились;
  правка одного названия при выбранном внешнем хранилище проходит без проверки;
  секрет в ответе не появляется.
- Браузер: вкладки, переключатель хранилища, предупреждение и неактивная «Сохранить»
  при пустом бакете, ошибка сервера при несуществующем бакете, «Отменить».
- Тестовые ключи после проверки стёрты.

## 2026-09-16 — поддомены и общая форма с редактором контента

**Что сделано**

- Бэкенд: в `settings` добавлены `hasSubdomains` (BOOLEAN) и `subdomains` (`STRING[]`),
  нормализация и проверка списка в `UpdateSettingsDto`, достройка имён в сервисе.
- Фронтенд: **слой формы вынесен из редактора контента в общий** — `logic/editorForm/` +
  `components/editorForm/`. Редактор контента (шторка) и «Настройки» рисуют поля одними
  и теми же компонентами.
- Раздел «Настройки» переписан на этот слой: поля описаны данными (`settingsFields.ts`),
  экран — карточка с кнопками «Отменить»/«Сохранить» в шапке и предупреждением о
  несохранённых правках, как в шторке.
- В контракт поля добавлены тип `tags` (список строк) и `validate(value, values)` —
  проверка значения чистой функцией раздела.

Подробности — [`docs/settings.md`](../docs/settings.md) и [`docs/editor-form.md`](../docs/editor-form.md).

**Ключевые решения**

- **Визуальную часть шторки не копировали, а вынесли.** Заказчик просил «взять визуальную
  часть из ContentEditorDrawer»; копия разошлась бы с оригиналом на первой же правке.
  Поля, группы и состояние формы теперь общие, шторка осталась обёрткой с вкладками,
  таблицей и историей. `logic/contentEditor/useEditorState` работает поверх того же
  `useEditorFormState`, что и «Настройки», — вторая реализация формы в панели не появилась.
- **Проверка значений переехала в описание поля** (`validate`). Иначе экранам пришлось бы
  дублировать её вокруг формы, а правила должны лежать рядом с полем, которое они проверяют.
- **Поддомены — массив в той же таблице, а не отдельная сущность.** Своих полей у поддомена
  нет, живёт он только вместе с настройками: отдельная таблица дала бы join и id там,
  где нужен просто список строк.
- **Поддомены хранятся полными именами** (`shop.example.com`), но `shop` при заданном домене
  достраивается. Полное имя — то, что потом попадёт в `server_name` nginx; достройка нужна
  потому, что в разговоре поддомен называют одним словом.
- **Снятая галочка очищает список.** Тот же принцип, что с шаблоном меты у статичной страницы:
  скрытых настроек, которые продолжают где-то действовать, в системе нет. Предупреждение
  об этом стоит подписью под переключателем.
- **Ограничение в 50 поддоменов.** Настройка сайта больше этого не бывает, а без предела
  один запрос мог бы залить в строку произвольный объём данных.

**Отступления от задания**

Задания в `planned/` не было — раздел заказан в переписке: галочка «сайт имеет несколько
поддоменов», поле для списка и «взять визуальную часть из ContentEditorDrawer». Сделано это,
плюс вынос общего слоя формы — без него «взять визуальную часть» означало бы копипасту.

**Не сделано**

- Проверка, что поддомен принадлежит основному домену: `shop.other.com` при домене
  `example.com` сохранится. Сайты нередко живут на нескольких разных именах, и запрет
  мешал бы чаще, чем помогал.
- Журнал изменений для настроек — как и раньше, журнал заведён под разделы со списками.

**Проверено**

- Нормализация и проверка списка поддоменов — прогон `UpdateSettingsDto` через
  `class-transformer` + `class-validator`: ` HTTPS://Shop.Example.com/catalog ` → `shop.example.com`,
  повторы схлопываются, пустые выбрасываются, `плохой поддомен` отклоняется, 51 элемент —
  ошибка `ArrayMaxSize`, `hasSubdomains: 'да'` — ошибка типа.
- Достройка имени: `completeSubdomains(['shop', 'blog.example.com'], 'example.com')` →
  `['shop.example.com', 'blog.example.com']`; без домена `shop` остаётся как есть;
  `shop` + `shop.example.com` схлопываются в одно.
- Схема в базе приведена автоматически (`sync: { alter: true }`): колонки `hasSubdomains`
  и `subdomains` на месте.
- `tsc --noEmit` на бэкенде и фронтенде — без ошибок.
- Раздел «Страницы» после выноса формы собирается и открывается без ошибок в консоли.

## 2026-09-16 — раздел настроек: домен и название сайта

**Что сделано**

- Бэкенд: модуль `settings/` (таблица `settings`, одна строка на пользователя),
  эндпоинты `GET /api/settings` и `PATCH /api/settings`.
- Фронтенд: раздел `/admin/settings` — `components/settings/` + `logic/settings/` +
  `redux/reducers/settingsReducer.ts` + `api/settings.ts`. Поля: название сайта, домен сайта.
- Пункт «Настройки» добавлен **последним** в `config/navigation.ts` — из этого же списка
  строятся меню, заголовок в шапке и подсветка активного пункта.
- Переходник `asRule` вынесен из `logic/auth/validate.ts` в общий `logic/formRules.ts`
  (из `logic/auth` он по-прежнему реэкспортируется, существующие импорты не трогали).

Подробности — [`docs/settings.md`](../docs/settings.md).

**Ключевые решения**

- **Свой экран, а не универсальный редактор контента.** Редактор — это «таблица + шторка»
  для списков записей; здесь одна запись на пользователя, списка нет. Натягивать на неё
  редактор значило бы заводить фиктивную таблицу из одной строки.
- **Строка заводится при первом сохранении, а не при чтении.** В разделе «Страницы»
  главная создаётся на `GET` (дереву нужен корень, раздел не бывает пустым) — здесь этого
  не требуется: пустые настройки прекрасно описываются пустым DTO, а `GET` не должен писать в базу.
- **Домен нормализуется до проверки формата** — `https://Example.com/about` → `example.com`.
  Адрес копируют из адресной строки; отказ из-за протокола выглядел бы придиркой.
  Нормализация продублирована на фронте, иначе после сохранения поле «мигало» бы другим значением.
- **На бэкенде домен проверяется регуляркой, а не `class-validator`-хелпером** (`IsFQDN`):
  нужно пропускать пустое значение и хост с портом (`localhost:3400`), а `IsFQDN` не пропускает ни то, ни другое.
- **Уникальность настроек держит индекс** `settings_single_per_user`, а не только проверка
  в сервисе — тот же довод, что у `pages_single_home`: два параллельных первых сохранения
  прошли бы проверку оба.
- **PATCH шлёт только изменённые поля**, а при пустом патче запрос не уходит вовсе —
  «сохранение» без единого изменения не должно дергать сервер.

**Отступления от задания**

Задания в `planned/` не было — раздел заказан в переписке: «страница настроек, последним
пунктом меню, домен сайта и название сайта». Сделано ровно это.

**Не сделано**

- Журнал изменений (`change_history`) для настроек — журнал заведён под разделы со списками,
  для одной формы это отдельная задача (и отдельный экран в интерфейсе).
- Прочие параметры сайта (почта, аналитика, реквизиты) — появятся по мере надобности,
  каркас раздела к этому готов: добавляется поле в модель, DTO и форму.

**Проверено**

- Нормализация и валидация DTO — прогон `UpdateSettingsDto` через `class-transformer` +
  `class-validator`: `https://Example.com/about` → `example.com`, `  CoPanel  ` → `CoPanel`,
  `sub.example.co.uk` и `localhost:3400` проходят, пустая строка проходит, `не домен`
  и `-bad-.com` отклоняются с текстом ошибки.
- `GET /api/settings` без токена → `401` (глобальный гард на месте).
- Вручную в браузере (`http://localhost:3400/admin/settings`): сохранение
  `https://Example.com/about` → в поле и в базе `example.com`, сообщение «Настройки сохранены»;
  повторное сохранение без правок → «Изменений нет», запроса в сеть нет; `bad_domain!` →
  ошибка под полем, форма не отправляется; перезагрузка страницы → значения читаются из базы.
  Тестовые значения после проверки очищены.
- `tsc --noEmit` на бэкенде и фронтенде — без ошибок.
