# Контент: типы и элементы

## 2026-10-24 — раздел `contents`, элементы — `items` внутри

**Что сделано**

- По просьбе заказчика структура ещё раз перевёрнута: раздел — `contents`, в нём типы
  контента, внутри — `items`, элементы. Предыдущая раскладка (`content/` с типами внутри,
  запись ниже) отменена.
- Бэкенд: `infoblocks/contents/` (`Contents`, `infoblock_contents`, `/api/infoblocks/contents`)
  и `infoblocks/contents/items/` (`ContentItems`, `infoblock_contents_items`,
  `/api/infoblocks/contents/:contentId/items`). Поле элемента `typeId` → `contentId`,
  у типа `elementsCount` → `itemsCount`. Общие куски DTO — в DTO типа.
- Ключи списков: `content-types` → `contents`, `content-elements.<id>` → `content-items.<id>`.
- База переименована одной транзакцией в SQL до перезапуска бэкенда: таблицы, колонка
  `typeId` → `contentId`, индексы, счётчики номеров; `infoblock_settings.listKey` и коды
  по умолчанию (`content-items-<id>`), `history.entity`. Данные — 8 типов, 3 элемента,
  настройки 11 списков, 32 строки журнала — на месте.
- Фронт: `/admin/contents`, `/admin/contents/[contentId]`; `components/contents/`
  (`ContentsScreen`, `ContentItemsScreen`), `logic/contents/` (`contentsApi`, `contentItemsApi`,
  `useContent`, `useContentsMenu`), `api/contents.ts`, `api/contentItems.ts`; ключи
  `ListKey.contents`, `ListKey.contentItems(id)`, источник меню `contents`. Клиент API
  перегенерирован начисто (`generate-api:clean` — иначе остаются файлы старых имён).
- HTML-блоки остаются на `/admin/html-blocks`.
- Документация раздела — `docs/contents.md` (было `content-types.md`), журнал — этот файл.

**Проверено**

- `tsc` бэкенда и фронта, `jest` — 82 теста.
- API: `/api/infoblocks/contents`, `/api/infoblocks/contents/2/items`, настройки
  `content-items.8` (имя и код типа), журнал `contents` — отдают перенесённые данные;
  лишних пустых таблиц sync не создал.
- В браузере: `/admin/contents` — дерево типов, счётчики, меню; `/admin/contents/8` —
  крошки через родителя, элемент на месте.

## 2026-10-24 — контент главный, типы внутри; HTML-блоки переехали

**Что сделано**

- Бэкенд: модуль `infoblocks/content-types/` (с элементами во вложенном `elements/`)
  перевёрнут — `infoblocks/content/` теперь сам контент (элементы), а `types/` вложен в него,
  как `categories/` в `products/`. Маршруты: элементы — `/api/infoblocks/content/:typeId`,
  типы — `/api/infoblocks/content/types`. Таблица элементов переименована
  `infoblock_content_elements` → `infoblock_content` вместе с индексами и счётчиком номеров
  (руками в SQL до перезапуска бэкенда, данные сохранены). Общие куски DTO (формат кода,
  `ParentDto`) — в DTO элемента, типы берут их оттуда.
- Фронт: «Контент» — `/admin/content` (типы) и `/admin/content/[typeId]` (элементы), папки
  `components/content/`, `logic/content/`. HTML-блоки переехали на `/admin/html-blocks`,
  папки — `components/htmlBlocks/` (`HtmlBlocksScreen`) и `logic/htmlBlocks/` (`htmlBlocksApi`).
  Клиент API перегенерирован.

**Не тронуто намеренно**

- Ключи списков `content-types` и `content-elements.<id>`: ключ `content` занят HTML-блоками,
  а по ключам в базе лежат настройки, свойства, значения и журнал.
- Бэкенд HTML-блоков (`src/content/`, `/api/content`, `content_blocks`) и `api/content.ts` на фронте.
- Файл документации раздела — по-прежнему `docs/content-types.md`: `docs/content.md` — HTML-блоки.

**Проверено**

- `tsc` бэкенда и фронта, `jest` — 82 теста.
- API: `/api/infoblocks/content/types` и `/api/infoblocks/content/2` отдают ваши данные,
  старый `/api/infoblocks/content-types` — 404.
- В браузере: `/admin/content` — дерево типов и то же дерево в меню; `/admin/content/8` —
  крошки через родителя, ветка меню раскрыта; `/admin/html-blocks` — список блоков.

## 2026-10-23 — типы контента в меню; имя списка типов закрыто

**Что сделано**

- «Контент» в левом меню раскрывается в дерево типов — та же вложенность, что в списке;
  сам пункт по-прежнему ведёт на список типов. В конфиге меню вернулся источник подпунктов
  из данных (`childrenSource: 'contentTypes'`), дерево строит `useContentTypeMenu`
  (`logic/contentTypes/`) из ячейки списка типов в сторе.
- Имя списка `content-types` закрыто в настройках — «Типы контента».

**Ключевые решения**

- Меню читает ту же ячейку стора, что редактор: тип, заведённый или переименованный
  в списке, появляется в меню без отдельной загрузки.
- Тип с потерянным родителем или в кольце родителей встаёт в корень меню, а не пропадает.

**Проверено**

- `tsc` фронта; `typeMenu` на дереве из трёх уровней, сироте и кольце.
- В браузере: «Контент» раскрыт на странице типа, тип подсвечен; клик по «Контенту» ведёт
  на список; в настройках списка типов имя закрыто. Вложенное меню на живых данных
  не смотрел: список типов у вас плоский, а менять его настройки ради проверки я не стал.

## 2026-10-23 — тип задаёт имя и код списка элементов; вложенность открыта

**Что сделано**

- Название и код типа — имя и код списка его элементов `content-elements.<id>`. Сервер
  пишет их в настройки списка при каждом создании и правке типа, в той же транзакции
  (новые методы `InfoblockSettingsService.assignIdentity` / `releaseIdentity`). В окне
  настроек списка элементов имя и код закрыты: в `BlockedSettings` общего слоя появилось
  поле `name` (до сих пор закрывать можно было только код).
- Код типа стал обязательным (DTO и `codeMode: Required` у списка типов): список без кода
  сайту не найти. Занятый другим списком код — 409, тип не сохраняется.
- Удаление типа возвращает его списку элементов имя и код по умолчанию — код освобождается.
- «Уровней вложенности» больше не закрыт ни у типов, ни у элементов: у обеих таблиц
  появился `parentId`, сервер проверяет «не в свою ветку» и предел списка, тип и элемент
  с вложенными не удаляются (409). Крошки типа идут через его предков.

**Ключевые решения**

- **Синхронизирует сервер, а не только окно настроек**: закрытое значение в окне чинит
  список лишь при сохранении настроек, а сайт ищет список по коду сразу после правки типа.
- По умолчанию оба списка остаются плоскими (предел 1) — деревом их делают в настройках.

**Проверено**

- `tsc` бэкенда и фронта, `jest` — 82 теста.
- Через API: настройки списка элементов получают имя и код типа при создании и после
  переименования; код `products` — 409 и тип не заведён; тип без кода — 400; вложение
  при пределе 1 — 400; после смены предела на 3 элемент вкладывается, родитель
  с вложенным не удаляется (409); после удаления типа код свободен для нового.
- В браузере: в настройках списка элементов имя и код закрыты и совпадают с типом,
  «Уровней вложенности» правится, после сохранения 2 в карточке элемента есть «Родитель».
  Тестовые типы удалены.
- У типа «Марки автомобилей», заведённого до изменения, настройки списка элементов
  синхронизированы правкой типа через API.

## 2026-10-23 — раздел «Контент»: типы контента и элементы типа

**Что сделано**

- Бэкенд: модули `infoblocks/content-types/` (таблица `infoblock_content_types`,
  `/api/infoblocks/content-types`) и `infoblocks/content-types/elements/`
  (`infoblock_content_elements`, `/api/infoblocks/content-types/:typeId/elements`);
  ключи списков `content-types` и `content-elements.<typeId>` — в `content-lists.ts`.
- Виды списков в `infoblock-kinds.ts`: оба плоские, оба с журналом. Общее правило
  реестра: у **вложенного** вида с журналом тип записи в журнале — полный ключ списка
  (`content-elements.3`), а не вид.
- Фронт: пункт меню «Контент» после «Страниц» (`config/navigation.ts`), страницы
  `/admin/content-types` и `/admin/content-types/[typeId]`, экраны `components/contentTypes/`
  (`TypesScreen`, `TypeScreen`), Api и открытый тип — `logic/contentTypes/`, сетевой слой —
  `api/contentTypes.ts`, `api/contentElements.ts`, ключи `ListKey.contentTypes`,
  `ListKey.contentElements(typeId)`. Клиент API перегенерирован.

**Ключевые решения**

- **Устроено как «Файлы»** (так попросил заказчик): корень — список типов с `recordPath`,
  тип — своя страница с крошками и вторым редактором контента. Своего экрана списка нет.
- **Элементы каждого типа — свой список** `content-elements.<typeId>`: у новостей и статей
  разные свойства. Отсюда и журнал по полному ключу — иначе журнал «Новостей» показывал бы
  правки «Статей». Альтернатива (один вид `content-elements` на всех) отклонена.
- **Элемент адресуется вместе с типом** и фильтруется по `userId` и `typeId` — по одному
  номеру нельзя поправить элемент чужого типа.
- **Оба списка плоские** (закрыто разделом, `maxDepth: 1`): колонки `parentId` нет.
- **Удаляется только пустой тип** (как раздел файлов), непустой приходит с `isBlocked`.
- **`userId` у обеих таблиц** — контент сайта, как страницы и товары.
- Маршрут `/admin/content-types`, а не `/admin/content`: тот занят HTML-блоками.

**Не сделано**

- Элементы не стали источником «Привязки к контенту» (`LinkTargetsService`).
- Вложенность элементов (дерево) и ручной порядок.
- Журнал в интерфейсе — заглушка нового редактора, как у всех разделов; сервер пишет.

**Проверено**

- `npx tsc --noEmit` во `backend/` и `frontend/`; `jest` — 82 теста зелёные.
- Через API на поднятом стеке: создание типа и элемента, правка, 404 на чужой тип,
  409 на удаление непустого типа, журнал `content-elements.1` пишет правку, настройки
  списка `content-elements.1` читаются.
- В браузере: пункт «Контент» в меню и подсветка на обоих уровнях, список типов со счётчиком
  и замком, переход в тип, крошки, создание элемента из карточки. Тестовые данные удалены.
