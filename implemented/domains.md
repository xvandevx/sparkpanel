## 2026-10-13 — домены и поддомены деревом во вкладке «Домены» настроек

**Что сделано**

- Бэкенд: модуль `infoblocks/domains/` — таблица `infoblock_domains` (`parentId`, `name`,
  `isActive`), `GET/POST/PATCH/DELETE /api/infoblocks/domains`; в ответе — ещё полный
  `address`. Вид списка `domains` в `infoblock-kinds.ts`: общий (`isShared`), без журнала,
  2 уровня по умолчанию.
- Фронт: вкладка «Домены» в настройках (`components/settings/DomainList.tsx`) на новом
  `ContentEditor`, Api — `logic/settings/domainsApi.ts`, сеть — `api/domains.ts`.
  Колонки «Домен» (дерево), «Адрес», «Активность». На этой вкладке скрыты
  «Отменить»/«Сохранить» настроек сайта.
- Из публичного входа редактора отдаётся тип `BlockedSettings`: закрытые настройки
  раздела выносятся в константу модуля, а не пишутся литералом в JSX.
- Данные перенесены из прежней таблицы `domains` (см. ниже).

Подробности — [`docs/domains.md`](../docs/domains.md) и [`docs/settings.md`](../docs/settings.md).

**Ключевые решения**

- **Дерево вместо флага `isMain`.** Задание — «сколько угодно доменов, к каждому сколько
  угодно поддоменов, вложенность 2». Основной домен как понятие ушёл: доменов в корне
  сколько угодно, поддомен привязан к своему домену `parentId`. Предел 2 закрыт разделом
  (`blockedSettings`) и задан видом списка по умолчанию.
- **У поддомена хранится только его часть** (`ekb`), полный адрес складывается при выдаче.
  Сначала было сделано наоборот — полное имя в базе, короткое достраивалось родителем,
  — и заказчик, посмотрев, назвал это нелогичным: набрал `ekb`, сохранил, а в поле
  `ekb.farkop.ru`. Теперь что набрали, то и сохранено, а адрес видно отдельной колонкой.
  Заодно ушёл каскад переименования: сменили имя домена — адреса поддоменов сложились
  заново сами.
- **Уникален адрес, а не имя.** `www` у двух доменов — разные адреса, а домен
  `ekb.farkop.ru` рядом с поддоменом `ekb` у `farkop.ru` — один. Поэтому проверка в сервисе
  по сложенным адресам всех записей; индексы (`parentId`+`name` и `name` у корневых)
  держат от гонки частые случаи.
- **Полное имя в поле поддомена — ошибка, а не молчаливая правка**: `ekb.farkop.ru` под
  `farkop.ru` → 400 с подсказкой «только его имя: ekb». Срезать хвост самому — снова
  сохранить не то, что набрали.
- **Без примечания.** Поле `note` было перенесено из прежней схемы и убрано по просьбе
  заказчика; что нужно знать о домене — свойства списка. Тексты остались в старой таблице
  `domains`.
- **Домены общие на сайт, а не по `userId`.** Прежний модуль хранил их у пользователя,
  но вкладка живёт в настройках, а настройки и хранилища общие: иначе у каждого
  сотрудника был бы свой список доменов одного сайта.
- **Без журнала** — как у остальных настроек сайта. Свойства у доменов есть: их уже
  завели (регион, счётчик, стартовая страница, блоки в подвале, схема филиала, robots.txt),
  поэтому «Настройки» списка на вкладке оставлены.
- **Домен с поддоменами не удаляется** (409) — как категории товаров и разделы файлов.

**Перенос данных** — одним SQL после первого старта сервера с новым модулем (таблица
к этому времени создана синхронизацией схемы). Поддомен встаёт под самый короткий домен,
которым кончается его имя, — так он всегда оказывается под корнем, — и от имени остаётся
только его часть. Настройки списка становятся общими сами только у списков с системными
свойствами, у доменов их нет — поэтому владелец переписан руками, а с ним и предел
вложенности (у прежнего списка был 1: без этого сервер не пустил бы поддомен, пока
настройки списка не сохранят).

```sql
BEGIN;
INSERT INTO infoblock_domains (id, "parentId", name, "isActive", "createdAt", "updatedAt")
SELECT DISTINCT ON (d.host) d.id, p.id,
  CASE WHEN p.id IS NULL THEN d.host ELSE left(d.host, length(d.host) - length(p.host) - 1) END,
  d."isActive", d."createdAt", d."updatedAt"
FROM domains d
LEFT JOIN LATERAL (
  SELECT p.id, p.host FROM domains p
   WHERE p.id <> d.id AND p.host <> '' AND right(d.host, length(p.host) + 1) = '.' || p.host
   ORDER BY length(p.host) LIMIT 1
) p ON true
WHERE d.host <> ''
ORDER BY d.host, d.id;
SELECT setval(pg_get_serial_sequence('infoblock_domains', 'id'),
  (SELECT COALESCE(max(id), 1) FROM infoblock_domains));
UPDATE infoblock_settings SET "userId" = 0, "maxDepth" = 2
 WHERE "listKey" = 'domains'
   AND id = (SELECT min(id) FROM infoblock_settings WHERE "listKey" = 'domains')
   AND NOT EXISTS (SELECT 1 FROM infoblock_settings WHERE "listKey" = 'domains' AND "userId" = 0);
COMMIT;
```

Локально перенесено 9 записей: `farkop.ru` с семью поддоменами (`www`, `msk`, `spb`, `ekb`,
`shop`, `opt`, `m`) и `towbar-shop.ru` отдельным доменом; номера сохранены. Локальная база
проходила и промежуточную схему (полные имена, `note`, индекс `infoblock_domains_name`) —
её привели руками: срезали хвосты, сбросили `infoblock_domains_name` и
`infoblock_domains_parent_id` (синхронизация схемы лишних индексов не удаляет), колонку
`note` удалила синхронизация. На прод промежуточная схема не попадала. Прежняя таблица
`domains` в базе осталась, код прежнего модуля — в `to_delete/` (бэкенд и фронт).

## 2026-10-03 — домены сайта отдельной сущностью, редактирование через ContentEditor

**Что сделано**

- Бэкенд: модуль `domains/` — таблица `domains` (`host`, `isMain`, `isActive`, `note`,
  `position`), эндпоинты `GET/POST/PATCH/DELETE /api/domains`, история записи и общий
  журнал раздела.
- Фронтенд: `api/domains.ts`, redux-слой доменов, `logic/domains/` (контроллер редактора,
  описание колонок и полей), `components/settings/DomainsPanel.tsx`.
- Раздел «Настройки» разделён на две части: `SiteForm` (название сайта) и `DomainsPanel`
  (таблица доменов в редакторе контента).
- Из настроек убраны `siteDomain`, `hasSubdomains` и `subdomains`; существующий домен
  перенесён в новую таблицу.

Подробности — [`docs/domains.md`](../docs/domains.md) и [`docs/settings.md`](../docs/settings.md).

**Ключевые решения**

- **Домены — записи, а не поле настроек.** Заказчик попросил редактировать их через
  ContentEditor, и это сходится с их природой: у домена есть примечание, активность и
  история правок — всё то, что в массиве строк не живёт.
- **Основной домен — строка с флагом `isMain`**, как главная страница в «Страницах»:
  создаётся сама при первом обращении к списку, не удаляется, флаг через API не меняется.
  Альтернатива — держать основной домен полем настроек, а в таблице только поддомены —
  отклонена: тогда одно и то же (имя хоста) правилось бы в двух разных местах.
- **Пустой основной домен — нормальное начальное состояние.** Список не бывает пустым, и
  поддоменам есть к чему достраивать короткие имена. Пустое имя хоста допустимо только у
  этой автоматической записи: в DTO имя обязательно.
- **Короткое имя достраивается основным доменом** (`shop` → `shop.example.com`) — перенесено
  из прежней реализации поддоменов: в разговоре поддомен называют одним словом, а в базе
  и в `server_name` нужно полное имя.
- **Принадлежность поддомена основному домену не проверяется.** Сайты нередко живут на
  нескольких разных именах; запрет мешал бы чаще, чем помогал.
- **Данные перенесены руками одним SQL** (`settings.siteDomain` → строка `isMain`,
  `settings.subdomains` → обычные строки). Файлов миграций в проекте нет, схема правится
  через `sync: alter`, который колонки просто удаляет, — значит перенос нужно было сделать
  до того, как старые колонки исчезли.

**Отступления от задания**

Задания в `planned/` не было — раздел заказан в переписке: «для редактирования доменов
использовать ContentEditor». Раскладка (сущность «домены» + таблица на странице настроек)
и набор полей карточки (имя, активность, примечание) согласованы перед реализацией.

**Не сделано**

- Смена основного домена «назначением» другой записи: сейчас главное имя меняют правкой
  карточки основного домена. Отдельное действие «сделать основным» появится, если
  понадобится.
- Привязка доменов к nginx/прод-конфигам: пока это справочник в панели, конфиги
  по нему не генерируются.

**Проверено**

- Нормализация и проверка имени — прогон `CreateDomainDto`/`UpdateDomainDto` через
  `class-transformer` + `class-validator`: ` HTTPS://Shop.Example.com/catalog ` →
  `shop.example.com`, `localhost:3400` проходит, `не домен`, `-bad-.com` и пустое имя
  отклоняются; частичное обновление (`{isActive:false}`, `{note:null}`) проходит.
- Достройка: `shop` + `example.com` → `shop.example.com`; `shop.other.com` не трогается;
  без основного домена `shop` остаётся как есть.
- Схема создана автоматически (`sync: { alter: true }`): таблица `domains` с индексами
  `domains_single_main` и `domains_user_host`; из `settings` колонки доменов удалены.
- Перенос данных: существующий `farkop.ru` лежит в `domains` как основной домен.
- Swagger отдаёт `/api/domains*`, клиент перегенерирован; `tsc --noEmit` чист на бэке и фронте.

## 2026-10-24 — мультидоменное свойство: фронтенд

Второй шаг мультидоменности: значение свойства записи своё на домен. По заданию сделан
только фронт, бэкенд — следующим заходом.

**Что сделано**

- Шторка свойства: в «Правилах» галочка «Мультидоменное» (`isMultiDomain`), с пояснением.
- Карточка записи: у мультидоменного свойства строки «домен + поле» (`drawer/DomainValues.tsx`).
  Первая — «Все домены» (её значение — для всех доменов), «Значение для домена» добавляет
  строку со своим доменом или поддоменом. Домен выбирается один раз, в выборе — деревом
  с полными адресами (`ekb.farkop.ru`), выключенный помечен. Ввод значения в строке —
  тот же, что у обычного поля, включая множественное: он вынесен из `RecordFields`
  в `drawer/FieldInput.tsx`.
- Формат значения — `[{ domainId: null | номер, value }]`, общее первым
  (`logic/domains/domainValues.ts`); домены для выбора — `logic/domains/useDomainOptions.ts`
  через `loadEditorDomainsThunk`, читаются при каждом показе карточки, как записи привязки.
- Таблица: в ячейке общее значение и «+N доменов»; фильтр ищет по значениям всех доменов.

**Ключевые решения**

- **Общее значение — строка с `domainId: null`, а не отдельное поле.** Так значение
  свойства остаётся одним списком, а сайту достаточно правила «своё, иначе общее».
- **Мультидоменность — флаг свойства, а не раздела**: работает в любом списке нового
  редактора, раздел про неё не знает.
- **Старое значение становится общим.** Включили флаг у свойства со значениями — они
  читаются как «Все домены», ничего не теряется.
- Строку без домена или без значения не отправляем: её добавили, пока думают.
  Обязательность — по общему значению.

**Не сделано**

- **Бэкенд** — в этом заходе. Флаг сделан следующей записью, значения — ещё нет.

**Проверено** — `tsc --noEmit` на фронте. Тело запроса — прогоном `record.ts` в node:
старое значение становится общим, строки без домена или значения отбрасываются, без
правок ничего не уходит, обязательность ловит пустое общее. В браузере (флаг временно
включён свойству в коде, запись не сохранялась): «Все домены» с прежним значением,
добавление строки, выбор `ekb.farkop.ru` и значения, во второй строке `ekb` в выборе
уже нет; галочка в шторке свойства, снятая обратно, не делает свойство изменённым.

## 2026-10-24 — мультидоменное свойство: флаг на бэкенде

**Что сделано**

- Колонка `infoblock_settings_properties.isMultiDomain` (`BOOLEAN NOT NULL DEFAULT false`,
  авто-миграция), поле в `PropertyDef`, нормализации и DTO свойства; сервис пишет его
  при создании и правке и отдаёт в списке. Системные свойства — с `false`.
- В DTO флаг необязательный: тело без него не ломается, а правка без него оставляет
  флаг как был (`{ ...before, ...dto }`).
- Фронт: флаг уходит в теле свойства всегда (`property.ts`) — без `false` его не выключить;
  в таблице свойств он виден в колонке «Правила» («мультидоменное»). Клиент API
  перегенерирован.
- Тест нормализации: флаг у любого типа, не присланный — «выключено».

**Ключевые решения**

- **Колонкой, а не в `params`.** `params` — параметры типа (форматы, столбцы), а это
  правило любого свойства, как `required` и `multiple`; по нему же будут разбирать
  значения.

**Не сделано**

- **Значения по доменам.** API значений их пока не принимает: `[{ domainId, value }]`
  для строки или списка — значение не того типа, и сервер отклоняет весь запрос значений
  (порчи данных нет, карточка говорит «Запись сохранена, а значения свойств — нет»).
  Следующий шаг — хранить домен в строке `infoblock_values` и разбирать такие значения.

**Проверено** — `npm test -- settings` (54 теста), `tsc --noEmit` на бэке и фронте;
колонка появилась в базе. В браузере: у TESTSETSET включили «Мультидоменное» и сохранили
(раньше — `property isMultiDomain should not exist`), после перезагрузки флаг на месте,
в «Правилах» — «мультидоменное», в карточке записи — строки доменов. Через API:
`PATCH { isMultiDomain: false }` выключает, `true` — включает обратно.

## 2026-10-24 — мультидоменное поле: вид в карточке

Прежний вид — серый выбор «Все домены» перед каждым полем и большая кнопка под каждым —
сливался в кучу. Варианты собраны макетами на холсте (вариант A — поле как обычное,
B — вкладки доменов, C — один домен на всю карточку); выбран A с доработкой.

- Поле целиком в светлой рамке (`colorFillAlter`, `colorBorderSecondary`,
  `borderRadiusLG` из `theme.useToken()` — своих цветов нет), строки сеткой
  «домен 200px | значение | убрать», первая подписана «Все домены» текстом, а не
  закрытым выбором.
- Внизу рамки пунктирная кнопка на всю ширину — «Добавить уникальное значение для домена».
- У подписи поля значок глобуса; подпись опущена на отступ рамки, чтобы стоять вровень
  с первой строкой.

## 2026-10-24 — мультидоменное поле таблицей и «для всех, кроме»

По макетам на холсте (ряд D) выбран D1 — значения маленькой таблицей.

- `DomainValues` — таблица в рамке: шапка «Домен | Значение» (`colorFillAlter`), строки
  через `colorBorderSecondary`, в подвале кнопка-ссылка «Добавить уникальное значение
  для домена». Подгонка отступа подписи из прошлого вида убрана: подпись стоит вровень
  с шапкой.
- **«Кроме»** у строки «Все домены» — `Select mode="multiple"` с `prefix="кроме"`:
  домены, на которые общее значение не распространяется. В значении — `exceptDomainIds`
  у общего элемента (`logic/domains/domainValues.ts`). Домен занят либо своей строкой,
  либо исключением (`freeDomainOptions` принимает занятые и свои номера); номер со своим
  значением из исключений убирается при сборке тела (`record.ts`).
- Под общим значением при исключениях — «На … значения нет» (`domainLabels`).

**Решения**

- Исключение — отдельный список у общего, а не «пустое своё значение»: пустые строки
  доменов карточка считает недописанными и не отправляет, а «здесь значения нет» — это
  осознанный выбор, его видно рядом с общим значением.

**Проверено** — `tsc --noEmit`; тело запроса прогоном `record.ts` в node: исключения
доходят, без правок ничего не уходит, домен со своим значением из исключений выпадает.
В браузере не смотрел — сессия панели во встроенном браузере истекла. Бэкенд значений
по доменам (и `exceptDomainIds`) ещё не сделан.

## 2026-10-24 — группы доменов у уникального значения, «кроме» тем же выбором, описание

- **Несколько доменов на одно значение.** Строка уникального значения выбирает домены
  множественным `Select`: в значении `domainIds: number[]` вместо одного `domainId`;
  общее — `domainIds: null`. Бэкенда значений ещё нет, поэтому формат поменян без
  переходного слоя. В таблице списка «+N доменов» считает домены во всех группах
  (`ownDomainCount`).
- **«Кроме» — тот же выбор, что у остальных строк.** Мелкий селектор под подписью
  «Все домены» убран: в первой строке обычный множественный `Select` колонки «Домены»,
  пустой подписан «Все домены», с исключениями — приставка «Все, кроме»; длинный список
  сворачивается в «+N» (`maxTagCount="responsive"`). Все строки одной высоты.
- **Описание под общим значением** — всегда, а не только при исключениях: как сделать
  «для всех, кроме» и что будет на исключённых доменах.
- Колонка доменов — 260px, заголовок «Домены».

**Проверено** — `tsc --noEmit`; тело запроса прогоном `record.ts` в node: группы доходят,
строки без доменов или без значения отброшены, домен с уникальным значением выпадает
из исключений, без правок ничего не уходит, обязательность — по общему. Макет D1 на холсте
обновлён под этот вид. В браузере не смотрел — сессия панели во встроенном браузере истекла.

## 2026-10-24 — домен из «кроме» можно выбрать и в уникальном значении

Раньше домен, отмеченный в «кроме», пропадал из выбора уникальных строк (и наоборот):
считалось, что исключать домен с уникальным значением незачем. Заказчик ждал обычного
сценария «всем, кроме msk и spb, а msk — своё», и запрет его ломал. Теперь:

- в «кроме» — все домены; в строке уникального значения — все, кроме занятых другими
  уникальными строками (уникальное значение у домена по-прежнему одно);
- исключения уходят как выбраны — раньше карточка убирала из них домены с уникальным
  значением, и после сохранения домен молча пропадал бы из «кроме»;
- смысл: уникальное сильнее, исключение срабатывает на доменах без уникального.

**Проверено** — `tsc --noEmit`.

## 2026-10-24 — мультидоменные значения: бэкенд

**Что сделано**

- `infoblock_values`: колонки `domainIds INTEGER[]` (null — общее значение, иначе домены
  уникального) и `exceptDomainIds INTEGER[]` (у строк общего), GIN-индекс по `domainIds`.
  Группы лежат теми же строками «строка на значение», `sort` сквозной по группам.
- `property.ts`: `DomainGroup`, `normalizeDomainGroups` — каждая группа проверяется как
  обычное значение свойства; обязательность по общему; недописанные группы отбрасываются;
  домен в двух уникальных группах — ошибка; значение, сохранённое до флага, — общее.
  `plainValues` — значения всех групп одним списком для проверки файлов, блоков и привязок;
  `referencedDomainIds` — домены значения для проверки, что они есть.
- `PropertyValuesService`: `valueRows`/`valuesMap` раскладывают группы по строкам и
  собирают обратно; при выключенном флаге читается только общее; `assertDomains` (400
  «Домен не найден»); `forgetDomain` — удалённый домен уходит из групп и исключений,
  пустые группы удаляются. Зовёт его `DomainsService.remove`.
- Фронт не менялся: он уже слал этот формат; клиент API перегенерирован без изменений.

**Решения**

- **Колонки-массивы в `infoblock_values`, а не отдельная таблица групп.** Значение
  остаётся строкой на значение — по нему ищут и сортируют, — а «значение для домена X»
  это `X = ANY(domainIds)` под GIN-индексом. Цена — нет внешнего ключа на домен, поэтому
  удаление домена чистит значения само.
- **Исключения — при строках общего значения**, поэтому без общего не сохраняются:
  на домене без уникального значения его и так нет, исключать нечего. Отдельная таблица
  ради этого случая не оправдана.
- Выключение флага ничего не стирает: строки уникальных значений просто не читаются.

**Проверено** — `npm test` (87 тестов, из них новые: 6 на разбор групп в `settings.spec.ts`,
4 на раскладку по строкам в `values/property-values.spec.ts`); `tsc --noEmit` на бэке
и фронте; колонки и индекс появились в базе; SQL `forgetDomain` — на копии таблицы
во временной транзакции (откат). Сквозное сохранение из карточки не прогонял: сессия
панели во встроенном браузере истекла.
