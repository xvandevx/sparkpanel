# Внешнее API

## 2026-10-30 — `/api/v1` по ключу, ключи и документация в «Настройки → API»

**Что сделано**

- Бэкенд, модуль `external-api/`:
  - ключи — таблица `api_keys` (`userId` создателя, название, SHA-256 ключа, последние
    4 символа, время последнего запроса); `GET`/`POST /api/external-api/keys`,
    `DELETE /api/external-api/keys/:id`, только root;
  - внешнее API `/api/v1` по заголовку `X-Api-Key` (`ApiKeyGuard`): у каждого списка
    `items`, `items/{idOrCode}`, `properties`, `facets`; списки — `/pages`,
    `/contents/{код типа}`, `/catalog/products`, `/catalog/categories`, `/domains`;
    плюс `GET /contents`, `/pages/by-url`, `/domains/by-host`;
  - спецификация OpenAPI 3.1, собранная из настроек списков, —
    `GET /api/v1/openapi.json` (по ключу) и `GET /api/external-api/openapi` (панели, по JWT).
- Фронт: пункт «API» в подменю «Настройки» (`/admin/settings/api`, только root),
  `components/settings/api/` + `logic/externalApi/`: вкладка «Доступ» (адрес, правила,
  ключи; полный ключ — один раз в окне создания), вкладка «Документация» —
  встроенный Scalar (`@scalar/api-reference-react` 0.9.81).
- `RootOnlyGuard` перенесён из `backups/` в `common/` — им закрыты и копии сайта,
  и ключи. В `FilesService` — `findByIds` (файлы с адресами, без привязок).

Подробности — [`docs/external-api.md`](../docs/external-api.md).

**Ключевые решения**

- **Документацию не пишем руками.** Сначала на холсте рисовались свои страницы методов
  на каждый раздел; заказчик спросил, зачем велосипед, если есть Swagger. Обычный
  Swagger из декораторов Nest не подходит: свойства списков заводят в панели, и он
  показал бы `properties: object`. Поэтому сервер собирает спецификацию сам из настроек
  списков (`openapi-spec.ts`, чистая функция): схема записи — с кодами свойств, «Список» —
  `enum` кодов вариантов, у каждого типа контента — свои пути. Показывает её Scalar —
  современнее Swagger UI, с примерами запросов и «Test Request».
- **Один набор методов на любой список**, а не ручки на раздел: сайт строит фильтр
  каталога по `properties` и `facets` без знания кода сайта.
- **Отбор — общий `pageRecords`** (`records-page.ts`), как у таблицы редактора: поиск,
  фильтр и сортировка одинаковы в панели и в API. `filter[код]` переводится в поля этого
  отбора (`external-values.ts`).
- **Мультидоменное значение выбирается до отбора** — фильтр на домене ищет по значениям
  этого домена, а не по всем сразу.
- **Ключ читает данные создателя** (`api_keys.userId`) — правило изоляции по `userId`
  то же, что у JWT. Хэш — SHA-256, а не bcrypt: ключ случайный и длинный, а найти его
  нужно по хэшу одним запросом.
- **Фасет свойства не учитывает собственный фильтр** — иначе после выбора Bosch
  в «Бренде» остался бы один Bosch.
- **Внешнее API не входит в Swagger панели** (`@ApiExcludeController`): иначе
  `generate-api` тащил бы его в клиент панели.
- **Меню документации — группы «Сайт» (страницы, домены), «Контент», «Каталог».**
  Сначала у каждого раздела была своя группа, и у «Страниц» и «Доменов» пункт повторял
  её имя («Страницы → Страницы»); а тег вне групп Scalar не показывает вовсе. Пункты
  в группе — без приставки (`x-displayName`: «Новости», а не «Контент · Новости»);
  имя тега с приставкой осталось — оно уникально, даже если тип контента назовут «Товары».
- **Scalar — без облачных функций**: чат «Ask AI» и MCP выключены (спецификация сайта
  ушла бы в облако Scalar), панель разработчика скрыта. Справочник прокручивается своей
  областью — в общей прокрутке страницы его меню уезжало вверх.

**Отступления от задания**

- Блок «Разделы в API» с переключателями и выбор разделов на ключ убраны по просьбе
  заказчика: ключ видит страницы, контент, каталог и домены целиком.
- Схема «Фильтр каталога» как отдельное руководство не делалась (заказчик убрал её
  с холста); правила фильтра — во введении спецификации.

**Не сделано**

- Лимит частоты (429), запись через API, файлы, пользователи, роли, хранилища и формы
  наружу не отдаются.
- Отбор в памяти, как и у таблицы редактора: на больших списках понадобится SQL.

**Проверено**

- `npm test -- external-values` — 15 тестов: значение домена, значения по типам,
  разбор `filter[…]`, фасеты.
- Вручную через curl на живых данных: без ключа и с отозванным — 401; `/contents`,
  `items` с фильтром по «Списку» и привязке, `facets` (счётчики с учётом остальных
  фильтров), запись по коду, `/pages/by-url?url=/`, `/domains/items`; ошибки — неизвестное
  свойство и сортировка (400), список и запись (404), домен (400).
- `openapi.json`: 47 путей, группы меню «Сайт / Контент / Каталог», у товаров —
  схема с кодами свойств; в Swagger панели путей `/v1` нет.
- В браузере: создание ключа (окно с ключом один раз), список ключей, «Документация» —
  Scalar со стилями, меню и примеры запросов. Тестовые ключи после проверки отозваны.

## 2026-11-01 — раскрытие связей `expand`

**Что сделано**

- `GET …/items` и `GET …/items/{idOrCode}` принимают `expand=код,код` — коды
  свойств-привязок. У них вместо `{ list, id, name }` приходит связанная запись целиком,
  как её отдаёт `items/{id}` её списка, для того же `domain`; привязка к типу контента —
  типом, как в `GET /contents`.
- Бэкенд, `external-api/`: разбор и проверка — `parseExpand` и `isExpandable`
  (`external-values.ts`, чистые); раскрытые записи — поле `expanded` у `ValueContext`,
  `apiValue` берёт запись оттуда, а нет её — отдаёт `Link`. Чтение — `expandedOf`
  и `linkedRecords` в сервисе; в DTO — `expand` у `ExternalItemsQueryDto` и новый
  `ExternalItemQueryDto` для записи.
- Спецификация (`openapi-spec.ts`): параметр `expand` с перечнем кодов у обоих методов
  списка, схема раскрываемой привязки — `Link` или запись её списка, строка во введении.

Подробности — [`docs/external-api.md`](../docs/external-api.md#api).

**Ключевые решения**

- **Один уровень.** Привязки внутри раскрытой записи остаются `Link`: в коде это просто
  то, что `contextOf` для связанных записей зовут без `expand`. Вложенное раскрытие даром
  не выходит — синтаксис пути, предел глубины, защита от кольца товар → категория → товар
  и лишние чтения целых списков на каждый уровень. Нужно глубже — второй запрос.
- **Пачкой:** на запрос — одно чтение на список-источник (тем же `load`, что у `items`),
  из него берутся только записи, на которые ссылается страница ответа.
- **Не видна — значит `Link`.** Удалённая, выключенная или не опубликованная связанная
  запись приходит `{ list, id, name }` — так же, как без `expand` (у удалённой `name: null`).
  Отдать её целиком нельзя: API показывает только активные опубликованные записи.
- **Раскрываются только привязки к спискам API и к типам контента.** Привязку к ролям
  или пользователям раскрыть — значит отдать наружу то, чего API не показывает; такой код
  в `expand` — 400, и в перечне спецификации его нет.
- **Тип контента — в виде `GET /contents`** (`{ code, name, path, total }`): своего
  `items/{id}` у типов нет, а `path` — то, что сайту нужно дальше.
- **`expand` — строка через запятую**, без повтора параметра (`expand=a&expand=b` — 400
  от валидации DTO): одна форма проще, и спецификация описывает именно её
  (`style: form`, `explode: false`).
- **`pages/by-url` и `domains/by-host` без `expand`** — в задании только `items`
  и `items/{idOrCode}`; добавить — передать `expand` в `one()`, как у `item`.

**Проверено**

- `npm test` — 170 тестов, из них в `external-values` 21 (+6): `parseExpand` (коды через
  запятую, повторы, пусто, 400 на неизвестный код, не привязку и привязку к списку
  не из API) и `apiValue` с раскрытыми записями (массив в прежнем порядке, одиночная —
  объектом, нет записи — `Link`, свойство не из `expand` — `Link`).
- Вручную через curl на живых данных, с временными свойствами товаров (одиночная
  привязка к «Уникальным описаниям», привязка к типу контента), потом удалены:
  - товар 108 без `expand` и с `expand=categories,descr,ctype,mark`: множественные —
    массивами записей с файлом-картинкой категории, одиночная — объектом, тип — типом;
  - мультидоменное `kueue` в раскрытой записи для `domain` пусто / ekb / msk совпало
    с `items/9` самого списка (`334` / `112` / `334`);
  - `items?expand=categories,descr&search=sportage` — 9 записей, раскрыто у каждой;
  - глубина и удалённая запись: у страницы `related` → товары 108, временный (удалён),
    106 — первый и третий целиком, со своими `categories` в виде `Link`, удалённый —
    `{ list, id: 112, name: null }`, порядок прежний;
  - 400: `expand=nope`, `expand=color` (не привязка), `expand=categories,nope`, у записи —
    тоже; пустой `expand` — как без него; 404 у несуществующей записи с `expand`;
    у `facets` и `by-url` параметра нет — 400 от валидации.
- `openapi.json`: `expand` у `/pages/items*` (`related`) и `/catalog/products/items*`;
  в «Настройки → API → Документация» Scalar показывает у метода `expand` с вариантами.
  Тестовый ключ отозван.

## 2026-11-01 — права ключей, внешний ID записи и запись через `/api/v1`

Задание — `planned/external-api-write.md` (удалено после сдачи).

**Что сделано**

- Миграция `0002-external-write`: `infoblock_records.externalId` + частичный уникальный
  индекс `infoblock_records_external_id (settingsId, externalId) WHERE externalId IS NOT NULL`;
  `api_keys.isWritable` (по умолчанию `false` — старые ключи только читают) и
  `api_keys.writeLists TEXT[]` (null — все списки); индексы по `code` у страниц, товаров,
  категорий и элементов типов контента (`(contentId, code)`).
- Права ключа: `POST /api/external-api/keys` принимает `isWritable` и `writeLists`,
  `GET /api/external-api/lists` — списки для выбора; после создания права не меняются.
  Проверка — `keys/write-access.ts` (`canWrite`), 403 «Ключу не разрешена запись в «…»».
- Внешний ID: пишет его маршрут значений (`PATCH …/values` с `externalId`) только при `via`
  в JWT, 409 при повторе; в журнал — ключом `externalId`; наружу — полем записи
  у `RecordsService.rows` (страница таблицы, внешнее API, MCP). Поиск по нему —
  `PropertyValuesService.recordIdByExternalId`. В копии списка переносится.
- Запись `/api/v1` (`external-api/write/`): `POST …/items`, `PATCH`/`DELETE …/items/{idOrCode}`,
  `PUT`/`DELETE …/items/external/{externalId}`, `POST …/items/batch` (до 500),
  `GET …/items/external/{externalId}`. Тело — `{ fields, properties }`, свойства по кодам
  (`write-values.ts`), родитель — и `parentExternalId`. Предел тела `/api/v1` — 25 МБ.
- MCP: `save_record` принимает `fields.externalId` (сразу, мимо черновика).
- Спецификация: методы записи у каждого списка с пометкой «Нужен ключ с правом записи»
  и значком «Запись», схемы тел `<Схема>Input` / `<Схема>Upsert`, `externalId` в записи.
- Фронт: окно «Создать ключ» с правами (чтение всегда, запись — все или отмеченные списки),
  колонка «Права» в таблице ключей, правила записи на вкладке «Доступ»; «Внешний ID»
  на просмотр внизу вкладки «Запись» карточки и подпись в журнале.
- `PanelClient` перенесён из `mcp/` в `common/` — им пишут и MCP, и внешнее API.

**Ключевые решения**

- **Пишем маршрутами панели, как MCP**, а не сервисами разделов: DTO, проверки разделов
  (код, адрес страницы, глубина дерева, защищённые записи), проверки значений и журнал —
  те же самые, без второй реализации. Журнал: «Ivan · API «ключ»». Цена — поля и свойства
  идут двумя транзакциями. Задание просит транзакцию на запись; сквозная транзакция
  потребовала бы протащить `transaction` через пять разделов и проверять поля своим DTO.
  Выбрано с заказчиком: **как MCP плюс откат** — всё, что проверяется до записи
  (права, поля, коды свойств и вариантов, привязки, занятый внешний ID, родитель),
  проверяется до неё; не легли свойства — созданная запись удаляется, у правленой
  возвращаются прежние поля. Внешний ID пишется в одной транзакции со свойствами,
  поэтому запись без него не остаётся и дубля при повторе нет.
- **Внешний ID — в `infoblock_records`**, а не колонкой в таблице каждого раздела: строка
  общая на все списки, уходит вместе с записью (все разделы стирают её при удалении),
  индекс один. Согласовано с заказчиком вместе с миграцией.
- **Привязка в теле**: число — номер, строка — код, `{ "externalId": "…" }` — внешний ID
  (строку не различить: код это или внешний ID). Принимается и то, что отдаёт чтение.
- **Поиск записи — запросом к базе** по номеру, коду (новые индексы) и внешнему ID; таблицы
  разделов — в `record-lookup.service.ts`.
- Поля, равные сохранённому, в раздел не уходят: часовой обмен, где почти ничего
  не поменялось, не дёргает маршрут раздела зря.

**Отступления от задания**

- «У каждой записи своя транзакция» — не одна транзакция БД, а две с ручным откатом (выше).
- Найден и исправлен рост времени записи со списком, не связанный с API напрямую:
  `InfoblockPropertiesService.filledOf` (признак «у свойства есть значения», читается
  при каждом сохранении значений) выбирал все значения списка через `GROUP BY` — 48 мс
  на 50 тыс. товаров с 20 свойствами. Теперь `EXISTS` по индексу — 0,8 мс.

**Не сделано**

- Создание элементов типов контента и категорий маршрутами разделов по-прежнему читает
  все записи списка (проверка глубины дерева), проверка привязок — целевой список целиком.
  Для деревьев в десятки тысяч записей это заметно; лечится отбором в базе — отдельная
  задача «Отбор записей в базе» (`webSite/headless/README.md`).
- Чтение `/api/v1` (в том числе `items/external/{externalId}`) по-прежнему читает список
  целиком — вне задания.

**Проверено**

- Тесты (`npm test`, 201): `keys/write-access.spec.ts` — ключ только на чтение не пишет,
  ключ с отмеченными списками пишет только в них; `write/external-write.spec.ts` (на
  поддельной панели) — upsert создаёт и повторно правит, дерево через `parentExternalId`,

  `property-values.spec.ts` — `isExternal` ключ пишет, из панели нельзя, внешний ID из

- Вживую на локальном стеке: 403 у ключа на чтение и у ключа не в свой список; upsert

## 2026-11-03 — фильтр и фасеты по привязке за доли секунды

Задание — `planned/content-link-filter-speed.md` (удалено после сдачи): на cms.farkop.ru
`facets?filter[car]=922` и `items?filter[car]=922` по 7474 товарам отвечали 9–10 с.

**Что нашлось.** Отбор в памяти тут ни при чём — на него уходили миллисекунды. 95% времени
`items`, `facets` и даже `items/{id}` — `PropertyValuesService.findAll`: **все значения
всех записей списка** (описания, SEO-тексты, привязки) на каждый запрос, каждое — моделью
Sequelize, со сборкой массивов копированием (`[...old, row]` — квадрат на запись
с сотнями привязок). Локально на 7,5 тыс. товаров с описанием и SEO — ~0,9 с на любой
запрос; на проде данных больше, а процессор медленнее.

**Что сделано**

- Миграция `0003-link-values-index`: индекс `infoblock_values_property_link`
  `("propertyId", (json->>'recordId'))`. `PropertyValuesService.linkedRecordIds` — ключи
  записей, у которых свойство указывает на выбранные записи, запросом по нему.
- `PropertyValuesService.findSome(listKey, recordIds, propertyIds)` — значения части
  записей и части свойств; общее чтение (`read`) — без моделей (`raw`), только нужные
  колонки, весь список — подзапросом по `settingsId`, а не перечнем в 10 тыс. номеров
  (он ещё и попадал в лог SQL на каждый запрос).
- `ExternalApiService`: `load` больше не читает значений. `items` — привязки отбираются
  в базе (`linkMatches` + `withLinks`), значения на отбор — только свойств фильтра
  и сортировки у оставшихся записей, на ответ — только записей страницы. `facets` —
  у каждого фасета свои записи (без его фильтра) и значения только его свойства и свойств
  остальных фильтров. `items/{id}`, `items/external/…`, `pages/by-url`, раскрытые
  привязки — значения только показываемых записей. `ApiFilter.linkIds` — номера записей
  привязки из `filter[…]`.
- Мелочи на горячем пути: `valuesMap` и группировка в `read` — `push` вместо копирования
  массива, `uniqueBy` считает ключ (`JSON.stringify`) один раз, `facetOf` — циклом
  вместо `flatMap`.

**Ключевые решения**

- **Сужение в базе, точный отбор — прежний.** Запрос по индексу находит записи с привязкой
  в любом домене; `pageRecords` потом отбирает по значениям для `domain`, как раньше.
  Так поведение не поменялось ни в одном случае (мультидоменные, черновики, выключенные),
  а второй реализации отбора в SQL нет.
- **Фасеты не переписаны на SQL-агрегаты** (`GROUP BY json->>'recordId'`): у них свои
  правила (значения по текущим настройкам, мультидоменные, поиск по полям раздела),
  и SQL-версия разошлась бы с `pageRecords` на краях. Фасет привязки по всему списку
  (свой фильтр он не учитывает) по-прежнему читает значения этого свойства у всех
  записей — это и есть основная его цена.
- Индекс без `listKey`: у свойства-привязки список-источник один, его условие идёт
  в запросе вторым.

**Отступления от задания**

- Чтение значений ускорилось для всех: таблица редактора (`GET /api/infoblocks/records/…`)
  на 7,5 тыс. товаров — 0,84 → 0,39 с, карточка товара во внешнем API — ~1 с → 0,1 с.

**Не сделано**

- Записи раздела (`RecordsService.rows`) по-прежнему читаются целиком моделями: на 10 тыс.
  товаров 50–80 мс (под нагрузкой до 200). Следующий шаг, если понадобится, — `raw`
  в `findAll` разделов.
- Логирование SQL Sequelize включено во всех окружениях (`logging` в `app.module.ts`
  не задан) — каждый запрос пишется в stdout.
