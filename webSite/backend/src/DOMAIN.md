# Доменная модель SparkPanel

> Здесь описывается, из каких сущностей состоит домен админ-панели, как они связаны
> и какие инварианты обязаны соблюдаться в сервисах. Подробности по модулям — в `docs/`.

## Формат описания сущности

Для каждой сущности:

- **Назначение** — что это в предметной области, одной фразой.
- **Поля** — имя, тип, обязательность, что означает.
- **Связи** — на кого ссылается (`parentId`, `ownerId`, …) и что происходит при удалении.
- **Инварианты** — правила, которые сервис обязан удерживать (уникальность, допустимые
  переходы статусов, права).

## Общие правила (действуют для всех сущностей)

- PK — `SERIAL` (порядковый номер): идентификатор виден в админке и в адресе страницы,
  и читаемый номер там удобнее случайного UUID. `userId` — `INTEGER`, ссылка на `users`.
- Мультитенантность: данные всех пользователей лежат в общих таблицах, изоляция — по `userId`.
  В каждом `where` — фильтр по `userId`; в update/delete — по `id` И `userId`.
- Деревья хранятся **плоско**: `parentId` + `position`, без вложенного `children[]`.
  Сборка дерева — задача фронта (`logic/`), не БД. Производные от дерева значения
  (адрес страницы из кодов родителей) не хранятся — иначе перенос ветки заставлял бы
  переписывать всё поддерево.
- Индексы на `userId` и на все FK.
- Модели не импортируют друг друга (циклы ломают Swagger-схемы) — связь описывается на
  стороне ребёнка через `@BelongsTo(() => Parent)`.
- FK без `ON DELETE CASCADE` ⇒ удаление родителя сносит детей **в транзакции**.

## Сущности

### `users` — пользователи панели

- **Назначение:** учётные записи, под которыми входят в SparkPanel. Раздел `/admin/users`.
- **Поля:** `id` (serial), `email` (уникальный, он же логин), `passwordHash` (bcrypt, наружу
  не отдаётся), `name` (необязательное), `role` (`root` | `user` — только признак главного
  администратора), `isActive`, `passwordChangedAt` (когда пароль меняли в последний раз).
- **Роль из справочника** (`infoblock_roles`) — не колонка, а системное свойство «Роль»
  списка `users`: привязка к контенту, значение в `infoblock_values`.
- **Исключение из общего правила:** `userId` здесь нет. Учётные записи не принадлежат
  тенанту — они его и определяют, и изоляции по `userId` для них не существует. Её место
  занимает проверка роли: список видят все авторизованные, правит только `root`.
- **Инварианты:**
  - `root` в системе **ровно один**. Гарантия — частичный уникальный индекс
    `users_single_root` (`UNIQUE (role) WHERE role = 'root'`), а не только проверка в сервисе:
    эндпоинт первичной настройки публичный, и две параллельные попытки прошли бы проверку обе.
  - Создаётся root только пока его нет — через `POST /api/auth/setup`; потом эндпоинт отвечает 409.
  - Неактивный (`isActive: false`) пользователь не может войти и не проходит `/auth/me`.
    Главного администратора отключить нельзя: входить после этого было бы некому.
  - `role` через API не меняется вообще — ни при создании, ни при правке. Роль из
    справочника меняется значением свойства, и только руками `root`.
  - Учётные записи **не удаляются**: запись владеет данными тенанта (страницы, мета,
    настройки, авторство в журнале), а `userId` в тех таблицах — колонка с индексом, без
    внешнего ключа, так что удаление молча оставило бы сирот. Доступ забирают `isActive`.
  - `passwordChangedAt` — единственное, что о пароле попадает в журнал изменений:
    сам пароль хранится хэшем и сравнивать «было/стало» нечего.

### `infoblock_roles` — роли пользователей

- **Назначение:** справочник ролей («Редактор», «SEO-специалист»). Список редактора
  контента с ключом `roles`, раздел `/admin/users/roles`. Модуль `infoblocks/roles/`.
- **Поля:** `id`, `name`, `isActive`, `sort`. Кода нет — роль назначают по номеру;
  описание, если понадобится, — свойство списка.
- **Владельца нет** — роли общие на панель, как и учётные записи; правит только `root`.
- **Связи:** кому роль назначена, здесь не хранится — это значения системного свойства
  «Роль» (`{ listKey: 'roles', recordId }` в `infoblock_values.json`).
- **Инварианты:**
  - Код уникален — по нему будут проверять права.
  - Роль, на которую ведёт хоть одна привязка к контенту, не удаляется (наружу —
    `isBlocked`): у пользователей осталась бы ссылка в никуда.

### `infoblock_products_categories` / `infoblock_products` — категории и товары

- **Назначение:** каталог — дерево категорий и товары. Списки редактора контента
  с ключами `product-categories` и `products`, разделы `/admin/products/categories`
  и `/admin/products`. Модули `infoblocks/products/categories/` и `infoblocks/products/`.
- **Поля категории:** `id`, `userId`, `parentId` (null — корень), `code` (пустой — без кода),
  `name`, `isActive`. **Поля товара:** `id`, `userId`, `code`, `name`, `isActive`.
  Цена, описание и прочее — свойства списка, не колонки.
- **Связи:** категории товара — не колонка и не таблица связей, а значения системного
  свойства «Категории» (`products`, код `categories`, множественное;
  `{ listKey: 'product-categories', recordId }` в `infoblock_values.json`).
- **Инварианты:**
  - Категория, на которую ведёт хоть одна привязка, не удаляется (наружу — `isBlocked`);
    с вложенными категориями — тоже. Удаляется только пустая.
  - Категорию нельзя перенести в собственную ветку и глубже «Уровней вложенности»
    списка `product-categories` (по умолчанию без предела).
  - Удаление товара или категории стирает значения их собственных свойств — у товара
    это и привязки к категориям.

### `infoblock_contents` / `infoblock_contents_items` — типы контента и их элементы

- **Назначение:** раздел «Контент» — типы («Новости», «Статьи») и элементы каждого типа.
  Списки редактора контента с ключами `contents` и `content-items.<contentId>`,
  разделы `/admin/contents` и `/admin/contents/<contentId>`. Модуль `infoblocks/contents/`
  (типы) и вложенный `infoblocks/contents/items/` (элементы).
- **Поля типа:** `id`, `userId`, `parentId` (null — корень), `code` (обязателен), `name`,
  `isActive`. **Поля элемента:** `id`, `userId`, `contentId`, `parentId` (элемент того же
  типа), `code`, `name`, `isActive`. Текст, дата и прочее — свойства списка, у элементов
  каждого типа свои.
- **Связи:** название и код типа — имя и код списка его элементов в `infoblock_settings`
  (`listKey = content-items.<id>`); пишет их сервис типов при каждой правке типа.
- **Инварианты:**
  - Тип с элементами или вложенными типами не удаляется (наружу — `isBlocked`);
    элемент с вложенными — тоже.
  - Код типа уникален среди кодов списков пользователя (индекс настроек) — иначе 409.
  - Не в свою ветку и не глубже «Уровней вложенности» своего списка.
  - Элемент адресуется вместе с типом (`/infoblocks/contents/:contentId/items/:id`) и
    фильтруется по `userId` и `contentId`.
  - Удаление типа или элемента стирает значения их собственных свойств.

### `infoblock_forms` / `infoblock_forms_fields` — формы обратной связи и их поля

- **Назначение:** формы, которые панель отдаёт сайту, и вопросы посетителю. Списки
  редактора контента с ключами `forms` и `form-fields`, разделы `/admin/forms`
  и `/admin/forms/fields`. Модули `infoblocks/forms/` и `infoblocks/forms/fields/`.
- **Поля формы:** `id`, `code` (уникальный — `infoblock_forms_code`), `name`, `isActive`.
  Получатель заявок и прочее — свойства списка.
- **Поля поля:** `id`, `code` (имя значения в заявке; уникальный — `infoblock_forms_fields_code`),
  `name`, `isActive`. Плейсхолдер — системное свойство «Плейсхолдер» (`form-fields`,
  код `placeholder`, строка); тип, обязательность и прочее — свойства списка.
- **Владельца нет** — формы и поля общие на сайт, оба списка `isShared`: их настройки
  и свойства одни на всех (владелец `0`).
- **Связи:** поле форме не принадлежит. Поля формы — значения системного свойства
  «Поля» (`forms`, код `fields`, множественное; `{ listKey: 'form-fields', recordId }`
  в `infoblock_values.json`), порядок — `sort` значений. Одно поле — в любом числе форм.
- **Инварианты:**
  - Код формы и код поля уникальны на сайт (индексы, наружу 409). Код поля —
    не в пределах формы: поле подключают к разным формам.
  - Поле, на которое ведёт хоть одна привязка, не удаляется (`isBlocked`); то же у формы,
    выбранной в чьей-то привязке.
  - Удаление формы стирает значения её свойств, в том числе привязки к полям.
- Старые таблицы `forms` и `form_fields` (схема из `to_delete/forms/`) не используются,
  но и не тронуты.

### `pages` — страницы сайта

- **Назначение:** дерево страниц, которые панель отдаёт сайту. Раздел `/admin/pages`.
- **Поля:** `id`, `userId`, `parentId` (`null` — страница в корне сайта), `sort`,
  `code` (сегмент адреса), `name` (для админки), `isActive`. Текста и прочих полей
  в модели нет: их заводят свойствами списка, значения лежат
  в `infoblock_settings_values`.
  Всё, что сверх этого — мета, тип страницы и прочее, — задаётся **свойствами списка**
  (`list_settings`), а не колонками: страница остаётся обычной записью редактора контента.
- **Связи:** `parentId` → `pages`. Удаление родителя уносит всё поддерево в транзакции.
- **Инварианты:**
  - Страница без родителя — главная. **Их может быть несколько**: по одной на домен,
    на A/B-тест и т.п. Отдельного признака «главная» нет и не нужно — его роль играет
    пустой `parentId`.
  - Код уникален среди соседей (`pages_sibling_code`): иначе две страницы в одной ветке
    получили бы один адрес. На корневые это не распространяется (Postgres считает `NULL`
    различными) — и так и задумано: главных рядом несколько, их разводит домен.
  - Пустой `code` допустим **только в корне** — это адрес `/`. У вложенной страницы без
    кода адрес совпал бы с родительским.
  - Страницу нельзя перенести внутрь собственного поддерева.

### `content_blocks` — HTML-блоки (раздел удалён)

Таблица осталась в базе с прежними данными, но модели и модуля у неё больше нет:
раздел «HTML-блоки», маркеры `#BLOCK:код#` и тип свойства `html-blocks` убраны целиком.

### `infoblock_sections` / `infoblocks` / `infoblock_elements` — инфоблоки

- **Назначение:** списки однотипных записей (новости, товары, отзывы). Три уровня:
  раздел группирует инфоблоки, инфоблок описывает список, элемент — одна его запись.
  Раздел `/admin/infoblocks`.
- **Поля раздела:** `id`, `userId`, `position`, `code`, `name`, `description`.
- **Поля инфоблока:** `id`, `userId`, `sectionId`, `position`, `code`, `name`,
  `description`, `elementName` (как зовётся одна запись), `isActive`.
- **Поля элемента:** `id`, `userId`, `infoblockId`, `position`, `code`, `name`,
  `preview` (анонс), `content`, `image`, `date`, `isActive`, `props` (задел под
  настраиваемые свойства; пока всегда `{}`).
- **Связи:** `infoblocks.sectionId` → `infoblock_sections`,
  `infoblock_elements.infoblockId` → `infoblocks`. Удаление верхнего уровня уносит
  нижние в транзакции: раздел — свои инфоблоки, инфоблок — свои элементы.
- **Инварианты:**
  - Инфоблок всегда лежит в разделе: `sectionId` обязателен, «ничьих» списков нет.
  - Код раздела и код инфоблока уникальны у пользователя
    (`infoblock_sections_user_code`, `infoblocks_user_code`), код элемента — внутри
    своего инфоблока (`infoblock_elements_block_code`). Гарантия — индексы, а не
    только проверка в сервисе: два параллельных запроса прошли бы её оба.
  - Код инфоблока уникален у пользователя целиком, а не внутри раздела: им список
    подключают в вёрстке, и после переноса в соседний раздел шаблон звал бы уже не тот.
  - Элемент адресуется вместе со своим инфоблоком: по одному номеру элемента
    без проверки списка можно было бы править чужие записи.
  - Набор полей элемента общий на все инфоблоки; свои свойства лягут в `props`.

### `settings` — параметры сайта

- **Назначение:** название сайта и хранилище файлов. Раздел `/admin/settings`.
- **Поля:** `id`, `key`, `value` (текст) — **строка на настройку**, а не колонка.
  Ключи и значения по умолчанию — `SETTINGS_DEFAULTS` в `settings/settings-values.ts`:
  `siteName`, `storageId` (номер хранилища из `infoblock_storages` для новых файлов;
  пусто — встроенное). Новая настройка — новый ключ в этом списке, а не колонка в базе.
- **Владельца нет.** Настройки общие на весь сайт — это исключение из правила
  мультитенантности, как и `users`. Маршруты всё равно закрыты JWT.
- **Инварианты:**
  - Ключ встречается один раз — уникальный индекс `settings_key`; на нём же держится
    upsert при сохранении.
  - Нет строки — у настройки значение по умолчанию. Строки заводятся при сохранении,
    и пишутся только изменённые ключи. Незнакомые ключи в базе не читаются.
  - Выбрать для новых файлов можно только существующее хранилище, которое отвечает
    (`HeadBucket`) — проверка идёт при смене выбора.
  - Доменов здесь нет: их несколько и у каждого своя карточка — это `infoblock_domains`.

### `infoblock_storages` — внешние хранилища файлов

- **Назначение:** S3-совместимые хранилища, куда можно загружать файлы, — сколько угодно.
  Встроенного здесь нет: оно одно, его ключи в env. Модуль `infoblocks/storages/`,
  маршрут `/api/infoblocks/storages`, список редактора с ключом `storages` —
  как все списки редактора, лежит в `infoblocks/`, хотя показывается в настройках.
- **Поля:** `id`, `name`, `endpoint`, `region`, `bucket`, `accessKey`, `secretKey`,
  `publicUrl`. Владельца нет — хранилища общие на сайт, как и настройки.
- **Инварианты:**
  - `secretKey` наружу не отдаётся никогда; пустой секрет при правке — «не менять».
  - Хранилище сохраняется, только если отвечает с этими ключами (`HeadBucket`):
    при создании всегда, при правке — если поменяли адрес, регион, бакет или ключи.
  - Не удаляется, пока выбрано для новых файлов или в нём лежат файлы (наружу —
    `isBlocked`): иначе у файлов не осталось бы ключей, чтобы их удалить.

### `infoblock_files_sections` — разделы файлов

- **Назначение:** дерево разделов, по которым разложены файлы. Список редактора
  контента с ключом `file-sections`, раздел `/admin/files`. Модуль
  `infoblocks/files/sections/`, маршрут `/api/infoblocks/files/sections`.
- **Поля:** `id`, `userId`, `parentId` (null — корень), `name`, `sort`.
- **Инварианты:**
  - Здесь только разделы, заведённые пользователем. **Разделов свойств в базе нет**:
    файл, загруженный через свойство, помнит его (`infoblock_files.propertyId`), а раздел
    свойства (`property-<номер>`) и группу его списка (`group-<ключ>`, в названии путь)
    сервер собирает при выдаче — по одному на свойство, у которого есть файлы.
  - Глубина дерева — не больше «Уровней вложенности» списка `file-sections`
    (по умолчанию 2): проверяется при создании и переносе раздела, всей его веткой.
  - Удаляется только пустой раздел: без файлов и без вложенных разделов.
  - Раздел нельзя перенести в собственную ветку.

### `infoblock_files` — файлы

- **Назначение:** карточка файла; сам файл — во встроенной папке панели или объектом во внешнем S3.
  Запись списка редактора `files.<номер раздела>`, а загруженный через свойство —
  `property-files.<номер свойства>`: у файлов каждого раздела свои свойства. Модуль `infoblocks/files/`, маршрут
  `/api/infoblocks/files`.
- **Поля:** `id`, `sectionId` (→ `infoblock_files_sections`; null — загружен через
  свойство), `propertyId` (свойство «Файл»/«Изображение», через которое загружен; null —
  файл в разделе), `name`, `code` (имя в адресе, не меняется), `mimeType`, `size`, `storageId` (→ `infoblock_storages`;
  null — встроенное). **Владельца нет** — файлы общие на сайт. **Адреса нет** — он
  собирается из ключа `00/00/<номер>/<код>` и хранилища; ключа в базе тоже нет.
- **Связи:** **к каким записям привязан файл, не хранится** — это значения свойств
  «Файл»/«Изображение» (`infoblock_values.number`). Один файл могут выбрать сколько
  угодно записей. Удаление файла стирает эти значения в той же транзакции.
- **Инварианты:**
  - Хранилище запоминается при загрузке: переключение хранилища в настройках уже
    загруженные файлы не трогает.
  - Файл в значении свойства — существующий и подходящий под ограничения свойства
    (изображение, формат, вес); проверяет запись значений.
  - Задано ровно одно из `sectionId` / `propertyId`.
  - Удаление файла уносит и значения его собственных свойств (`files.<раздел>` или
    `property-files.<свойство>`).
  - Свойство удалили — его файлы остаются с `propertyId`; «Файлы» показывают их
    в разделе «Удалённое свойство #N», оттуда их удаляют.

### `infoblock_domains` — домены сайта

- **Назначение:** имена хостов, на которых работает сайт, деревом: в корне домены, под
  каждым его поддомены. Список редактора контента с ключом `domains`, в панели —
  «Настройки» → «Домены» (`/admin/settings/domains`). Модуль `infoblocks/domains/`, маршрут `/api/infoblocks/domains`.
  Подробности — [`docs/domains.md`](../../../docs/domains.md).
- **Поля:** `id`, `parentId` (null — домен, иначе поддомен этого домена), `name` (у домена —
  имя целиком, у поддомена — только его часть: `ekb`), `isActive`. Полного адреса в базе
  нет: `ekb.farkop.ru` складывается из имён по цепочке родителей и отдаётся полем `address`.
  **Владельца нет** — домены общие на сайт, как и настройки; общий и сам список
  (`isShared`), поэтому его свойства одни на всех.
- **Инварианты:**
  - Адрес уникален на весь сайт — проверяет сервис по адресам всех записей после правки;
    индексы `infoblock_domains_parent_name` (`parentId`, `name`) и
    `infoblock_domains_root_name` (`name` у корневых) держат частые случаи от гонки.
  - Имя поддомена не содержит имени его домена (`ekb`, а не `ekb.farkop.ru`); сложенный
    адрес — имя хоста, порт только в конце.
  - Имя хранится нормализованным: без протокола, пути, пробелов и заглавных букв.
    Приведение делает DTO — до проверки формата; больше имя не меняется.
  - Глубина — не больше «Уровней вложенности» списка `domains` (по умолчанию 2),
    проверяется при создании и переносе всей веткой; в свою ветку не переносится.
  - Домен с поддоменами не удаляется; удаление стирает значения его свойств.

### `infoblock_settings*` — настройки списков, их свойства и значения записей

- **Назначение:** у любого списка редактора контента — имя, код, уровни вложенности и правила
  записей (`infoblock_settings`), вкладки карточки (`infoblock_settings_tabs`), свойства
  записей (`infoblock_settings_properties`) с вариантами «Списка»
  (`infoblock_settings_property_options`), сами записи списка
  (`infoblock_records` — дерево) и значения их свойств (`infoblock_values`,
  модуль `infoblocks/values/`), а ещё вид таблицы списка — какие колонки видны
  (`infoblock_settings_columns`) — и поля её фильтра (`infoblock_settings_filters`). Подробности —
  [`docs/infoblock-settings.md`](../../../docs/infoblock-settings.md).
- **Поля:** `infoblock_settings` — `id`, `userId`, `listKey`, `name`, `code`, `maxDepth`
  (уровней вложенности: 1 — плоский список, больше или null — дерево; отдельного флага
  дерева нет), правила символьного кода; `infoblock_records` — `id`,
  `settingsId`, `recordKey`, `parentId`; `infoblock_values` — `id`,
  `recordId`, `propertyId`, `sort`, `text`, `number`, `json`, `optionId` (вариант «Списка»);
  `infoblock_settings_columns` — `id`, `userId`, `settingsId`, `key`, `position`, `width`;
  `infoblock_settings_filters` — `id`, `settingsId`, `key`, `position`.
- **Строка на значение, а не JSON на запись:** по строкам ищут, фильтруют и сортируют,
  поэтому и колонка под значение у каждого вида своя. Значение привязано к **номеру** свойства: код
  у свойства правят, и значения от этого страдать не должны.
- **Связи:** список и запись адресуются строковыми ключами (`infoblock-elements.3`,
  `element-7`) — настройки общие для таблиц всех разделов, FK туда не поставить. Зато
  внутри настроек всё на FK с `ON DELETE CASCADE`: удалили свойство — ушли его значения,
  удалили запись — ушли все её значения. Файлы, блоки и привязанные записи проверяются
  на владельца при записи.
- **Общие списки** (`users`, `roles`): настройки одни на сайт — строка `infoblock_settings`
  с `userId = 0` (`SITE_OWNER`), иначе роль пользователя у каждого смотрящего была бы
  своя. Правит такие списки (настройки, свойства, значения) только `root`.
- **Вид таблицы — у каждого свой, и у общих списков тоже:** строки
  `infoblock_settings_columns` подписаны `userId` того, кто смотрит, а не владельцем
  настроек. Строка — видимая колонка; строк нет — колонки по умолчанию. Внешнего ключа
  на настройки модель не объявляет (как и модель вкладок): строки читаются только
  по паре `(userId, settingsId)`.
- **Поля фильтра — одни на список для всех:** строки `infoblock_settings_filters`
  принадлежат настройкам списка (`settingsId`), без `userId`, правит их любой, кто список
  видит. Что в полях выбрано, в базе нет — это в адресе страницы.
- **Инварианты:**
  - Системное свойство (`isBlocked`) заводит и выравнивает сервер по перечню
    `infoblocks/settings/properties/system-properties.ts` — при старте и при появлении
    настроек нового списка; через API оно не меняется и не удаляется.

### `history` — журнал изменений

- **Назначение:** кто, когда и что поменял. Общий на все разделы панели.
  Модуль — `infoblocks/history/`, маршрут — `/api/infoblocks/history/:listKey`;
  таблица осталась `history`: при `sync({ alter })` переименование завело бы новую,
  пустую таблицу, а записанное осталось бы в старой.
- **Поля:** `id`, `userId`, `entity` (раздел, напр. `pages`), `entityId` (идентификатор
  записи строкой), `entityCode`, `entityName`, `action` (`create` | `update` | `delete`),
  `changes` (изменённые поля с «было/стало»), `snapshot`, автор (`authorId`, `authorName`,
  `authorEmail`, `authorIp`), `createdAt`.
- **Инварианты:**
  - Автор берётся из JWT, IP — из запроса; из тела запроса они не читаются никогда.
  - `update` без единого изменённого поля в журнал не пишется.
  - Записи журнала не правятся и не удаляются.
