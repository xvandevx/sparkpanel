# SparkPanel headless — панель в одном Docker-образе

Цель — чтобы любой поднял SparkPanel у себя одной командой и спокойно обновлял её:
сайт читает данные через внешнее API (`/api/v1`), ассистенты пишут через MCP
(`/api/mcp`), а сама панель — один контейнер рядом с базой.

В этой папке — всё, что относится к такой поставке: образ, пример `docker-compose.yml`
для того, кто ставит, шаблон секретов и этот файл. Наша разработка (`docker/`,
`scripts/dev.sh`) и наш прод (`prod/`) отсюда ничего не берут и не меняются.

## Как устроен образ

```
                    один контейнер, порт 3000
┌──────────────────────────────────────────────────────────┐
│ NestJS                                                   │
│   /api/…     → контроллеры, как сейчас                   │
│   /admin…    → фронтенд статикой (HTML + JS next build)  │
│   /uploads/… → файлы встроенного хранилища из MinIO      │
│   /          → редирект на /admin                        │
└──────────────────────────────────────────────────────────┘
         │                         │
     Postgres                    MinIO (файлы)
```

- **Фронтенд — статикой.** Серверного рендеринга в панели нет: ни `getServerSideProps`,
  ни API-маршрутов Next, ни `middleware`, все данные грузятся в браузере после входа.
  Поэтому `next build` с `NEXT_OUTPUT=export` (`frontend/next.config.js`) выгружает
  панель в `out/` — около 9 МБ HTML и JS, — и её отдаёт сам NestJS.
  Сервер Next в образе не нужен: на один процесс Node меньше, а панель и API
  по-прежнему на одном адресе — CORS не нужен, относительные `/api`-пути работают.
- **Раздача** — `backend/src/frontend/serve-frontend.ts`, включается переменной
  `FRONTEND_DIR` (в образе — `/app/frontend`). Страница — файл `<адрес>.html`;
  динамические страницы Next выгружает по одной на маршрут
  (`admin/contents/[contentId].html`, `admin/files/[sectionId].html`), номер из адреса
  страница берёт сама в браузере. Список страниц читается при старте. Неизвестный
  адрес — `404.html` с кодом 404. Файлы сборки (`/_next/static/…`, в имени хэш)
  кешируются навсегда, HTML — `no-cache`.
- **Файлы встроенного хранилища** (`/uploads/<ключ>`) отдаёт тоже NestJS —
  `backend/src/storage/serve-uploads.ts`: читает объект из MinIO своими ключами
  и передаёт браузеру тип, «показать или скачать», кэш, `ETag`; `Range` (перемотка
  видео) и условные запросы (304) проходят в MinIO. MinIO наружу не публикуется, ставить
  перед ним ничего не нужно. Локально и на нашем проде `/uploads/` по-прежнему
  перехватывает nginx. Внешние хранилища из «Настроек → Хранилища» отдают файлы сами,
  по своему адресу. Резервная копия сайта файлов не содержит — их бэкапят из тома
  `minio-data`.
- **Стили antd** собираются при `next build` (`pages/_document.tsx`) и лежат в HTML —
  проверено на выгрузке.
- **Сборка** — два независимых этапа (фронтенд, бэкенд), Docker гоняет их параллельно
  и кеширует по отдельности. Node 22.

Локально ничего не поменялось: `next dev` (:3401) за nginx (:3400), как раньше.
Без `NEXT_OUTPUT` конфиг Next прежний, без `FRONTEND_DIR` бэкенд статику не отдаёт.

## Запустить

Выпущенный образ — `ghcr.io/xvandevx/sparkpanel`. Клонировать репозиторий не нужно:
`docker-compose.yml` и шаблон секретов лежат в каждом выпуске на GitHub.

```bash
mkdir sparkpanel && cd sparkpanel
curl -fsSLO https://github.com/xvandevx/sparkpanel/releases/latest/download/docker-compose.yml
curl -fsSL https://github.com/xvandevx/sparkpanel/releases/latest/download/env.example -o .env
# заменить в .env значения
docker compose up -d
```

Панель — `http://localhost:3000`. Первым входом заводится главный администратор.
Обновить — `docker compose pull && docker compose up -d`. Версия — `SPARKPANEL_VERSION`
в `.env`: `1.4.0` — ровно она, `1` — свежая 1.x, не задана — `latest`.

Из исходников — в клоне репозитория раскомментировать `build` в `docker-compose.yml`,
`cp .env.example .env` и `docker compose up -d --build`.

## Переменные

Все — в `environment:` у `sparkpanel` в `docker-compose.yml`, секреты — из `.env`.

| Переменная | Назначение |
|------------|-----------|
| `DATABASE_URL` | база одной строкой: `postgres://user:pass@host:5432/db`, TLS — `?sslmode=require` (сертификат проверяется; самоподписанный — `?sslmode=no-verify`). Спецсимволы в пароле — URL-кодом (`@` → `%40`). Без неё читаются пять `POSTGRES_*` (`HOST`, `PORT`, `USER`, `PASSWORD`, `DB`), как в нашей разработке |
| `PUBLIC_URL` | внешний адрес панели (`https://cms.example.com`): из него полные адреса файлов во внешнем API и `servers` спецификации. Не задан — адрес из запроса (`Host` + `X-Forwarded-Proto` от прокси) |
| `PRIVATE_KEY` | подпись входа в панель (JWT) |
| `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY` | встроенное хранилище файлов (MinIO из того же compose) |
| `FRONTEND_DIR` | папка статики панели; в образе уже задана (`/app/frontend`) |

Своя база вместо сервиса `postgres` — заменить `DATABASE_URL` на её адрес и убрать
`postgres` из compose (вместе с `depends_on`).

Только образ, без запуска: `cd webSite && docker build -f headless/Dockerfile -t sparkpanel:dev .`

**Статику не собирать в рабочей папке `frontend/`.** Промежуточная сборка Next пишет
в `.next` и затирает кеш работающего `next dev` (тот отвечает 500, лечится
`rm -rf .next` и перезапуском); `distDir` меняет только каталог выгрузки, не сборки.
Поэтому статика собирается в Docker, а для пробы — в копии папки.

## Принятые решения

Открытых решений сейчас нет.

1. **Встроенное хранилище файлов — MinIO, `/uploads` отдаёт сама панель.**
   Зачем: у файла встроенного хранилища одна ссылка — `/uploads/<ключ>`, и по ней
   ходят двое. Админка — превью в «Файлах», картинки и файлы в карточке записи.
   Внешний сайт — API (`/api/v1`) отдаёт адрес файла полным, с адресом панели
   (`https://panel.example.com/uploads/00/00/78/banner.jpg`), и браузер посетителя
   идёт за картинкой прямо в панель; так же — ссылки на файлы в HTML-свойствах.
   Локально и на нашем проде эти ссылки отдаёт nginx, в образе его нет — без раздачи
   из NestJS файлы не открывались бы ни в админке, ни на сайте. Внешних хранилищ
   («Настройки → Хранилища») это не касается: у их файлов свой адрес, панель они минуют.

   Почему так: одна реализация хранилища на все поставки, наш dev и прод не меняются.
   Цена — три сервиса в установке и файлы через Node; перед большим сайтом стоит CDN
   или кэширующий прокси (заголовки кэша у файлов вечные). Папку на диске вместо MinIO
   (установка — панель + Postgres) рассматривали и отложили.

2. **Первичная настройка остаётся как есть** — главного администратора создаёт
   первый, кто откроет `/admin` (поставил — сразу зайди).

Репозиторий публичный — `github.com/xvandevx/sparkpanel`, один на фронтенд и бэкенд, лицензия — BSL 1.1
([`LICENSE`](../../LICENSE)). Образ выпускается только по тегу версии — см. «Как выпустить версию» ниже.

## Как выпустить версию

Образ выпускает `.github/workflows/image.yml` — **только по тегу** `v*.*.*`. Push в `main`
образ не трогает; кнопка «Run workflow» во вкладке Actions собирает образ для проверки
и ничего не выпускает.

Версия живёт **в одном месте — в теге**. `version` в `package.json` фронтенда и бэкенда
не используются и не правятся; в панели номер версии не показывается, он есть в метке
образа `org.opencontainers.image.version` (`docker inspect`).

1. Убедиться, что `main` в порядке, и выбрать номер по [semver](https://semver.org/lang/ru/):
   есть `feat!`/`BREAKING CHANGE` — старшая цифра, есть `feat` — средняя, иначе — младшая.
   Пока версия `0.x`, ломающие изменения поднимают среднюю.
2. Поставить тег и отправить его:
   ```bash
   git tag v1.4.0
   git push origin v1.4.0
   ```
   Проба перед выпуском — пре-релиз: `v1.4.0-rc.1`.
3. Минут через 15–20 (две архитектуры) появятся:
   - образ `ghcr.io/xvandevx/sparkpanel` с тегами `:1.4.0`, `:1.4`, `:1`, `:latest`
     (у `0.x` — без `:0`); у пре-релиза — только `:1.4.0-rc.1`, `latest` не двигается;
   - то же на Docker Hub, если он подключён (ниже);
   - GitHub Release `v1.4.0`: заметки — заголовки коммитов с прошлой стабильной
     версии по типам (ломающие, `feat`, `fix`, `perf`, остальное), к нему приложены
     `docker-compose.yml` и `env.example` — их качает быстрый старт.
     Пре-релиз помечается пре-релизом, и `releases/latest` на него не указывает.

Неудачный выпуск: удалить Release и тег (`git push origin :v1.4.0`), исправить, выпустить
следующий номер — переиспользовать номер не стоит, его образ уже могли скачать.

**Один раз после первого выпуска:** GitHub → профиль → Packages → `sparkpanel` →
Package settings → Change visibility → Public. Новый пакет GHCR закрыт, и без этого
`docker compose pull` у чужих людей просит логин.

**Docker Hub** — второй адрес, включается настройками репозитория (Settings → Secrets
and variables → Actions); пока их нет, выпуск идёт в один GHCR без ошибок:

| Где | Имя | Значение |
|-----|-----|----------|
| Variables | `DOCKERHUB_NAMESPACE` | аккаунт или организация на Docker Hub: образ — `docker.io/<namespace>/sparkpanel` |
| Secrets | `DOCKERHUB_USERNAME` | логин Docker Hub |
| Secrets | `DOCKERHUB_TOKEN` | Personal Access Token (Docker Hub → Account settings → Personal access tokens) с правами Read, Write, Delete — Delete нужен, чтобы обновлять описание репозитория |

Описание на Docker Hub выпуск берёт из `README.md` репозитория. Не обновилось
(например, у токена нет Delete) — образ всё равно выпущен, шаг помечен предупреждением.
