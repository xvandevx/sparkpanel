# frontend — архитектурные правила (ОБЯЗАТЕЛЬНЫ)

Эти правила применяются к **любому** коду во `frontend/`. Каждый компонент перед готовностью
должен пройти чек-лист в конце файла. Если код нарушает слой — его нужно переписать, а не «оставить пока так».

## Слои и направление зависимостей

```
pages/            тонкие страницы: только композиция компонентов, без данных и логики
  └─ components/  презентация: сами берут данные/колбэки из logic-хуков (НЕ через гору пропсов)
        ▲
  logic/          вся бизнес-логика + мост к redux: хуки use<Feature>() и use<Feature>Actions()
        ▲
  redux/          ТОЛЬКО стейт и получение данных: reducers, actions, thunks
        ▲
  api/            ТОЛЬКО сеть: обёртки над сгенерированным клиентом
        ▲
  src/generated/  авто-генерация из Swagger — НЕ РЕДАКТИРУЕМ руками
```

Зависимости идут только вниз: `pages → components`, `components → logic`, `logic → redux`,
`redux → api`, `api → generated`.
Компонент НЕ импортирует `api`/`redux`/`src/generated` напрямую — только `logic/`.

## Простота важнее универсальности

В репозитории лежат две реализации одного экрана, и сравнивать их можно построчно:

| | старая (`to_delete/components/contentEditor/`) | новая (`components/contentEditorNew/`) |
|---|---|---|
| ядро | **8595** строк, 85 файлов (компоненты + `logic/contentEditor` + `logic/listSettings` + `editorForm` + 3 среза стора) | **3890**, 36 файлов |
| на раздел | контроллер 93–183 строки + свой срез стора + thunks | «Страницы» 135 строк (удалённые потом «HTML-блоки» — 69) |
| что даёт раздел | 5 групп, ~30 полей, из них **14 функций** (`save`, `valuesOf`, `canRemove`, `rowAction`…) | 6 пропсов, обязательны 2; **функция ровно одна** — `column.logic` для вычисляемого значения |

Разница не в объёме, а в том, **кто что знает**: раньше раздел объяснял редактору, как собой
управлять, теперь — только где лежат его данные.

**Сжатие неравномерное, и это важно знать.** Таблица, карточка и плумбинг ужались в 3,3 раза
(5180 → 1555), а **окно настроек списка — всего в 1,46 раза** (2314 → 1585) и занимает теперь
47 % нового редактора. Это место, где новая реализация не проще старой: способ другой, объём
тот же. Копировать как образец стоит карточку и таблицу, а не настройки.

**Часть сжатия оплачена вычитанием, а не упрощением**: журнал (407 строк → заглушка; вернулся 2026-10-24 — ~450 строк вместе с галочкой в настройках списка), 8 типов
поля из 14 (медиатека, Quill, таблица, маркер блока), каскады `hidden/disabled/validate/onChange`,
переменные `#NAME#` (адрес открытой записи в URL вернулся 2026-10-28 — `useOpenRecord.ts`). Это долг, а не достоинство —
в скилле он помечен отдельно. Правила, которые это дают, и чек-лист —
в скилле [`simple-feature-design`](../../.claude/skills/simple-feature-design/SKILL.md).
Коротко:

1. **Раздел отдаёт Api и описание данными** — не функции `save`/`valuesOf`/`onSubmit`.
2. **Ключ вместо пробрасывания**: даётся `listKey`, ячейку стора каждый берёт сам.
3. **Сохраняет тот, кто правит** — форма не отдаёт черновик наверх.
4. **Одна сущность — один запрос, по номеру**; частичная правка — `PATCH` и только изменённое.
5. **Черновик локальный, в сторе — база**; после записи список перечитывается.
6. **Повторяющийся кусочек интерфейса — один компонент** (`ui/ActionIcon`, `ui/formLayout`).
7. **Никаких ветвлений «если раздел X»** внутри общего кода и обобщения поверх обобщения.

## Главный принцип: компоненты сами берут, что им нужно

❌ **НЕ прокидываем 10+ пропсов** сверху вниз — это невозможно поддерживать.
✅ Компонент **вызывает logic-хук** и получает оттуда готовые данные и обработчики.

```tsx
// ПЛОХО — прокидывание, «неподдерживаемо»
<UserDetail user={...} roles={...} onSave={...} onDelete={...} onResetPassword={...} /* +12 */ />

// ХОРОШО — компонент подключается сам
export default function UserDetail() {
  const { user, roles, onSave, onDelete, onResetPassword } = useUserDetail();
  if (!user) return null;
  ...
}
// на странице просто: <UserDetail />
```

**Пропсы у компонента допустимы только для:**
- идентичности элемента списка (`userId`, `row` у строки) — чтобы хук знал, что рендерить;
- презентационной настройки (вариант, размер) и `children` (композиция);
- **подключения универсального компонента к разделу** — **Api и описание**
  (`<ContentEditor api={contentApi} list={…} form={…} />`). Это не проброс данных:
  данные редактор грузит сам по Api, а в описании — только то, чем разделы
  действительно отличаются (колонки, поля, вкладки). Группами, а не россыпью
  по одному параметру, и не одним объектом: из экрана должно быть видно,
  что получает компонент.

Данные и обработчики фичи — из logic-хука, НЕ из пропсов.

## Имена

- **Логическое значение начинается с `is`**: `isNested`, `isReadOnly`, `isLoading`, `isActive`.
  Так из имени видно, что это флаг, а не данные: `nested` можно прочитать как «вложенные
  записи», `isNested` — только как «вложенность включена». Правило на все слои и на
  пропсы компонентов тоже.
- Остальные имена — существительные по смыслу (`rows`, `fields`, `listKey`), функции —
  глаголом (`buildPagePath`, `recordValues`).

## Правила по слоям

### `logic/` — бизнес-логика и единственный мост к redux
- **Хуки данных** `use<Feature>()`: делают `useSelector`, гоняют данные через чистые функции,
  возвращают готовые данные + обработчики. Тяжёлые селекторы (агрегации, сборка дерева) — здесь,
  мемоизированы.
- **Хуки-действия** `use<Feature>Actions()`: только `useDispatch` (без селекторов) → набор стабильных
  колбэков. Их можно звать где угодно, в т.ч. в строках таблицы, без лишних ререндеров и без пропсов.
- **Загрузка данных** — один хук-эффект `useLoad<Feature>()`, вызывается ОДИН раз (на странице),
  чтобы не дублировать запросы, если данные читают несколько компонентов.
- **Чистые функции**: фильтры, сортировки, подсчёты, форматирование, работа с датами и правами.
  Без React и без сети.
- `logic/<feature>/`: `use<Feature>.ts` + хуки-действия + файлы чистых функций.

### `components/` — презентация (подключаются к logic сами)
- ✅ Берут данные/колбэки из `logic/`-хуков; локальный UI-стейт (открыт/ховер/черновик инпута) — можно.
- ✅ `useDispatch`/`useSelector` НАПРЯМУЮ — нельзя. Только через `logic/`-хуки (redux остаётся заменяемым).
- ❌ Нет `api`, `fetch`, сгенерированного клиента.
- ❌ Нет бизнес-логики/расчётов/фильтров/работы с датами — это `logic/`.
- ❌ Нет длинных списков пропсов ради проброса данных — компонент подключается сам.

### `redux/` — стейт и данные
- ✅ Хранит **данные** (сущности) и **стейт экрана** (фильтры, выбранная строка, флаги загрузки,
  пагинация, что открыто и что набрано в форме редактора — `state.contentEditor`).
- ✅ Списки редактора контента — **один срез на все разделы** (`state.lists`, ключ списка →
  записи и флаги). Своего среза, thunk-ов и хуков-действий раздел не заводит: он отдаёт Api,
  а грузит и пишет редактор.
- ❌ Не хранит функции: контроллер раздела с его `save`/`valuesOf`/`options(values)` в сторе
  не лежит — он приходит пропсом, иначе ломается сериализуемость и devtools.
- ✅ **Thunks** — единственное место, откуда вызывается `api`. Тут же loading/success/error.
- ❌ Нет презентационной логики/форматирования (это `logic/`), reducer не дергает `api` мимо thunk.

### `api/` — сетевой слой
- ✅ Единственное место сетевых запросов: обёртки над `src/generated/api` (конфиг — `src/api/client.ts`).
- ❌ Никаких запросов в компонентах/редьюсерах мимо этого слоя.
- Генерация клиента: `npm run generate-api` (см. skill `frontend-api-client` / `API_CLIENT_README.md`).

### `src/generated/` — генерируется
- ❌ Не редактируем руками. Меняется бэкенд → перегенерировать.

## Раскладка `components/`

Компоненты группируются **по экранам**, а не сваливаются в одну папку. Страницы импортируют
через публичный `index.ts` папки экрана — внутренняя раскладка остаётся деталью реализации
и её можно менять, не трогая `pages/`.

```
components/
  layout/         каркас админки: AdminLayout (гард доступа), AppShell, Sidebar
  <screen>/       экран раздела: admin/ (доступ), dashboard/ (главная), pages/ (страницы),
                  files/ (медиатека), settings/ (настройки)
  editorForm/     общая форма, описанная данными: поле, группа, форма целиком
    index.ts      публичный вход: только то, что нужно страницам
  shared/         то, что используется двумя и более экранами: LevelGate, LevelCrumbs
  ui/             универсальные виджеты без привязки к домену (BrandMark, VantaHalo)
```

**Внутри папки экрана файлы тоже не сваливаются в кучу.** Больше 4–5 файлов на уровень —
раскладываем по смысловым частям (`header/`, `table/`, `drawer/`, `fields/`, `history/`),
у каждой свой `index.ts`; корневой компонент экрана — только композиция. Полные правила и
чек-лист — skill **`frontend-component-structure`**
([`.claude/skills/frontend-component-structure/SKILL.md`](../../.claude/skills/frontend-component-structure/SKILL.md)).

Разделы левого меню перечислены в [`config/navigation.ts`](config/navigation.ts) —
один список на меню, шапку и заглушки; новый раздел добавляется туда и в `pages/admin/`.

Новый компонент кладём в папку своего экрана; начали использовать из двух экранов —
переносим в `shared/`. `index.ts` не превращаем в реэкспорт всего подряд.

## Формы и списки — общие слои, свой экран не пишем

**Форма не верстается заново.** Поля и группы описываются данными
(`logic/editorForm/`), рисуют их общие компоненты (`components/editorForm/`):
экран отдаёт описание полей и значения, разметку полей не пишет. На этом слое живут и
шторка редактора контента, и отдельные экраны (`components/settings/`), поэтому поле
везде выглядит одинаково. Контракт — [`docs/editor-form.md`](../../docs/editor-form.md).

**Экраны «список записей + форма редактирования» тоже не пишутся заново**: для них есть
редактор контента — сейчас он переписывается с нуля в `components/contentEditorNew/`.
Раздел отдаёт ему **код списка** и **Api** (где лежат записи) — это разные сущности:
кодом адресуются настройки списка и журнал, Api ведёт к самим записям. Плюс описание:
`columns` (поле записи → заголовок, ширина, сортировка, поиск, своя логика значения),
`fields` (поля карточки записи), `settings` (как редактор показан: раскрытие дерева,
подпись кнопки добавления `addLabel`, скрыть журнал `isHistoryHidden` (виден он и так
только при включённой «Истории изменений» в настройках списка), кнопку
«Настройки» `isListSettingsHidden`, кнопку «Экспорт» `isExportHidden` и заголовок `isTitleHidden`,
а кнопку «Резервные копии» раздел, наоборот, включает — `isBackupShown` (копии сервер умеет
не у каждого списка); строка поиска есть всегда —
в плашке над таблицей, ищет по ID, коду записи и колонкам с `isSearch`; колонку ID
таблица добавляет сама, первой, — в «Колонках таблицы» её можно спрятать и переставить;
так же сама — «Создано» и «Изменено» после колонок раздела (`columnView.ts`, `DATE_COLUMNS`;
своя колонка раздела с тем же ключом — вместо системной), а в карточке сохранённой записи
эти даты внизу вкладки «Запись» — `drawer/RecordDates.tsx`, там же «Внешний ID»
записи, если интеграция его задала: берётся со страницы записей в сторе, `useExternalId`),
`blockedSettings` и, если в запись можно перейти, `recordPath` — шаблон её адреса
с `:id` (`"/admin/files/:id"`): в строке появляется значок перехода, и туда же ведёт
первая колонка. Шаблон — данные, а не функция: раздел говорит редактору, куда, а не как.

```tsx
<ContentEditor
  listKey={ListKey.pages}
  api={pagesApi}
  blockedSettings={{ maxDepth: null }}
  columns={…}
/>
```

**Устройство списка раздел не описывает — он его закрывает.** Дерево, символьный код
записей и историю изменений задаёт пользователь в «Настройках списка», и хранятся они
на сервере; разделу остаётся `blockedSettings` — настройки, которые у него не выбирают.
Страницы вкладываются друг в друга по самой своей природе (`maxDepth: null`), у файлов,
хранилищ и доменов нет журнала (`isHistoryEnabled: false`), у пользователей, ролей,
доменов, типов контента и файлов — черновиков (`isDraftEnabled: false`): в окне настроек эти поля
видны, показывают значение раздела и закрыты. Имени и кода списка в окне нет вовсе:
заголовок над таблицей — название пункта меню, код задаёт панель. Закрытое значение
сильнее сохранённого — список, у которого в базе лежит другое, чинится первым же
сохранением (`settings/blockedSettings.ts`).

Пока редактор умеет таблицу, карточку записи, настройки списка со свойствами записей
и журнал изменений (включается в настройках списка); логика живёт в самих компонентах
и переедет в `logic/`, когда её станет столько, что по файлам её придётся искать. Раскладка — по кускам экрана, имя файла
называет, что рисует компонент:

```
                          (сохраняются сразу), blockedSettings.ts — настройки, закрытые разделом
    tabs/                 TabList, TabNameDialog — вкладки карточки записи
    properties/           PropertyList — вкладка «Свойства записей»: «Добавить свойство»
                          справа сверху, вкладки карточки, свойства таблицей
                          (в строке — перенос на другую вкладку меню `Dropdown`), PropertyDrawer — одно свойство,
                          PropertyTypeFields — параметры его типа, property.ts — сам черновик,
                          useProperties.ts — сохранить и удалить свойство
  ui/                     ActionIcon — значок действия строки, вкладки, свойства;
                          CodeInput — поле кода с кнопкой «из названия» (код записи,
                          свойства, варианта списка);
                          FileThumb — превью файла (поле карточки и таблица «Файлов»);
                          TabCount — счётчик в заголовке вкладки (`Tag`)
```

Значки действий берутся из `ui/`, а не собираются на месте из `Button`: рядом друг
с другом кнопка antd и голый значок выглядят вразнобой.

**Карточка записи описывается полями, а не разметкой.** Раздел перечисляет `fields`
(подпись, тип, пояснение, обязательность) ровно так же, как перечисляет колонки; шторка
собирает по ним черновик, тело запроса и проверку. Код записи и родителя раздел не описывает —
их добавляет сам редактор по настройкам списка: «Символьный код записей» решает, есть ли поле
«Код» и обязательно ли оно (на любом уровне дерева, исключений по уровню нет; «Родитель» —
выбор деревом), галочка «Древовидная структура» — показывать ли выбор родителя
(в окне настроек «Уровней вложенности» видно только при ней, минимум 2; на сервере
это одно поле `maxDepth`: 1 — плоский список, больше или пусто — дерево). Писать
записи редактор умеет сам: `EditorListApi` раздела — это `list` и, если список это умеет,
`create`/`update`/`remove`; после каждой правки список перечитывается (сервер мог поправить
запись по-своему).

**Стандартные поля и колонки — готовыми описаниями**: `standardFields` (`drawer/record.ts`)
и `standardColumns` (`table/ContentEditorTable.tsx`) — название, активность, сортировка
(у колонок ещё код). «Сортировка» (`sort`) есть у каждого списка, кроме файлов: раздел
берёт её как есть — `sort: standardFields.sort` (число, пояснение «Чем меньше число, тем
выше запись в списке. Пусто — у новой записи 500») и `sort: standardColumns.sort`
(сортируемая, ширина 140), а не описывает заново.

**Форма во всём редакторе горизонтальная**: подпись слева, поле справа, пояснение под
полем. Раскладка одна на все окна — `contentEditorNew/ui/formLayout.tsx`, подключается
как `<Form {...FORM_LAYOUT}>`. Колонки заданы долями сетки, а не пикселями: при `flex`
строка переносится, как только содержимое не влезает, и поле с длинной подсказкой уезжает
под подпись во всю ширину.

**У множественного свойства — поле на значение**, с крестиком у каждого и кнопкой
«Добавить значение» внизу (`FieldInput` → `ValueList`). Исключение — «Список»:
там множественность умеет сам `Select`. Одним текстом через перевод строки значения
не набирают: это невидимое правило, о котором нужно помнить.

**У мультидоменного свойства (`isMultiDomain`) — таблица «Домены | Значение»** (`DomainValues`):
первая строка общая («Все домены» / «Все, кроме …»), ниже уникальные значения — каждое
для одной или нескольких доменов сразу, у каждой строки ввод тот же `FieldInput`.
В черновике — `[{ domainIds, value, exceptDomainIds? }]`, общее (`domainIds: null`) первым; формат
и домены для выбора — `logic/domains/`. Хранение и проверки на сервере —
в [`docs/infoblock-settings.md`](../../docs/infoblock-settings.md).

**Свойства записей встают в карточку сами.** Раздел описывает только свои поля; свойства,
заведённые в «Настройках списка», карточка раскладывает по вкладкам — первая «Запись»
(поля раздела и свойства без вкладки), дальше вкладки из настроек. Запись и её значения —
две сущности и два запроса: сначала `POST`/`PATCH` самой записи, потом
`PATCH /api/infoblocks/:listKey/values/:recordId` со значениями, потому что у новой записи
ключ появляется только после первого. Значения адресуются **номером свойства**
(`[{ propertyId, value }]`), а не кодом: код у свойства правят. В самой карточке ключ поля
свойства — `property-<номер>` (`drawer/propertyFields.ts`): голые номера объект ставит
по возрастанию, и поля встали бы по номерам, а не по сортировке; стор и API — по номерам,
переводят `fieldValuesOf`/`propertyValuesOf` на краях. И уходят только
**изменённые** — остального сервер не трогает, поэтому карточка не может стереть то, чего
не показывала. Родителя во втором запросе нет: он поле записи и уходит в первом. Не прошёл второй — говорим прямо: «Запись сохранена, а значения свойств —
нет», иначе пользователь нажмёт «Сохранить» ещё раз и заведёт вторую запись.

Поле незнакомого карточке типа показывается закрытым (`isReadOnly`).
**Значение такого поля карточка не трогает**: читает из записи и отдаёт серверу как есть.

**«HTML» — поле `HtmlField` (`FieldType.Html`, `drawer/html/`)**: два режима над одной
строкой HTML. «Визуально» — TipTap со своей панелью кнопок на antd, «HTML» — CodeMirror.
Оба грузятся только в браузере (`next/dynamic`, `ssr: false`). Значение с разметкой вне
схемы TipTap (`htmlMarkup.ts`) открывается в «HTML», в визуальный — после предупреждения:
TipTap выбросил бы чужие теги и атрибуты. В «HTML» — «Отформатировать» (Shift+Alt+F,
`logic/htmlFormat.ts`: только пробелы и переносы; разметку с незакрытым тегом не трогает).
«На весь экран» — то же поле в `Modal` (`HtmlFullscreen`) с третьим режимом «Рядом»: код
и результат во фрейме с пустым `sandbox` (`HtmlPreview`); сохранения у окна нет. Подсказки
кнопок — `title`, не `Tooltip`: всплывашка antd 6, раз показавшись, перехватывает Esc
у окна. Картинки в текст грузятся туда же, куда у поля
«Изображение», — через свойство (`field.upload`, только изображения); выбрать можно
и из загруженных (`FilePickerDrawer`). Рамка и подложка — токены темы через CSS-переменные
(`HtmlVisual.module.css`), своих цветов нет.

**«Таблица» — поле `TableField` (`FieldType.Table`)**: сетка antd `Table` с полем ввода
в каждой ячейке. Столбцы и заголовки — из настроек свойства (`field.table`), шапка
видна, только если хоть одному столбцу дали заголовок; строки добавляют и убирают
здесь же. В черновике — `string[][]` ровно по числу столбцов, в тело запроса пустые
строки с конца не уходят, таблица без строк — `null` (`tableValue.ts`).

**«Привязка к записям контента» — поле `LinkField` (`FieldType.Link`, antd `TreeSelect`)**:
выбор записи деревом — записи вложены под родителей в своём списке (`linkTree`
в `logic/contentLinks/`), у каждой подпись с ID (`withId`; так же подписаны записи
в фильтре и в выборе родителя: «Новости #8»). Где дерева не видно — в выбранном
значении и в ячейке таблицы — запись подписана путём от корня (`linkPaths`):
«Kia / Rio / Седан #23». Список задан в свойстве и обязателен
(`linkList`; элементы одного типа контента — `content-items.8`), и `useLinkTargets(listKeys)`
грузит записи **только этих списков**: все записи панели разом повесили бы выбор.
**«Привязка к типу контента»** — то же поле с `linkList` = `contents`
(`CONTENT_TYPES_LIST`, `linkListOf`): выбирают тип из раздела «Контент».
**«Привязка к значениям списка»** — обычное поле «Списка» (`FieldType.List`): варианты
свойства-источника сервер кладёт в `options` самой привязки.
Записи для выбора поле читает при каждом показе карточки (`logic/contentLinks/`): роль,
заведённая только что, должна сразу быть в выборе. В черновике значение — ключ
`список/запись`, в тело запроса уходит `{ listKey, recordId }`. Так назначают роль
пользователю.

**Системное свойство** (`isBlocked`, его заводит сервер) в окне настроек — с замком
вместо корзины, а его шторка на просмотр: всё закрыто одним `ConfigProvider
componentDisabled`. Свой `disabled` у поля этот запрет перебивает — у таких полей
системность учитывается явно.

**Секрет — поле `FieldType.Password`**: набирается скрыто, значение — обычная строка.
Им карточка показывает **скрытое свойство** (`isHidden`, «Не отдавать через API» в «Правилах»
шторки свойства): сервер его значение не отдаёт, поэтому поле всегда пустое, обязательным
не бывает и подписано «Значение не показывается после сохранения: оставьте пустым, чтобы
не менять» (`drawer/propertyFields.ts`). Пустое — значит «прежнее»: карточка шлёт только
изменённые значения. Так заведён секретный ключ внешних хранилищ.

**Свойство из внешнего источника** (`isExternal`, «Внешний источник» в «Правилах» шторки
свойства) — поле с флагом `isExternal`: значение видно, ввод закрыт (`isLocked`), у подписи
значок облака, под полем — «Заполняется из внешнего источника — в панели не правится»,
обязательным не бывает. Закрытое поле не меняется — и на сервер не уходит; сервер такую
правку из панели всё равно отклонил бы: значение пишет внешняя система через внешнее API или MCP.

**«Файл» и «Изображение» — поле `FileField`** (`drawer/file/`): значение — номер своего файла
или адрес внешнего (`https://…`, файл на чужом сервере; у множественного — список, можно
вперемешку; функции значения — `logic/files/fileValue.ts`), выбранные файлы с превью,
«Загрузить» с диска, «Выбрать из загруженных» и «Вставить ссылку». У внешнего файла —
метка «Внешняя ссылка», «Заменить ссылку» и «Забрать в хранилище» (сервер скачивает его
к себе, на месте адреса встаёт номер файла).
Файл с диска проверяется до загрузки по ограничениям свойства (`logic/files/fileRules.ts`,
включая разрешение — серверу его не узнать) и уходит сразу, не дожидаясь «Сохранить»:
файл запоминает свойство, в «Файлах» он в разделе свойства. К записи файл привязывается её
сохранением. Список файлов поле берёт из общего среза `state.files`. Одиночное поле
с выбранным файлом кнопок не показывает — иначе загрузка молча вытесняла бы файл.

Выбор из загруженных — своя шторка `FilePickerDrawer`, вложенная в карточку (antd
сдвигает карточку сам): дерево разделов, файлы с превью, поиск. Дерево, раздел свойства
и отбор файлов — чистые функции `logic/files/filePicker.ts`, неподходящий по формату
и весу файл закрывается с причиной (`pickError` — та же проверка, что у сервера).
Содержимое шторки собирается при каждом открытии (`destroyOnHidden`): разделы и файлы
перечитываются, поиск и раздел — с начала. Отдаёт шторка только номера, в значение
их кладёт само поле.

**Запись бывает защищена от удаления** — сервер присылает её с `isBlocked: true`
(раздел файлов, под который заведено свойство). Тогда в строке вместо корзины замок
с подсказкой, а в карточке нет «Удалить». Почему запись защищена, редактор не знает
и по разделу не ветвится: это поле самой записи.

**Запись бывает только для показа** — `isReadOnly: true` (раздел свойства в «Файлах»:
его собирает сервер, в базе его нет). Карточка не открывается — ни клика, ни номера
в колонке ID, ни значка правки, ни галочки, родителем в карточке её не выбрать;
перейти в неё (`recordPath`) можно. Удаление закрывает `isBlocked`, сервер шлёт оба флага.
**Заголовок группы** — ещё и `isGroup: true` (группа разделов свойств одного списка):
своего в нём ничего нет, поэтому нет и ссылки с переходом.

**Что умеет список, видно по его Api**: нет `create` — нет кнопки «Добавить запись»
(файлы заводятся загрузкой над списком, а не карточкой); нет `update` — карточка на
просмотр, поля закрыты и «Сохранить» нет; нет `remove` — нет корзины и «Удалить». Так же делается и «только просмотр»: «Пользователи» и «Роли»
отдают не-`root` Api с одним `list` (`logic/users/useUsersAccess.ts`), флага `readOnly` нет.
Колонка с `isPreview` — адрес файла: в ячейке превью (`ui/FileThumb`) — картинка по клику
открывается на весь экран (просмотр antd), остальное — ссылкой в новой вкладке.
`FileThumb` так открывает картинку везде: в таблице, в ячейке свойства, в карточке записи
и в выборе из загруженных.
Колонка с `isTag` — значение меткой `Tag` (хранилище у файла), пустое — пустая ячейка.
Колонка с `linkField` (`'url'`) — значение ссылкой на адрес из этого поля записи, в новой
вкладке: так имя файла открывает файл. Это данные, а не `logic`, поэтому колонка остаётся
в поиске и фильтре.
`logic` колонки может вернуть вместо текста ссылки `[{ text, href }]` (`EditorCellLink`):
в ячейке они по одной на строку и открываются в новой вкладке, в выгрузке и фильтре —
текстом через «; ». Так «Файлы» ведут в записи, выбравшие файл.

**Открытая запись живёт в адресе** — `?id=<ключ записи>` (`useOpenRecord.ts`): клик по строке
дописывает его, закрытие карточки убирает, остальное в адресе (фильтр, раздел) не трогается.
Страница открыта с `?id` — карточка открывается сама: запись ищется на странице таблицы,
нет там — во всём списке (он тогда догружается). У новой записи ключа нет, в адрес она
не попадает. Адрес записи любого списка собирает `recordPagePath(listKey, id)`
(`logic/navigation/listPaths.ts`): страница списка по его ключу плюс `?id`; у списка
без своей страницы (формы, инфоблоки) — null.
Колонка с `badge` (`{ key, name, color }`) — метка `Tag` рядом со значением, когда
у записи логическое поле `key` включено: так «Пользователи» отмечают главного
администратора у email. Цвет — из набора antd.

**Колонки раздела — это колонки по умолчанию, а не окончательные.** Шестерёнка
в заголовке столбца действий открывает шторку «Колонки таблицы»: пользователь выбирает,
какие из колонок раздела, **свойств записей** и номера записи (ID) видны, в каком
порядке и какой ширины.
Вид свой у каждого и лежит на сервере (`/api/infoblocks/settings/:listKey/columns`),
в сторе — `columns` в ячейке списка (`null` — ещё не пришёл, пусто — не настраивали).
Раздел для этого ничего не делает: ключ колонки свойства — `property-<номер>`, как
у поля в карточке; ячейку свойства таблица собирает сама (`table/propertyValue.ts`).
«По умолчанию» стирает вид, а не сохраняет копию колонок раздела — тогда новая колонка
раздела появится сама.

**Фильтр раздел тоже не описывает.** Фильтруют по тем же полям, из которых собирают
таблицу, — колонкам раздела и свойствам записей; поле фильтра адресуется ключом колонки.
Колонка раздела — подстрока по полю записи, логическая (ключ на `is`) — выбор «да / нет»
(`true`/`false`, подписи — из её логики); свойство — по типу («Список» и привязка — варианты,
текст — подстрока, число — диапазон, остальное — «заполнено»). Колонка со своей подписью
(`logic`) в фильтр не встаёт, кроме логической: сервер сверяет поле, а не подпись.
**Набор полей** — один на список для всех, на сервере (`filterKeys` в ячейке списка);
**выбранное** — в адресе страницы (`?f.name=фар`), у каждого своё. Оба держит `useFilters`
у корня редактора: набор уходит на сервер с задержкой, выбранное — в адрес сразу, а запрос
страницы берёт его копию в хуке: адрес меняется не мгновенно, а поле ввода должно
отзываться на каждую букву.

**Таблица — страницами с сервера** (`table/useRecordsPage.ts` →
`GET /api/infoblocks/records/:listKey`, один маршрут на все списки). Поиск, фильтр,
сортировку и страницу (20 / 50 / 100) ведёт сервер; запрос уходит через 250 мс после
последней правки и лежит в ячейке списка (`page.query`) — после правки записи страница
перечитывается им же. Значения свойств приходят со страницей — только её записей —
и вливаются в `values` ячейки; карточка записи не со страницы (из журнала) догружает
свои (`useRecordValues`) и до их прихода полей свойств не показывает: черновик из пустоты
стёр бы их сохранением. **Дерево страницей не рвётся**: размер страницы — записи верхнего
уровня, каждая приходит со всей веткой. Найденное и отобранное — плоским списком.
Сортируются колонки с `isSort` и ID — по полю записи, у дерева — среди соседей, равные —
новые сверху; **по умолчанию — «Сортировка» по возрастанию** (`DEFAULT_SORT`
в `useRecordsPage.ts`; сняли сортировку колонки — снова она). У файлов поля `sort` нет —
там все равны, и по умолчанию новые сверху.

**Галочки в строках и быстрые действия** (`table/useBulkActions.ts`): «Активировать»,
«Деактивировать», «Удалить» и крестик «Снять отметку» — в тёмной плавающей «пилюле»
у нижнего края экрана по центру раздела (`table/BulkBar.tsx`), пока что-то отмечено.
Она `sticky`, а не `fixed`: держится в области раздела и не наезжает на меню; места
в разметке не занимает (обёртка нулевой высоты, панель растёт вверх поверх таблицы,
таблица с панелью — один блок колонки редактора), поэтому страница не удлиняется; тёмная —
через `darkAlgorithm` antd, цвета из её токенов, своих нет. Какие есть, решает Api
раздела: «Удалить» — при `remove`, включение — при `update` и поле `isActive`
в карточке; нет ни одного — нет и галочек. Правки уходят маршрутами раздела по одной
записи (`runEditorBatchThunk`): у каждой свои проверки и след в журнале, упавшая
не останавливает остальные, список перечитывается раз в конце. Удаление спрашивает,
пропускает защищённые (`isBlocked`) и записи, чей предок тоже отмечен (уйдут с ним).
Отмечают только на показанной странице: перелистнули или нашли другое — отметка
с ушедших строк снимается; после быстрого действия — целиком.
Поменяли поиск или фильтр — первая страница; опустела страница после удаления —
последняя, где записи есть.

**Ширины колонок точные** (`tableLayout="fixed"`): при раскладке «auto» antd подгоняет
их под содержимое, и узкие колонки (галочки, ID) у каждой таблицы выходили своей ширины.
Тянется одна **главная** колонка — первая видимая после ID, кроме превью (`isPreview`; `mainColumnKey`): ширину
ей не задают, в ней же ветки дерева и ссылка в запись. Колонку галочек и служебную
колонку раскрытия antd считает в номерах колонок, поэтому `expandIconColumnIndex` —
место главной колонки плюс 2, когда есть галочки (проверено в браузере).

**Весь список** (`items` ячейки, `api.list`) таблица не грузит. Его догружают те, кому
он нужен целиком: карточка дерева (выбор родителя — `useCardRows`), журнал (открыть
запись не с текущей страницы), меню типов контента, выбор хранилища. После правки
записи он перечитывается, только если его уже грузили. Настройки, вкладки и свойства
грузятся один раз — их правят только из своего окна.

**Описания (`fields`, `columns`) выносятся из компонента раздела в константу модуля**:
у литерала внутри каждый рендер новая ссылка, а редактор по ней решает, не пора ли пересобрать
карточку. Сама шторка от такой небрежности защищена ссылкой на поля, но лишних сборок лучше
не плодить.

**Сохраняет тот, кто правит.** Шторка не отдаёт черновик наверх, чтобы его сохранил
список: запись уходит на сервер по своему номеру, и посредник между формой и `api/`
не нужен. Общие действия сущности живут рядом с её компонентами в `use<Сущность>()`
(`settings/properties/useProperties.ts`) и переедут в `logic/`, когда редактор дорастёт. Старый редактор (`components/contentEditor/`,
`logic/contentEditor/`, общий слой формы `editorForm/`) и экраны остальных разделов
лежат в `to_delete/` и возвращаются по частям. Своего среза в redux у раздела нет:
данные и настройки всех списков лежат в `state.contentEditorNew` по коду списка.

Не хватает чего-то редактору — **расширяем общий слой, а не пишем свой экран**: так
«Файлы» получили переход в запись (`recordPath`), защиту записи (`isBlocked`) и поле
файла, и этим теперь может пользоваться любой раздел. Список внутри списка —
это уровни-страницы (`/admin/files/2`, `/admin/infoblocks/2`), а не вторая панель рядом:
каркас уровня (`LevelGate`, `LevelCrumbs`) лежит в `components/shared/`.

Важное следствие для logic-слоя: **колонки и поля описываются данными, а не разметкой**
(`variant`, `value`, `hint`, `hidden`, `disabled`, `validate`, `onChange`).
JSX из `logic/` не возвращается.

## UI-кит — Ant Design

Весь интерфейс строится на **Ant Design** (`antd` v6). Своих кнопок/инпутов/таблиц не пишем —
берём компоненты antd и настраиваем их через тему, а не через локальные стили.

- **Тема стандартная**: светлый алгоритм antd, фирменный синий, дефолтные размеры. Своих
  цветов не заводим — компоненты должны выглядеть так, как их рисует antd. Единственная
  настройка — фон шапки, в [`config/theme.ts`](config/theme.ts); это же единственное место,
  где вообще меняются цвета и скругления, инлайном по компонентам — нельзя.
- Левое меню — штатная связка antd: `Layout.Sider` по умолчанию тёмный, `Menu` в нём с
  `theme="dark"`, содержимое светлое.
- Валидация форм — правила `Form.Item` вызывают **чистые функции из `logic/`**
  (`asRule(validateEmail)`), сами правила в компонентах не пишем. Переходник `asRule`
  общий на все разделы — [`logic/formRules.ts`](logic/formRules.ts).
- Tailwind оставлен только как утилиты раскладки, **preflight выключен**
  (`tailwind.config.js`): его сброс ломает стили antd, в первую очередь фон у `Button`.
  Свой минимальный сброс — в `styles/globals.css`.
- Иконки — `@ant-design/icons`.

## Грабли этого стека (проверено на экране `/admin`)

- **SSR и состояние из cookie.** Страницы статические: сервер не знает про cookie и рендерит
  «нейтральный» вариант. Если начать рисовать результат проверки уже в первом клиентском
  рендере, разметка разойдётся с серверной — React упадёт с `Hydration failed` и оставит
  мёртвый экран (кнопки не работают, стейт не обновляется). Поэтому зависящий от cookie UI
  показываем только после монтирования: см. флаг `isReady` в `logic/auth/useLogin.ts`.
- **antd + Next 14 (pages router).** Пакеты `antd`, `@ant-design/*` и `rc-*` публикуются как ESM,
  а SSR подключает их через `require` — без списка `transpilePackages` в `next.config.js`
  страница падает с `Cannot use import statement outside a module`.
- **Стили antd генерируются в рантайме (css-in-js).** Без сборки стилей на сервере
  (`pages/_document.tsx`: `createCache` + `StyleProvider` + `extractStyle`) первый рендер
  приходит без оформления и моргает «голым» HTML.

## Чек-лист компонента (проверять ВСЕГДА перед готовностью)

1. [ ] Нет импортов из `api/`, `src/generated/`, нет `fetch`.
2. [ ] Нет `useSelector`/`useDispatch` напрямую — данные и колбэки берутся из `logic/`-хука.
3. [ ] Нет длинного списка пропсов для проброса данных — компонент подключается к `logic/` сам.
       Пропсы — только идентичность элемента (id/item), настройка вида, `children`.
4. [ ] Нет бизнес-логики/расчётов/фильтров/работы с датами — только рендер и локальный UI-стейт.
5. [ ] Вся логика фичи в `logic/<feature>/`, все запросы в `api/`, весь стейт в `redux/`.
