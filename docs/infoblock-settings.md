# Настройки списков

У каждого списка, построенного на [редакторе контента](content-editor.md), есть кнопка
**«Настройки»** над таблицей. В настройках:

- **имя** — заголовок над таблицей;
- **код** — по нему список находит сайт;
- **древовидная структура** — записи вкладываются друг в друга, как страницы;
- **свойства записей** — дополнительные поля, которые появляются вкладкой «Свойства»
  в шторке каждой записи списка. Так у новостей появляется «Обложка», у товаров — «Цена»
  и «Артикул», без правки таблиц разделов.

Отдельно от них, значком над столбцом действий таблицы, открывается шторка **«Колонки
таблицы»**: какие колонки раздела и свойства записей видны, в каком порядке и какой
ширины. Это вид таблицы, а не настройка списка: он у каждого пользователя свой.

Строка **«Фильтр»** в плашке над таблицей отбирает записи по колонкам раздела
(название, код, активность) и по значениям свойств: «Добавить условие» ставит поле
чипом, клик по чипу — выбор значения. **Набор полей** фильтра один на список для всех и хранится на сервере,
а **что в полях выбрано** — в адресе страницы, у каждого своё.

Настройки — у **конкретного списка**, а не у раздела целиком: у записей инфоблока
«Новости» и инфоблока «Товары» свойства разные.

## Модель данных

### Ключ списка

Список задаётся строкой: вид списка, а у вложенных списков ещё и номер владельца через точку.

| Ключ | Список | Журнал правок свойств |
|------|--------|-----------------------|
| `pages` | страницы | `pages` |
| `forms` | формы обратной связи ([`forms.md`](forms.md)) — общий список | `forms` |
| `form-fields` | поля форм — их подключают к форме системным свойством «Поля»; общий список | `form-fields` |
| `users` | пользователи панели — общий список, правит `root` | `users` |
| `roles` | роли пользователей ([`users.md`](users.md)) — общий список, правит `root` | `roles` |
| `products` | товары ([`products.md`](products.md)) | `products` |
| `product-categories` | категории товаров — дерево без предела по умолчанию | `product-categories` |
| `contents` | типы контента ([`contents.md`](contents.md)) | `contents` |
| `content-items.<contentId>` | элементы одного типа контента — свойства и журнал у каждого типа свои | `content-items.<contentId>` |
| `domains` | домены сайта ([`domains.md`](domains.md)) — общий список, дерево в 2 уровня | — |
| `infoblock-sections` | типы инфоблоков | `infoblocks` |
| `infoblocks.<sectionId>` | инфоблоки одного типа | `infoblocks` |
| `infoblock-elements.<blockId>` | записи одного инфоблока | `infoblocks` |
| `file-sections` | разделы файлов ([`files.md`](files.md)) | — |
| `files.<sectionId>` | файлы одного раздела — свойств нет (`isPropertyless`) | — |
| `property-files.<propertyId>` | файлы, загруженные через свойство «Файл»/«Изображение» — свойств нет | — |
| `storages` | внешние хранилища файлов ([`settings.md`](settings.md)) — общий список | — |

У вложенного списка с журналом тип записи в журнале — **полный ключ списка**
(`content-items.3`), а не вид: журнал «Новостей» не смешивается со «Статьями».

**Общий список** (`isShared` у вида: `users`, `roles`, `domains`, `forms`, `form-fields`, `storages`) — список, записи которого общие на
сайт и владельца не имеют. Тогда и настройки у него одни на всех: их строка лежит под
владельцем `0` (`SITE_OWNER`), куда бы ни пришёл запрос. Иначе роль одного пользователя
у каждого, кто на него смотрит, была бы своей. Ноль, а не `null`: на `(userId, listKey)`
уникальный индекс, а два `null` Postgres считает разными. Стал список общим, когда
настройки у него уже заводили по-старому каждый себе, — самые ранние из них при старте
сервера становятся общими целиком (со свойствами и значениями), остальные больше не читаются.
Делает это сверка системных свойств (`SystemPropertiesService`), поэтому только у списков
с системными свойствами; настройки доменов стали общими переносом руками
([`implemented/domains.md`](../implemented/domains.md)).

**Список из управления панелью** (`isRootOnly`: `users`, `roles`) правит только `root` —
настройки, вкладки, свойства и значения записей; читать может любой. Проверяет это
`ListEditGuard` на контроллерах настроек, вкладок, свойств и значений (403 «Этот список
правит только главный администратор»); журнал такого списка тоже видит только `root`.

Перечень видов держат обе стороны: бэкенд (`infoblocks/settings/infoblock-kinds.ts`) — незнакомый
ключ он отвергает с `400`; фронт (`logic/listSettings/listKeys.ts`) — из него ключи берут
контроллеры разделов. Новый экран на редакторе контента добавляется в оба места.

### `infoblock_settings` — настройки списка

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `userId` | `INTEGER` | владелец; изоляция данных идёт по нему. У общего списка — `0` |
| `listKey` | `STRING` | ключ списка |
| `name` | `STRING` | имя списка — заголовок над таблицей |
| `code` | `STRING` | код, по которому список находит сайт |
| `useCode` | `BOOLEAN` | у записей есть символьный код (по умолчанию да) |
| `codeRequired` | `BOOLEAN` | без кода запись не сохранить |
| `codeUnique` | `BOOLEAN` | код сверяется с кодами остальных записей списка |
| `maxDepth` | `INTEGER`, null | «Уровней вложенности»; он же решает, **дерево ли список** — галочка «Древовидная структура» в окне настроек своей колонки не имеет, она пишет сюда же (выключена — 1, включена — 2 и больше или пусто): 1 — плоский список, больше — дерево не глубже этого уровня, null — дерево без ограничения. Пока настройки не сохраняли — по умолчанию вида (`infoblock-kinds.ts`: обычно 1, у `pages` — null, у `file-sections` — 2). Проверяет раздел при создании и переносе записи (сейчас — разделы файлов и страницы), карточка не предлагает слишком глубоких родителей; уровень корня — 1, записи, которые уже глубже, остаются на месте |
| `isHistoryEnabled` | `BOOLEAN` | «История изменений»: вести журнал правок записей списка (по умолчанию да). Выключен — сервер правки списка в журнал не пишет (`HistoryService.record` сверяется с настройками), а редактор не показывает ни журнал над таблицей, ни вкладку «История» в карточке; записанное раньше остаётся. Наружу `isHistoryEnabled` всегда `false` у списка без журнала (`hasJournal: false` — файлы, хранилища, домены); в окне переключатель у них закрывает раздел (`blockedSettings.isHistoryEnabled: false`) |
| `isDraftEnabled` | `BOOLEAN` | «Черновики»: правки записей сохраняются черновиком (`infoblock_drafts`) и попадают в записи по «Опубликовать» (по умолчанию нет). У пользователей, ролей, доменов, типов контента и файлов черновиков не бывает (`hasDrafts: false`) — сервер держит `false`, а их экраны закрывают переключатель (`blockedSettings.isDraftEnabled: false`). Пока в списке есть черновики, выключить нельзя (`409`). Подробности — [`drafts.md`](drafts.md) |

**Внешний файл.** Значение «Файла» и «Изображения» — номер своего файла (`number`) или
адрес файла на чужом сервере (`text`, `http(s)://`, до 2000 символов): так заводят картинки
старого сайта, не перекачивая их. Сервер адрес не скачивает и проверяет только расширение
в нём по `formats` свойства (адрес без расширения пропускается); вес и разрешение чужого
файла не проверяются. В «Привязан к» у файлов внешние адреса не попадают — это не файлы
панели. Забрать внешний файл к себе — `POST /api/infoblocks/files/import`
([`files.md`](files.md)), номер нового файла ставится в значение вместо адреса.

Индексы: `infoblock_settings_user_key` (`UNIQUE (userId, listKey)`) — одни настройки на список;
`infoblock_settings_user_code` (`UNIQUE (userId, code)`) — у каждого списка свой код.

### `infoblock_settings_tabs` — вкладки карточки записи

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер; на него ссылается свойство |
| `settingsId` | `INTEGER` | настройки списка, которым принадлежит вкладка |
| `code` | `STRING` | ключ вкладки |
| `name` | `STRING` | подпись в карточке записи |
| `position` | `INTEGER` | порядок вкладок |

Индекс `infoblock_settings_tabs_settings_code` (`UNIQUE (settingsId, code)`).

### `infoblock_settings_columns` — колонки таблицы списка

Строка на **видимую** колонку, как её настроил пользователь. Чего здесь нет, того
в таблице не видно; строк нет вовсе — таблица показывает колонки по умолчанию.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `userId` | `INTEGER` | **чей это вид** — тот, кто смотрит, а не владелец настроек |
| `settingsId` | `INTEGER` | настройки списка, таблицу которого настроили |
| `key` | `STRING` | поле записи (`name`, `isActive`) или свойство (`property-12`) |
| `position` | `INTEGER` | порядок слева направо |
| `width` | `INTEGER`, null | ширина в px; null — как задал раздел |

Индекс `infoblock_settings_columns_user_settings_key`
(`UNIQUE (userId, settingsId, key)`).

**Вид у каждого свой, и у общих списков тоже.** Строка подписана тем, кто смотрит:
спрятанная колонка «Пользователей» не должна пропадать у соседа. Поэтому и правит его
любой, кто видит список, — `ListEditGuard` на этих маршрутах нет.

**Свойство — номером, поле — именем.** Колонка свойства — `property-<номер>`, как ключ
его поля в карточке: код у свойства правят, а колонка должна остаться на месте. Какие
поля у записей раздела есть, знает фронт (колонки раздела), поэтому сервер проверяет
только вид ключа; колонку, которой больше нет (раздел её убрал, свойство удалили),
таблица просто не рисует.

**«По умолчанию» — это отсутствие строк, а не их копия.** Сброс стирает вид, а не
сохраняет колонки раздела: тогда колонка, которую раздел добавит потом, появится у всех,
кто таблицу не настраивал. У настроивших она ждёт в шторке спрятанной.

### `infoblock_settings_filters` — поля фильтра таблицы

Строка на поле, которое поставили в фильтр. Строк нет — фильтра нет.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `settingsId` | `INTEGER` | настройки списка, таблицу которого фильтруют |
| `key` | `STRING` | колонка: поле записи (`name`, `isActive`) или свойство (`property-12`) |
| `position` | `INTEGER` | порядок поля в строке фильтра |

Индекс `infoblock_settings_filters_settings_key` (`UNIQUE (settingsId, key)`).

**Набор один на список для всех, кто его видит** — в отличие от колонок, `userId` здесь
нет: строки принадлежат настройкам списка, как вкладки и свойства. У общих списков
(`users`, `roles`) настройки одни на сайт, значит, и фильтр; у остальных — на того же
владельца, что и записи. Ставит и убирает поля **любой**, кто видит список, —
`ListEditGuard` на этих маршрутах нет.

**Что в полях выбрано, сервер не хранит.** Это в адресе страницы у того, кто смотрит:
выбор одного не отбирает таблицу соседу, а ссылкой с отобранной таблицей можно поделиться.

### `infoblock_settings_properties` — свойства записей

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `settingsId` | `INTEGER` | настройки списка, которым принадлежит свойство |
| `code` | `STRING` | ключ значения; по нему свойство читает сайт |
| `name` | `STRING` | подпись поля в карточке |
| `hint` | `TEXT`, по умолчанию `''` | подсказка под полем в карточке записи; пусто — без подсказки |
| `type` | `STRING` | тип свойства |
| `tabId` | `INTEGER` | вкладка карточки; `null` — общая вкладка «Свойства» |
| `required`, `multiple` | `BOOLEAN` | обязательность и множественность |
| `isMultiDomain` | `BOOLEAN` | мультидоменное: значение своё на домен. Колонкой, а не в `params`: это правило любого свойства, а не параметр типа |
| `isHidden` | `BOOLEAN`, по умолчанию `false` | «Не отдавать через API»: значение пишут, но не читают — см. «Скрытые свойства» |
| `isExternal` | `BOOLEAN`, по умолчанию `false` | «Внешний источник»: значение пишет внешняя система через внешнее API или MCP, из панели не правится — см. «Свойства из внешнего источника» |
| `position` | `INTEGER` | порядок полей в карточке |
| `params` | `JSONB` | параметры типа: форматы, вес, разрешение, столбцы, заголовки, привязка (варианты списка — своей таблицей) |
| `isBlocked` | `BOOLEAN` | системное свойство: его заводит сервер, через API не меняется и не удаляется |

Индекс `infoblock_settings_properties_settings_code` (`UNIQUE (settingsId, code)`).

**Всё внутри списка привязано к настройкам номером, а не ключом.** У вкладок, свойств
и значений записей нет ни `userId`, ни `listKey` — только `settingsId` с внешним ключом
и `ON DELETE CASCADE`. Ключ списка это строка, и сменись он (список переехал, инфоблок
пересобрали), привязка по строке оставила бы сирот, а изоляция по владельцу уже обеспечена
самой строкой настроек. Поэтому запись внутрь списка сначала заводит пустые настройки,
если их ещё не сохраняли, — `ensureSettingsId`.

**Почему строками, а не массивом в JSONB.** По значениям свойств нужно будет искать
и сортировать записи, а у свойства должен быть устойчивый номер: массив такого не даёт —
там ключом служит сам код, и переименовать его нельзя, не потеряв значения. Параметры
типов разнородны (варианты, форматы, размеры), поэтому они остались одним `params`:
десяток почти всегда пустых колонок был бы хуже.

**Три сущности — три запроса.** Настройки списка, вкладки карточки и свойства записей
читаются и пишутся отдельно друг от друга:

| Что | Чтение | Запись |
|-----|--------|--------|
| имя, код, правила записей | `GET /api/infoblocks/settings/:listKey` | `PUT` туда же |
| вкладки карточки | `GET …/:listKey/tabs` | `POST`, `PATCH /:id`, `DELETE /:id` — сразу, по одной |
| свойства записей | `GET …/:listKey/properties` | `POST`, `PATCH /:id`, `DELETE /:id` — сразу, по одному |
| вид таблицы (свой у каждого) | `GET …/:listKey/columns` | `PUT` — видимые колонки целиком; `DELETE` — вернуть по умолчанию |
| поля фильтра (одни на всех) | `GET …/:listKey/filters` | `PUT` — набор целиком |

Свойство и вкладка сохраняются поодиночке, каждое своим запросом: правка одного свойства
не должна переписывать соседей — у них свои значения у записей, и перезапись списком
целиком стирала бы их на ровном месте. Черновик в окне настроек есть только у свойства
(без кода и типа его отправлять нечего), и это черновик **одной** записи: нажали
«Сохранить» в его шторке — ушёл `POST` или `PATCH` с её номером. Окно настроек само
отвечает лишь за настройки списка: имя, код, уровни вложенности, символьный код записей
и мету записей.


Пока настройки не сохраняли, строки нет: API отдаёт пустые настройки — код `null`,
свойств нет, а имя по виду списка (`name` у вида в `infoblock-kinds.ts`, «Роли»;
у вида без имени — ключ списка): оно же заголовок над таблицей. Строку настроек, которую
заводит первая запись внутрь списка, сервер называет так же; код — из ключа
(`infoblock-elements.3` → `infoblock-elements-3`).

### Свойство

Строка `infoblock_settings_properties`; в ответе API — элемент массива `properties`. Общие поля:

| Поле | Описание |
|------|----------|
| `code` | ключ значения: `^[a-z][a-z0-9_]*$`; после сохранения **не меняется** |
| `name` | подпись поля в шторке |
| `hint` | подсказка под полем в карточке записи (до 500 символов, пробелы по краям срезаются); пусто — без подсказки. В теле необязательно: не прислали — подсказки нет. Задают в шторке свойства полем «Подсказка» |
| `type` | тип, см. ниже |
| `required` | без значения запись не сохранить |
| `multiple` | несколько значений; можно включить любому типу, **кроме таблицы** — у неё строки и так добавляются сколько угодно, и вторая таблица от лишних строк первой неотличима |
| `isMultiDomain` | мультидоменное: значение своё на домен, см. ниже; у любого типа. В теле необязательно: не прислали — у нового «выключено», у заведённого «как было». Фронт шлёт его всегда, иначе флаг не выключить |
| `tab` | код вкладки карточки; пусто — общая вкладка «Свойства» |

Настройки отдельных типов — у чужого типа всегда пустые (`[]` / `null`):

| Поле | У какого типа | Описание |
|------|---------------|----------|
| `options` | список | варианты выбора: `{ id, code, name }` (код и название — до 255 символов, строками в `infoblock_settings_property_options`). В значении записи хранится **номер** варианта (`id`): код уходит на сайт, и его можно менять — выбранное у записей останется; название видит редактор. Сохранённый вариант узнаётся по `id`, вариант без `id` — новый; пропавший из списка удаляется. Код уникален внутри свойства, повтор — `400`. В шторке свойства у вариантов колонка «ID» (у нового пусто) |
| `formats` | файл, изображение | допустимые расширения; пусто — любые. У изображения — из JPG, PNG, WebP, GIF, SVG, AVIF; `jpeg` считается `jpg` |
| `maxSizeMb` | файл, изображение | наибольший вес, МБ |
| `maxWidth`, `maxHeight` | изображение | наибольшее разрешение, px |
| `columns` | таблица | столбцов: до 20, по умолчанию 3. Строки задаёт сама запись |
| `headers` | таблица | заголовки столбцов, ровно по их числу; все пустые — шапки нет |
| `linkList` | привязка к записям контента | ключ списка-источника (`pages`, `content-items.8` — элементы одного типа контента): в карточке выбирают запись только из него. **Обязателен** (иначе 400): «любая запись панели» тянула бы в выбор все записи разом. Пусто осталось только у свойств, заведённых раньше, — выбрать в них нечего, пока источник не зададут. Уже сохранённые ссылки на другие списки отбрасываются **по одной**, остальные ссылки свойства остаются |

| Тип | В шторке | Значение |
|-----|----------|----------|
| `string` — строка | однострочный ввод | строка, пробелы по краям срезаются |
| `number` — число | числовой ввод, пустое — «не указано» | число, в том числе дробное и отрицательное |
| `text` — текст | многострочный ввод | строка как есть, с переносами |
| `html` — HTML | два режима: «Визуально» (TipTap — кнопки начертания, заголовков, списков, ссылок, таблиц и вставка изображений) и «HTML» (CodeMirror — разметка как есть, с подсветкой) | HTML-строка как есть |
| `list` — список | выбор из вариантов настройки | **номер** варианта (массив при `multiple`) |
| `file` — файл | загрузка с диска (файл запомнит свойство), выбор из загруженных или внешняя ссылка | номер файла или адрес внешнего `https://…` (массив при `multiple`, можно вперемешку) |
| `image` — изображение | то же, только картинки, с превью | номер файла или адрес внешней картинки (массив при `multiple`) |
| `content-link` — привязка к записям контента | выбор записи из списка-источника (`linkList`, обязателен): страницы, элементы одного типа контента, роли, товары, категории товаров, формы, поля форм — деревом с поиском | `{ listKey, recordId }` (массив при `multiple`) |
| `list-option-link` — привязка к значениям списка | выбор варианта «Списка» другого свойства (`optionsPropertyId` — номер свойства-«Списка» из любого доступного списка) | **номер** варианта (массив при `multiple`), колонка `optionId`, как у «Списка» |
| `content-type-link` — привязка к типу контента | выбор типа из раздела «Контент» (`/admin/contents`); источника не задают — он всегда `contents` | `{ listKey: 'contents', recordId }` (массив при `multiple`) |
| `table` — таблица | сетка: столбцы из настроек, строки добавляются кнопкой | строки ячеек `string[][]`; в строке ровно `columns` ячеек, строк — сколько завели, не больше 50 |

Обязательная таблица — хотя бы одна заполненная ячейка; пустые строки с конца не хранятся
и в потолок 50 строк не считаются.

**Множественное значение у простых типов** (строка, число, текст, HTML) — список полей
со строками «Добавить значение» и «Убрать»; значение записи становится массивом.
У выбора (список, файлы, блоки, привязка) несколько значений умеет сам Select, у таблицы
множественности нет.

**Мультидоменное свойство** (`isMultiDomain`, галочка «Мультидоменное» в «Правилах»
шторки свойства) — значение своё на [домен сайта](domains.md). Значение записи —
список по доменам, общее первым:

```json
[
  { "domainIds": null,   "value": 207, "exceptDomainIds": [3, 5] },
  { "domainIds": [2, 4], "value": 205 }
]
```

`domainIds: null` — общее значение, для всех доменов; остальные элементы — уникальные
значения, каждое сразу для одного или нескольких доменов и поддоменов. `exceptDomainIds`
(только у общего, пустой не отправляется) — «для всех, кроме»: на этих доменах общего
значения нет. Сайт на домене берёт уникальное, если домен есть в одной из групп; иначе
общее, если домен не в исключениях; иначе значения нет. Уникальное значение у домена одно
(домен не может стоять в двух группах), а в исключениях может стоять и домен с уникальным
значением — «всем, кроме msk, а msk своё»: уникальное сильнее, исключение срабатывает там,
где его нет. Исключения уходят как выбраны. Внутри `value` — обычное значение типа, у множественного — массив.

В карточке записи поле — маленькая таблица в рамке (токены темы antd) с шапкой
«Домены | Значение», значок глобуса у подписи. Выбор доменов во всех строках один и тот
же — множественный `Select` (лишние метки сворачиваются в «+N»), поэтому строки одной
высоты. Первая строка — общая, её не убирают: слева текстом «Все домены», под ним
выбор исключений с приставкой «кроме». Под каждой строкой — мелкая подсказка (`fontSizeSM`),
где действует её значение: у общей — как сделать «для всех, кроме» и что будет на
исключённых, у уникальной — «Действует на … вместо общего значения». В подвале таблицы —
кнопка-ссылка «Добавить уникальное значение для домена» и, справа, «Без значения: …» —
домены, где значения не будет: нет уникального, а общее пустое или домен в исключениях
(`uncoveredDomainIds`; у вовсе незаполненного поля список не показывается). Новая строка; в выборе домена строки — домены, которых нет в других строках (исключения общего не мешают), деревом
с полными адресами, выключенный помечен. Строка без доменов или без значения не
отправляется. Обязательность проверяется по общему значению. Значение, сохранённое до
включения флага, читается как общее. В таблице списка — общее значение и «+N доменов»
(сумма доменов во всех группах). Формат и разбор — `logic/domains/domainValues.ts`,
поле — `drawer/DomainValues.tsx`.

**На сервере** (`normalizeDomainGroups` в `settings/properties/property.ts`) каждая группа
проверяется как обычное значение свойства (тип, варианты, файлы, привязки — во всех
группах, `plainValues`), домены — что такие есть (`referencedDomainIds`, иначе `400`
«Домен не найден»). Обязательность — по общему значению. Группа без доменов или без
значения отбрасывается, домен в двух уникальных группах — `400`. Исключения хранятся
при общем значении, поэтому **без общего не сохраняются**: им не на что действовать.
Хранятся группы теми же строками `infoblock_values`, с доменами в своих колонках (ниже).
Удалили домен — он вычищается из всех значений (`PropertyValuesService.forgetDomain`):
из групп и исключений, группа без доменов уходит. Выключили флаг у свойства — читается
только общее значение, строки уникальных лежат, пока флаг не включат снова.

**Символьный код записей — настройка списка, а не свойство.** В окне он один выпадающий
список: «Нет» (поля «Код» у записей нет, колонка в таблице тоже убирается),
«Необязательный», «Обязательный», «Обязательный и уникальный» (перед сохранением код
сверяется с кодами остальных записей списка). По отдельности три флага (`useCode`,
`codeRequired`, `codeUnique`) бессмысленны — уникальность без обязательности нечего
проверять, — поэтому в интерфейсе они одним выбором. «Обязательный» обязателен
у записи на любом уровне дерева, у корневых тоже: исключений по уровню нет.

**Сервер проверяет те же правила.** Сохранение записи сверяет её итоговый код
с настройками списка — общей функцией `assertRecordCode`
(`backend/src/infoblocks/settings/record-code.ts`): пустой код у «Обязательного» — `400`,
код, который уже есть у другой записи того же списка, у «Обязательного и уникального» —
`409`. Итоговый — значит присланный или прежний: правка одного названия у записи
без кода в списке, где код стал обязательным, тоже не пройдёт, как и в карточке.
Настроек списка нет — правил тоже (код необязательный). Уникальность проверяется
запросом, а не индексом: две записи, сохранённые одновременно, могут разминуться.

Проверку вызывают сервисы списков с символьным кодом: страницы, товары, категории
товаров, типы и элементы контента (элементы — в пределах своего типа). Каждый читает
свои настройки сам — общим сервисом это не сделать: модуль настроек импортирует модули
списков, и обратный импорт замкнул бы кольцо (так же устроен предел вложенности,
`tree-depth.ts`). Роли, формы и поля форм проверку не зовут: их код и так обязателен
в DTO, и на нём уникальный индекс — это строже любой настройки. У пользователей,
доменов, файлов, разделов файлов и хранилищ символьного кода нет.

«Нет» прячет поле, но **не отменяет код у записи**: он по-прежнему собирается
из названия и уходит на сервер — иначе запись в разделах, где код обязателен
по самому DTO, просто не создать.

**Код из названия — кнопкой рядом с полем.** У «Кода» записи в карточке, у кода свойства
и у кода варианта «Списка» справа кнопка-переключатель (`contentEditorNew/ui/CodeInput.tsx`).
Нажата — код собирается из названия латиницей одинаково во всех разделах
(`frontend/logic/slug.ts`: «Акции и скидки» → `akcii-i-skidki`, у свойства дефисы
становятся подчёркиваниями) и идёт за каждой правкой названия, а само поле закрыто;
отжата — код набирают свой. У новой записи, свойства и варианта кнопка нажата сразу,
у сохранённых — отжата: их код уже знает сайт (адрес страницы, ключ значения), и
переименование не должно молча его менять. Включить можно в любой момент — код сразу
догонит название. Положение кнопки нигде не хранится: это состояние поля, а не записи.
Повтор кода в списке с уникальностью карточка сама не правит — говорит, что такой код
уже есть. Длина кода обрезается до 64 символов — столько принимают поля кодов на сервере.

**Своей меты у записей нет.** H1, Title, Description и прочее, что нужно сайту, заводят
обычными свойствами списка — отдельной галочки «Мета записи» и колонок под неё больше нет.

**Свойства неизвестного типа отбрасываются при чтении.** В настройках, сохранённых
прежними версиями, встречаются типы, которых больше нет (был тип «мета»): без этого
такие настройки нельзя было бы ни сохранить (enum в DTO их не принимает), ни показать.

### `infoblock_records` — записи списка глазами настроек

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `settingsId` | `INTEGER` | настройки списка; `ON DELETE CASCADE` |
| `recordKey` | `STRING` | ключ записи — тот же, что в адресе админки и в журнале (`2`, `element-7`) |
| `parentId` | `STRING \| null` | родитель в дереве списка — у списков, где дерева нет в своей таблице |
| `externalId` | `VARCHAR(255) \| null` | внешний ID — номер записи в системе-источнике (учётной, складской) |

Индексы: `infoblock_records_settings_key` (`UNIQUE (settingsId, recordKey)`),
`infoblock_records_external_id` (`UNIQUE (settingsId, externalId) WHERE externalId IS NOT NULL`).

Родитель лежит колонкой, а не свойством: это **настройка списка**, а не поле,
которое заводит пользователь.

**Внешний ID** есть у записи любого списка, поэтому он здесь — в единственной строке,
общей на все списки, а не в таблицах разделов; удалили запись — ушёл и он. Уникален
внутри списка, пустые не мешают друг другу. Задаёт его только интеграция:
`PATCH …/values/:recordId` принимает `externalId` (пустой или `null` — стереть, занятый
другой записью — 409), только если в JWT есть `via` — то есть от внешнего API или MCP;
из панели — 400 «Внешний ID задаёт только интеграция». Правка внешнего ID — в журнал
под ключом `externalId` и двигает «Изменено». Наружу он уходит полем `externalId` записи:
его добавляет `RecordsService.rows` — в страницу таблицы, во внешнее API и MCP;
карточка записи показывает его внизу вкладки «Запись», если заполнен. Запись по нему
ищут запросом по индексу — `PropertyValuesService.recordIdByExternalId`.

### `infoblock_values` — значения свойств, по строке на значение

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `recordId` | `INTEGER` | запись (`infoblock_records`); `ON DELETE CASCADE` |
| `propertyId` | `INTEGER` | свойство (`infoblock_settings_properties`); `ON DELETE CASCADE` |
| `sort` | `INTEGER` | порядок значения у множественного свойства; у одиночного `0` |
| `text` | `TEXT \| null` | строка, текст, HTML, код блока, адрес внешнего файла |
| `number` | `DOUBLE \| null` | число, номер своего файла или изображения |
| `json` | `JSONB \| null` | таблица и обе привязки: у них структура, а не значение |
| `optionId` | `INTEGER \| null` | вариант «Списка» (`infoblock_settings_property_options`); `ON DELETE CASCADE` — убрали вариант, ушли его значения |
| `domainIds` | `INTEGER[] \| null` | только у мультидоменного свойства: домены уникального значения; `null` — общее, для всех доменов. Ссылок нет — удаляя домен, его вычищают из значений сами |
| `exceptDomainIds` | `INTEGER[] \| null` | только у строк общего значения: домены, на которые оно не распространяется |

Индексы: `(recordId, propertyId, sort)` — уникальный, плюс `(propertyId, text)`,
`(propertyId, number)` и `(propertyId, optionId)` под будущие фильтры и сортировку
по значению свойства, GIN по `domainIds` — под «значения для домена» — и
`infoblock_values_property_link` — `(propertyId, (json->>'recordId'))`: по нему внешнее API
отбирает записи по привязке (`PropertyValuesService.linkedRecordIds`), не читая значений
списка (миграция `0003-link-values-index`).
У мультидоменного свойства `sort` сквозной по всем группам записи: строки одной группы
идут подряд, порядок групп — по первой строке.

**Строка на значение, а не JSON на запись.** По строкам можно искать, фильтровать
и сортировать — ради этого и колонка под значение у каждого вида своя: сортировать число
как текст нельзя («12» меньше «9»). И главное: значение привязано к **номеру** свойства,
а у «Списка» — и к номеру варианта, а не к кодам — код правят, и значения от этого больше
не страдают (раньше смена кода их стирала).

Значения и дерево лежат **отдельно от таблиц разделов**: так свойства заводятся у любого
списка, не трогая модель раздела.

### Системные свойства

Свойства, которые заводит сам сервер, а не пользователь: на них держится что-то вне
списка. Сейчас это **«Адрес» у страниц** (`pages`, код `url`, строка — сегмент адреса,
[`pages.md`](pages.md)), **подключение у внешних хранилищ** (`storages`, шесть строк:
`endpoint`, `region`, `bucket`, `accessKey`, `secretKey` — скрытое, `publicUrl` —
[`settings.md`](settings.md)), **«Роль» у пользователей** (`users`, код `role`, привязка
к контенту из списка `roles`, одно значение), **«Категории» у товаров** (`products`,
код `categories`, привязка к списку `product-categories`, несколько значений —
[`products.md`](products.md)), **«Поля» у форм обратной связи** (`forms`, код `fields`,
привязка к списку `form-fields`, несколько значений, порядок — порядок полей в форме)
и **«Плейсхолдер» у полей форм** (`form-fields`, код `placeholder`, строка —
[`forms.md`](forms.md)). Системному свойству можно задать подсказку (`hint`)
и скрытость (`isHidden`) — сверка выравнивает и их.

- **Перечень — одно место:** `infoblocks/settings/properties/system-properties.ts`,
  ключ — вид списка. У вложенного вида свойство получит каждый его список
  (`infoblock-elements` — записи всех инфоблоков).
- **Сверка — скрипт при старте сервера** (`SystemPropertiesService.onApplicationBootstrap`),
  как и схема базы: свойства всех списков вида приводятся к перечню — нет свойства —
  заводится, есть — выравниваются название, тип, правила, параметры; сортировка `0`,
  вкладка общая. Общему списку настройки заводятся тут же. Новому списку свойства
  заводит `ensureSettingsId` в момент появления его настроек, а у вида с системными
  свойствами настройки заводятся уже при первом чтении свойств — карточка новой записи
  показывает «Роль» сразу.
- **Код занят свойством пользователя:** того же типа — оно становится системным вместе
  со значениями; другого — сверка его не трогает и пишет предупреждение в лог (стереть
  чужие значения она не вправе).
- **Убрали из перечня** — свойство становится обычным (`isBlocked: false`): значения
  остаются, удалить его можно руками.
- **Через API** системное свойство не меняется и не удаляется — `PATCH`/`DELETE` отвечают
  409 «Системное свойство не меняется и не удаляется». `isBlocked` есть только в ответе:
  из тела сервис его не читает. Так же только в ответе — `isFilled`: заполнено ли
  свойство хотя бы у одной записи (от этого зависит смена типа). Значения у записей правятся как у любого свойства.

### Скрытые свойства

Свойство с `isHidden` («Не отдавать через API») — для паролей и ключей, которые нужны
только серверу. Значение сохраняется как у любого свойства, но **наружу не уходит
никаким маршрутом**: ни значениями записи, ни страницей таблицы — их общий выход
(`valueItems` в `values/property-values.service.ts`) скрытые отбрасывает. В снимке
журнала значение заменено на `••••••`: видно, что его меняли, но не на что.

Сам сервер читает значения списка по кодам свойств, вместе со скрытыми, —
`PropertyValuesService.codeValues(userId, listKey)`: так раздел страниц берёт адреса,
а хранилища — ключи.

### Свойства из внешнего источника

Свойство с `isExternal` («Внешний источник») заполняет другая система — учётная,
складская, интеграция, — и правка в панели разошлась бы с ней до следующей выгрузки.
Поэтому `PATCH …/values/:recordId` **из панели** такие значения не принимает: прислали
хоть одно — `400` «Свойство «…» заполняется из внешнего источника — в панели его не
правят». Пишут их только интеграции — внешнее API ключом с правом записи и MCP: их
запросы несут в JWT `via` (см. [`external-api.md`](external-api.md), [`mcp.md`](mcp.md)),
у панели его нет. Условие — `integrationOnlyError` в `property-values.service.ts`. Значения, которые не прислали, правка не трогает — поэтому карточка
записи с таким полем сохраняется как обычно. Отдаются значения как у любого свойства —
и в карточку, и на сайт. `describe_list` в MCP отмечает свойство `isExternal: true`.
Обязательность у такого свойства карточка не проверяет: заполнить его в ней нечем.

### Проверки значений разделом

Свойства общие, а часть правил у значений — раздела: «адрес уникален среди соседей»,
«хранилище отвечает». Раздел добавляет свою проверку для своего вида списка —
`PropertyValuesService.registerCheck(kind, check)` в своём `onModuleInit` (модуль значений
о разделах не знает: они импортируют его, а не наоборот). Проверка (`ValuesCheck`)
получает значения записи **после правки целиком**, по кодам и вместе со скрытыми, плюс
коды присланных свойств (`touched`) — проверять имеет смысл то, что правили. Идёт она
внутри транзакции сохранения: бросила исключение — правка откатывается.
Сейчас проверки две: адрес страницы (`PagesService.checkUrl`) и подключение
хранилища (`StoragesService.checkConnection`).

## API

Все маршруты требуют авторизации, `userId` берётся из JWT. Правка общих списков
и списков из управления панелью — только `root` (см. «Ключ списка»).

| Метод | Путь | Что делает |
|-------|------|-----------|
| `GET` | `/api/infoblocks/settings/link-targets` | что можно выбрать в «Привязке к контенту» |
| `GET` | `/api/infoblocks/settings/link-sources` | списки, которыми привязку ограничивают в настройках свойства |
| `GET` | `/api/infoblocks/settings/:listKey` | настройки списка (пустые, если не сохраняли) |
| `PUT` | `/api/infoblocks/settings/:listKey` | сохранить настройки списка: имя, код, дерево, правила записей |
| `GET` | `/api/infoblocks/settings/:listKey/tabs` | вкладки карточки записи |
| `POST` / `PATCH /:id` / `DELETE /:id` | `/api/infoblocks/settings/:listKey/tabs` | завести, переименовать, удалить вкладку |
| `GET` | `/api/infoblocks/settings/:listKey/properties` | свойства записей списка |
| `POST` / `PATCH /:id` / `DELETE /:id` | `/api/infoblocks/settings/:listKey/properties` | завести, изменить, удалить одно свойство |
| `GET` | `/api/infoblocks/settings/:listKey/columns` | вид таблицы того, кто спрашивает: видимые колонки по порядку `[{ key, width }]`; пусто — не настраивал |
| `PUT` | `/api/infoblocks/settings/:listKey/columns` | сохранить вид целиком: `{ columns: [{ key, width }] }` слева направо |
| `DELETE` | `/api/infoblocks/settings/:listKey/columns` | стереть вид — таблица вернётся к колонкам по умолчанию (`204`) |
| `GET` | `/api/infoblocks/settings/:listKey/filters` | поля фильтра таблицы — ключи колонок по порядку `["name", "property-12"]`; пусто — фильтра нет |
| `PUT` | `/api/infoblocks/settings/:listKey/filters` | сохранить набор полей целиком: `{ keys: [...] }`; пустой — фильтр убран. Ключи без повторов и того же вида, что у колонок, иначе `400` |
| `GET` | `/api/infoblocks/:listKey/values/:recordId` | значения одной записи (карточке, открытой не со страницы таблицы); значений всего списка маршрутом нет — записям страницы они приходят с ней (`/api/infoblocks/records/:listKey`, поле `values`) |
| `PATCH` | `/api/infoblocks/:listKey/values/:recordId` | изменённые значения одной записи |
| `DELETE` | `/api/infoblocks/:listKey/values?recordIds=5,6` | стереть значения удалённых записей |

Значения приходят и уходят **номерами свойств**: `values: [{ propertyId, value }]`. Кодом
их не адресуют — код у свойства правят.

**Вид таблицы пишется целиком (`PUT`), а не по колонке.** Порядок — свойство всего
набора: сдвиг одной колонки переставляет соседей. Чужого это не задевает — вид у каждого
свой. В теле хотя бы одна колонка, без повторов, ключ — буква и дальше латиница, цифры
или дефис, ширина 40–2000 px или `null`; иначе `400`.

Ответ правки — значения записи, **без родителя**: им владеет раздел записи,
а не её значения. Значения в ответе приходят все, а не только тронутые: карточке нужен
итог, чтобы обновиться.

**Правка частичная, поэтому `PATCH`.** В теле только изменённые свойства; чего в нём нет,
сервер не трогает, а чтобы стереть значение, его шлют как `null`. Так карточка не может
ни стереть то, чего не показывала (поля типов, до которых редактор ещё не дорос), ни
переписать чужую правку, сделанную, пока шторка была открыта; и в журнал попадает ровно
то, что меняли. Родителя в теле нет вовсе: он поле самой записи и уходит в запрос её
раздела.

Маршруты и код значений лежат **не под настройками**, а рядом с ними
(`infoblocks/values/`): настройки описывают список, а значения — это данные его записей.

`link-targets`, `link-sources` и `option-sources` объявлены до `:listKey` — иначе Nest
принял бы их за ключ списка. `link-targets?listKeys=pages,content-items.8` отдаёт записи
**только названных списков** (без `listKeys` — пусто): поле привязки смотрит в один
список, таблица — в источники видимых колонок, и все записи панели разом не грузятся.
Списки: страницы, элементы каждого типа контента
(группа «Контент: Новости», ключ списка `content-items.8`), сами типы контента
(группа «Типы контента», ключ `contents` — их выбирает только привязка к типу),
товары и категории товаров, формы обратной связи и поля форм пользователя и роли (они общие):
`{ listKey, recordId, parentId, name, code, group }`. `parentId` — ключ родителя в том
же списке (у страниц, типов и элементов контента, категорий), по нему выбор рисует
дерево; группа элементов подписана путём типа («Контент: SEO / Уникальные описания
товаров»). `link-sources` отдаёт сами списки — `{ id, listKey, name, label, group,
parentKey }`: страницы, каждый тип контента отдельно (его элементы; группа «Контент»,
вложенный тип — под родителем по `parentKey`, `id` — номер типа, `label` — полный путь
для закрытого поля), роли пользователей, товары, категории товаров. Формы обратной связи и поля
форм из `link-sources` убраны, пока раздел скрыт во фронтенде: новое свойство к ним
не привязать, но `link-targets` их записи отдаёт — на них держатся «Поля» у форм
и уже заведённые привязки. Записи инфоблоков
вернутся в оба ответа вместе со своим модулем из `to_delete/`. Инфоблок попадает туда, **даже если записей в нём
ещё нет**: свойство настраивают раньше, чем наполняют список, а `link-targets` строится
из записей и пустой инфоблок бы не показал.
`option-sources` отдаёт свойства-«Списки» всех списков, чьи настройки доступны
пользователю (свои и общие): `{ propertyId, name, listKey, listName }` — из них выбирают
источник привязки к значениям списка. Свойству такой привязки сервер при чтении
подставляет `options` — варианты источника, поэтому карточка, ячейка и фильтр работают
с ним как с «Списком»; свои варианты у привязки не хранятся. Источником может быть
только существующий «Список» из доступного списка и не само свойство (400); «Список»,
на варианты которого смотрит привязка, не удаляется и не меняет тип (409).

Коды ответов: `400` — незнакомый ключ списка, неверный ключ записи, свойства описаны
с ошибкой (повтор кода свойства или варианта, список без вариантов, таблица шире 20 столбцов), значение не
подходит под свойство, файл не подходит под ограничения, привязанной записи нет или
родитель замыкает дерево в кольцо; `403` — правка списка из управления панелью не
главным администратором; `409` — список с таким кодом уже есть, правка или удаление
системного свойства.

## Интерфейс

- **Кнопка «Настройки»** — в шапке каждого экрана редактора контента, рядом с «Добавить».
  Раздел может её убрать (`isListSettingsHidden`): так «Пользователи» и «Роли» не показывают
  её никому, кроме `root`.
- **Окно настроек** — две вкладки antd `Tabs`, окно открывается на первой.
  «Список»: галочка «Древовидная структура» и под ней,
  только когда она стоит, «Уровней вложенности» (от 2; пусто — без ограничения),
  «Символьный код записей», «История изменений» — общей формой, её сохраняет кнопка
  «Сохранить» в шапке. «Свойства записей N»: «Добавить свойство» справа сверху, вкладки карточки записи и их свойства; в строке свойства — перенос на другую вкладку (свойство встаёт последним, системное не переносится) —
  они сохраняются сразу, каждое своим запросом, поэтому и лежат отдельно. Символьный код — один
  выбор из четырёх («Нет», «Необязательный», «Обязательный», «Обязательный и уникальный»),
  а не три галочки: по отдельности флаги `useCode`/`codeRequired`/`codeUnique`
  бессмысленны — уникальность без обязательности нечего проверять. Раскладывает выбор
  обратно во флаги `logic/listSettings/codeMode.ts`.
- **Свойства в карточке записи**: первая вкладка «Запись» — поля раздела и свойства без
  вкладки, дальше вкладки из настроек со своими свойствами. Значения уходят вторым
  запросом (`PATCH …/values/:recordId`) после самой записи: у новой записи ключ появляется
  только после первого. «Таблица» правится сеткой
  (`drawer/TableField.tsx`): столбцы и шапка — из настроек свойства, строки добавляют
  и убирают в карточке, пустые строки с конца не сохраняются. «Файл» и «Изображение»
  правятся (см. ниже), «Привязка к записям контента» — выбором записи
  (`drawer/LinkField.tsx`, `TreeSelect`): из списка, заданного в свойстве, а без него —
  записи грузятся только этого списка; «Привязка к типу контента» — тем же полем,
  только из типов. Выбор — деревом: страницы, типы и элементы контента, категории
  вложены под родителей; выбранное значение и ячейка таблицы подписаны путём от корня
  («Kia / Rio / Седан #23»), иначе одноимённые кузова разных моделей неотличимы
  (`linkPaths`). **У каждой записи в любом выборе — её ID** («Новости #8»): в поле
  привязки, в фильтре, в выборе родителя записи и в дереве источников привязки
  («Откуда выбирать запись» — тоже `TreeSelect`, типы контента в группе «Контент»). Записи для
  выбора поле читает при каждом показе карточки (`logic/contentLinks/`), значение
  в черновике — ключ `список/запись`, в тело запроса оно уходит `{ listKey, recordId }`.
- **Системное свойство** в окне настроек — с отметкой «системное» и замком вместо
  корзины; его шторка открывается на просмотр: все поля закрыты, «Сохранить»
  и «Удалить» нет.
- **Имени и кода списка в окне нет.** Заголовок над таблицей — название пункта меню,
  код задаёт панель: по умолчанию это ключ списка (`pages`, `file-sections`), у элементов
  типа контента — код типа. `PUT …/:listKey` принимает `name`/`code` необязательными
  и без них оставляет прежние.
- **Часть настроек раздел закрывает** (`blockedSettings` у редактора): «Страницы» так
  закрывают уровни вложенности (дерево без предела) — страницы вкладываются друг в друга
  по своей природе; «Файлы», «Хранилища» и «Домены» — «Историю изменений»
  (`isHistoryEnabled: false`): журнала у них нет. Закрытая настройка в окне видна
  и показывает значение раздела с подписью «Задано разделом и не меняется», но не правится,
  и это значение сильнее сохранённого: список с другим значением в базе чинится первым
  же сохранением.
- Свойство правят в его шторке: название, код,
  «обязательное», «множественное», «сортировка», параметры типа и удаление. В «Правилах»
  рядом с «Множественным» и «Мультидоменным» — «Не отдавать через API» (`isHidden`)
  с подсказкой «?»; включённое правило пояснено под ними, в строке свойства — отметка
  «не через API». В карточке записи скрытое свойство — поле пароля (`FieldType.Password`):
  всегда пустое, никогда не обязательное, с пояснением «Значение не показывается после
  сохранения: оставьте пустым, чтобы не менять». Карточка шлёт только изменённые
  значения, поэтому пустое поле значит «прежнее». Там же — «Внешний источник»
  (`isExternal`) с подсказкой «?», в строке свойства — отметка «внешний источник».
  В карточке записи такое поле видно со значением, но закрыто, у подписи — значок
  облака, под полем — «Заполняется из внешнего источника — в панели не правится». Тип
  сохранённого свойства закрыт — его выбирают только при создании. Закрытие
  с несохранёнными правками спрашивает подтверждение.
- **Параметры типа и вкладка — отдельными окнами из меню строки.** В строке свойства
  меню «⋮»: «Параметры свойства» (варианты списка; форматы, вес и разрешение файла;
  столбцы и заголовки таблицы; список-источник привязки) и «Сменить привязку» — на какой
  вкладке карточки показывать свойство. Колонками в таблице и то, и другое занимало место
  у каждой строки, а трогают их редко. У типов, которым настраивать нечего (строка, число,
  текст, HTML, блоки), пункт «Параметры» не нажимается. Своего «Сохранить» у окон нет —
  правки ложатся в черновик свойства и уходят в базу общей кнопкой окна настроек.
- **Вкладки настраиваются вкладками.** В окне настроек свойства разложены по тем же
  вкладкам, что потом в карточке записи, — то есть окно заодно показывает её раскладку.
  Переключение показывает свойства только своей вкладки, в заголовке — их количество.
  «+» на панели открывает попап, где вводится **только название**: кода у вкладки
  пользователь не видит. Вкладка существует лишь в карточке записи — сайт о ней ничего
  не знает и читает значения по кодам **свойств**, — поэтому код генерируется из названия
  («Доставка» → `dostavka`) и живёт как внутренний ключ: по нему свойство привязано
  к вкладке и переживает её переименование. Название открытой вкладки правится справа
  на той же панели.
  Свойство переносится на другую вкладку пунктом «Сменить привязку» в меню строки,
  а порядок полей в карточке задаёт колонка «Сортировка» — число, а не стрелки
  «выше / ниже»: свойство сразу встаёт куда нужно, а не за несколько нажатий. Номера
  идут с шагом 10, чтобы между соседями всегда было куда вписать новое свойство;
  на сервер они не уходят — порядок там задаёт сам массив, и свойства сортируются
  перед отправкой.
  Общая вкладка «Свойства» всегда первая и не удаляется: на неё попадает всё, чему
  вкладку не назначили, и на неё же возвращаются свойства удалённой вкладки.
  Код сохранённой вкладки закрыт: на него ссылаются свойства.
  В карточке записи пустые вкладки не показываются.
- **«Колонки таблицы»** — значок-шестерёнка в заголовке столбца действий
  (`contentEditorNew/table/columns/ColumnSettings.tsx`). Шторка — один список: сначала
  видимые колонки в своём порядке, за ними спрятанные — колонки раздела, потом свойства
  записей с подписью «Свойство · тип». Галочка показывает колонку, стрелки двигают её
  (выше — левее в таблице), ширина пустая — как задал раздел. «Сохранить» недоступна, пока
  ничего не меняли или не отмечено ни одной колонки. «По умолчанию» стирает сохранённый
  вид (с подтверждением) и оставляет шторку открытой уже с колонками раздела; вида нет —
  просто возвращает черновик. Пока вид не пришёл, таблица показывает загрузку: иначе
  колонки по умолчанию мелькнули бы и сменились.
- **Ячейка свойства в таблице** (`table/propertyValue.ts`): строка, число, текст — как
  есть, HTML — текстом без разметки, «Список» — подписи вариантов, «Файл» — имена файлов,
  «Изображение» — превью, обе привязки — название записи или типа,
  таблица — количество строк («3 строки»). Множественное — через запятую.
  Мультидоменное — общее значение и сколько доменов со своим («33_ +1 домен»); фильтр
  ищет по значениям всех доменов. Файлы
  и записи для привязок таблица читает, только если такая колонка видна.
- **Заголовок над таблицей** — название открытого пункта меню (`header/ListTitle.tsx`,
  `useNavigation().currentSection`): «Файлы», «Роли». Раздел может его убрать
  (`isTitleHidden`), если название уже стоит рядом. Шапка — одна строка: заголовок,
  переключатель «Таблица / История изменений» (только если история включена в настройках
  списка; с «Черновиками» — «Все записи / Черновики N / История изменений», см. [`drafts.md`](drafts.md)), справа «Экспорт» (только у таблицы; раздел может убрать — `isExportHidden`), «Настройки» и «Добавить». Под ней, только у таблицы, — плашка
  на сером фоне (`filters/FilterPanel.tsx`): строка поиска и строка фильтра.
- **Страницы** — таблица получает с сервера только свою страницу:
  `GET /api/infoblocks/records/:listKey` (модуль `infoblocks/records/`, один на все списки)
  с параметрами `page`, `pageSize` (20 / 50 / 100), `search`, `searchIn`, `sort`, `order`,
  `isTree`, `isDraft` (вид «Черновики»), `filters` (JSON-массив полей `{ key, kind, … }`) →
  `{ items, total, values, drafts, draftsCount }` — отбирает с черновиками поверх, отдаёт
  опубликованное и черновики записей страницы рядом ([`drafts.md`](drafts.md));
  `values` — значения свойств только записей страницы, ими живут её ячейки свойств
  и карточка записи. Карточка записи не со страницы (из журнала) догружает свои
  значения одним запросом и до их прихода полей свойств не показывает.
  Записи сервер берёт у сервиса раздела теми же правилами, что его `GET` (владелец,
  вычисляемые поля), значения свойств — у `values/`, а отбирает общей чистой функцией
  `pageRecords` (`records/records-page.ts`). **У дерева страница — записи верхнего уровня,
  каждая со всей веткой**: ветка страницей не рвётся, строк на странице может быть больше
  её размера, `total` — число записей верхнего уровня; запись с потерянным родителем или
  из кольца встаёт наверх. Найденное и отобранное — плоским списком, `total` — найденных.
  Сортировка — по полю записи (числа числом, строки по алфавиту, пустое в конце), у дерева —
  среди соседей на каждом уровне; равные — новые сверху. **По умолчанию — по полю
  «Сортировка» (`sort`) по возрастанию** (и у таблицы, и у маршрута без `sort`); у списка
  без этого поля (файлы) все равны — значит, новые сверху.
- **Даты записи** — `createdAt` и `updatedAt` (ISO) отдаёт DTO записи каждого списка.
  **«Изменено» учитывает и правку свойств**: значения лежат отдельно от записи, поэтому
  сохранение значений, которое что-то поменяло (значение или родитель в дереве настроек),
  отмечает время в строке `infoblock_records` (`updatedAt`); то же самое ещё раз дату
  не трогает. Страница записей подставляет в `updatedAt` позднее из двух
  (`withEditedAt`, `records/records-page.ts`) — до отбора, так что сортировка идёт по нему же.
  Весь список (`GET` раздела) отдаёт дату правки самой записи, без свойств.
  В таблице это системные колонки «Создано» и «Изменено» — после колонок раздела, видны
  по умолчанию, сортируются, в фильтр не встают (у них своя подпись); раздел может
  описать колонку с тем же ключом сам — тогда она вместо системной («Загружен» у файлов).
  В карточке сохранённой записи — внизу вкладки «Запись», на просмотр (`drawer/RecordDates.tsx`).
- **Быстрые действия** — галочка в каждой строке; пока что-то отмечено, у нижнего края
  экрана по центру раздела всплывает тёмная плавающая панель: «Отмечено: N»,
  «Активировать», «Деактивировать», «Удалить» (красным) и крестик «Снять отметку».
  Кнопки — по тому, что умеет Api раздела (`remove`; `update` и поле «Активность»);
  нечего предложить — нет и галочек. Каждая запись правится своим маршрутом раздела,
  как из карточки: проверки и журнал те же, ошибка одной не останавливает остальные —
  итог сообщением («Удалено: 12», первая причина отказа и сколько ещё). Уже включённые
  повторно не включаются. Удаление спрашивает; защищённые записи и записи, чей предок
  тоже отмечен, пропускает. Отметка живёт на одной странице: перелистнули или нашли другое —
  снимается с ушедших строк; та же страница, перечитанная заново, её не теряет;
  после быстрого действия она снимается целиком. Листалка под таблицей видна, когда записей (у дерева —
  верхнего уровня) больше 20. Сервер пока читает записи раздела целиком и отбирает в памяти:
  наружу уходит только страница, а до запросов к базе с `LIMIT` дело дойдёт по разделам,
  когда списки вырастут.
- **Экспорт в CSV** — кнопка «Экспорт» в шапке таблицы (`contentEditorNew/export/`);
  раздел убирает её `isExportHidden` (так сделано у разделов «Файлов»).
  Окно с галочками: «Поля записи» (ID и колонки раздела) и «Свойства» (с подписью типа),
  «Выбрать все»; при открытии отмечено то, что видно в таблице. В файл уходят **все**
  записи, отобранные поиском и фильтром, со всех страниц, в порядке сортировки таблицы,
  плоским списком (у дерева тоже). Своего маршрута у выгрузки нет: страницы
  `GET /api/infoblocks/records/:listKey` по 100 подряд тем же запросом, что лежит
  в `page.query` (`exportEditorRecordsThunk`), в стор не кладутся. Значения — те же
  подписи, что в ячейках (`table/propertyValue.ts`), у «Изображения» — адреса картинок.
  Файлы и записи привязок грузятся, только если такое свойство отмечено. Файл —
  `<код списка>-<дата>.csv`, разделитель `;` и BOM в начале (`logic/csv.ts`): так его
  открывает Excel с русской локалью.
- **Поиск** (`table/search.ts`) — всегда, по номеру записи (ID, целиком: «12» не находит
  112; можно с `#`), по символьному коду записи (пока его не выключили в настройках списка)
  и по колонкам раздела с `isSearch` — по полю записи (адрес страницы — поле `path`,
  его собирает сервер). Подсказка в поле перечисляет, по чему ищут: «Поиск: название, ID, код».
- **Колонка ID** — номер записи, сортируется числом. Раздел её не описывает: редактор
  ставит её первой в любой таблице (`ID_COLUMN_KEY` в `table/columns/columnView.ts`,
  ширина по умолчанию 50 px), но в «Колонках таблицы» она такая же, как остальные —
  её прячут, переставляют, меняют ширину. В фильтр не встаёт: номер целиком находит
  строка поиска.
- **Ширины колонок точные** (`tableLayout="fixed"`): галочки — 48 px, остальные —
  как задал раздел или пользователь. Тянется одна колонка — **главная**, первая видимая
  после ID, кроме превью файла (обычно название): она забирает свободное место, ширина ей не задаётся
  (в шторке поле закрыто, «всё место»). В ней же ветки дерева и ссылка в запись.
- **Фильтр** (`contentEditorNew/filters/`). «Добавить условие» в конце строки фильтра —
  меню всех полей, по которым можно фильтровать: сначала колонки раздела, за чертой свойства записей (те же,
  что в «Колонках таблицы», кроме превью и колонок со своей подписью — размер, дата,
  «Привязан к»: сервер сверяет поле записи, а не подпись; логические колонки остаются). У поля, стоящего в фильтре, — галочка; клик
  ставит поле в фильтр или убирает, меню при этом не закрывается — закрывают его кнопкой
  или кликом мимо. Поле в фильтре — чип (`FilterChip`): пустое — пунктиром с именем поля,
  с выбранным — подсвечено («Активность: **Да**», «Статическая +1», «содержит «фар»»)
  и с крестиком, который очищает выбор. Клик по чипу открывает выбор: галочки вариантов
  (с поиском, если их больше 8; у привязки — деревом), подстрока, диапазон
  или «заполнено»; внизу «Убрать из фильтра» и «Готово». Таблица отбирается сразу.
  Справа в строке, если что-то набрано или выбрано, — «Сбросить» (очищает поиск и выбор,
  поля остаются). Поле фильтра адресуется ключом колонки (`name`, `property-12`), видна
  колонка в таблице или нет.

  **Набор полей общий**: поставил или убрал поле один — оно появится или пропадёт
  у всех, кто видит список (`/api/infoblocks/settings/:listKey/filters`). Набор уходит
  на сервер через 400 мс после последней отметки — несколько полей подряд одним
  запросом; ушёл из раздела раньше — уходит сразу. Не сохранился — сообщение, таблица
  отобрана и так. **Выбранное — в адресе**, у каждого своё: `?f.<ключ>=…` рядом
  с собственными параметрами страницы (`sectionId`, `id`), без записи в историю —
  «назад» уводит со страницы, а не по буквам фильтра. Варианты — по параметру
  на вариант (у «Списка» — номер варианта: `f.property-223=12&f.property-223=13`), подстрока — как есть,
  диапазон — `1..10` (с одной стороны можно пусто: `..10`), «заполнено» — `filled` /
  `empty`. Вид поля берётся из колонки, а не из адреса: непонятное значение — пустое
  поле. Выбранное в поле, которого в наборе нет, не действует. Что выбирают, решает
  поле (`filters/columnFilter.ts`):

  | Поле | Поле фильтра | Подходит запись, у которой |
  |------|--------------|----------------------------|
  | колонка раздела (название, код, адрес…) | подстрока | поле записи содержит её, без учёта регистра |
  | логическая колонка раздела (ключ на `is`: активность, вход) | «да» и «нет» с подписями колонки («Да / Нет», «Разрешён / Отключён»); в адресе — `true` / `false` | поле записи — выбранное |
  | «Список» | варианты списка, можно несколько | есть хоть один выбранный вариант |
  | «Привязка к записям контента» | записи списка-источника лесенкой по дереву (марка → модель → кузов), можно несколько; галочка у родителя отмечает всю ветку, снятая у ребёнка снимает и родителя (у него — полугалочка); в поиске найденное подписано путём, на чипе отмеченная ветка — одной записью («Kia #21») | есть хоть одна выбранная запись |
  | «Привязка к значениям списка» | варианты свойства-«Списка», можно несколько | значение — один из выбранных |
  | «Привязка к типу контента» | типы контента, можно несколько | есть хоть один выбранный тип |
  | строка, текст, HTML | подстрока | значение содержит её, без учёта регистра; у HTML — текст без разметки |
  | число | диапазон «от — до», границы включительно | значение в диапазоне |
  | файл, изображение, таблица | «Заполнено / Не заполнено» | свойство заполнено (или нет) |

  У множественного свойства достаточно одного подходящего значения. Поля фильтра
  складываются по «и», пустое поле никого не отсеивает. Отбирает **сервер**, сразу,
  без «Применить»: выбранное уходит в запрос страницы (с паузой 250 мс на набор).
  Как и найденное поиском, отобранное показывается **плоским списком** — в дереве
  совпадения прятались бы в свёрнутых ветках; ничего не подошло — «Ничего не нашлось».
  Колонка раздела фильтруется по **полю записи**, а не по подписи в ячейке. Пока набор
  полей не пришёл, страницу не спрашивают: иначе весь список мелькнул бы перед
  отобранным по адресу. Свойство удалили, пока стояло в фильтре, — его поле пропадает
  и не отбирает.
- **Файл и изображение** (`contentEditorNew/drawer/FileField.tsx`): выбранные файлы
  строками (превью, имя-ссылка, размер, крестик «Убрать файл»), «Загрузить»
  и «Выбрать из загруженных» — шторка поверх карточки с деревом разделов и файлами
  с превью (`drawer/FilePickerDrawer.tsx`, подробно — в [«Файлах»](files.md)); под полем —
  что подойдёт («JPG, PNG · до 2 МБ · до 1920×1080 px»). Одиночное поле с выбранным
  файлом кнопок не показывает: файл сначала убирают. Файл с диска проверяется до загрузки (изображение ли, формат, вес,
  разрешение), уходит сразу и запоминает свойство — в [«Файлах»](files.md) он в разделе свойства;
  к записи привязывается её сохранением. Файла, которого больше нет, — «Файл №N».
- **Свойству «Файл» и «Изображение» заводится раздел в «Файлах»** (свойству «HTML» — при первой загрузке картинки в текст) — при создании
  свойства (у свойств, заведённых раньше, — при первой загрузке через них). Раздел
  называется «список: свойство» и не удаляется, пока свойство есть.
- **HTML** (`drawer/html/`): переключатель «Визуально / HTML» над полем.
  «Визуально» — TipTap: жирный, курсив, подчёркнутый, зачёркнутый, H2/H3, списки,
  цитата, ссылка, **изображение** (загрузить с диска или выбрать из загруженных — файл
  запоминает свойство (в «Файлах» — раздел свойства), в текст встаёт `<img src="/uploads/…">`),
  таблица (вставить 3×3, строки, столбцы, шапка, удаление), отмена. «HTML» — CodeMirror:
  разметка как есть. Визуальный режим держит разметку по своей схеме (`htmlMarkup.ts`)
  и чужое — `div`, `span`, классы, стили, `iframe` — при правке выбросит, поэтому
  значение с такой разметкой открывается в «HTML», а переход в визуальный —
  только после предупреждения с перечнем того, что пропадёт. Пустой визуальный
  документ — пустая строка, а не `<p></p>`: обязательность проверяется честно.
  Картинки внутри HTML в привязки файла («где используется») не попадают: значение
  свойства — строка, а не номер файла; удалённый файл оставит в тексте битую картинку.
- **Привязки к записям и к типу контента** — выбор из списка; удалённое помечается («… — запись удалена»).
- **Таблица** — сетка ячеек: столбцы из настроек, «Добавить строку» и корзина у строки.
- **Дерево** — когда уровней вложенности больше одного (или без ограничения): строки
  вкладываются по родителям, в карточке — поле «Родитель» (все записи списка, кроме самой
  записи и её ветки, и без тех, под которыми ветка вышла бы за предел; пусто — в корне).
  У «Страниц» предел закрыт: дерево без ограничения.

## Правила и ограничения

- **Значения проверяются по настройкам на сервере**: тип, обязательность, варианты
  списка, размер таблицы; сверх того — проверкой раздела, если он её добавил
  (адрес страницы, подключение хранилища). Незнакомые коды отбрасываются молча — свойство могли удалить,
  пока форма была открыта.
- **Ссылаться можно только на своё**: файлы, блоки и привязанные записи проверяются
  на владельца, чужой номер — `400`.
- **Файл проверяется по ограничениям свойства** на сервере: формат по расширению, вес
  по карточке файла, «только изображения» по MIME-типу. **Разрешение изображения
  проверяет только шторка**, загрузив картинку: в карточке файла размеров нет.
- **Тип свойства меняется, пока это не портит значения** (`canChangeType` —
  одна функция на сервере и в `logic/listSettings`). Значения записей лежат так, как
  их понимает тип: у каждого своя колонка (`text`, `number`, `optionId`, `json`),
  и «12 шт.» числом не станет. Поэтому:
  - **свойство нигде не заполнено** (ни одной строки в `infoblock_values`) — тип
    меняется на любой;
  - **заполнено** — только между строкой, текстом и HTML: у них одно значение — текст
    в `text`, и новый тип читает его как есть;
  - иначе `PATCH` отвечает 409, а шторка закрывает недоступные типы в выборе (нечего
    выбрать — закрыто всё поле) и под полем объясняет, почему. Нужен другой тип —
    заводят новое свойство.

  Заполненность сервер считает сам и отдаёт в свойстве флагом `isFilled` (только
  в ответе). Сменили тип — параметры прежнего обнуляются, варианты «Списка» удаляются,
  ставшему «Файлом»/«Изображением» заводится раздел в «Файлах», а переставшему им быть
  раздел отпускается, как при удалении свойства.
- **Удаление свойства стирает его значения** у всех записей списка — каскадом,
  в той же транзакции. Смена кода значения не трогает: они привязаны к номеру
  свойства, а не к коду.
- **Чтение мягкое**: что под текущие настройки уже не подходит (вариант убрали из списка,
  свойство стало одиночным, таблицу уменьшили), не отдаётся или приводится — из массива
  у одиночного берётся первое значение, таблица обрезается до нового размера.
- **Свойства и родитель сохраняются вторым запросом** — после того как раздел сохранил
  запись и выдал её ключ. Не прошли — запись всё равно сохранена: шторка пишет «Запись
  сохранена, а свойства — нет», форма остаётся изменённой, повторное «Сохранить» отправит
  их снова (у новой записи — уже без повторного создания).
- **Правка свойств и родителя пишется в журнал раздела** под ключом самой записи, поэтому
  видна во вкладке «История» рядом с правками остальных полей («Цена», «Родитель»).
  Снимок такой строки — только свойства и родитель. Код и название записи берутся из её
  последней строки в журнале. У разделов файлов журнала нет — правки их свойств не пишутся никуда
  (`hasJournal: false` в настройках списка); в окне переключатель истории у них
  закрывает раздел.
- **Дерево**: запись нельзя вложить в саму себя и в свою ветку (`400`). Запись, чей
  родитель исчез из списка, показывается в корне. Удаление записи не уносит вложенные —
  раздел удаляет только её, а сервер поднимает её детей к её родителю. Выключенное дерево
  родителей не стирает: включат снова — вернётся как было.
- **Удаление записи стирает её значения** отдельным запросом после удаления; у раздела со
  своей вложенностью (страница уходит с дочерними) — значения всей ветки.
- **Пока настройки списка не загрузились, записи не показываются**: запись, открытая по
  адресу, прочиталась бы без свойств, и сохранение стёрло бы её значения.
- **Файлы перечитываются при каждом показе поля файла**, записи для привязки — при
  каждом заходе в список: их правят в других разделах.

Известные ограничения:

- Каскадное удаление между списками значения не убирает: тип инфоблока уносит инфоблоки
  и их записи, а их значения и настройки вложенных списков остаются. Номера записей не переиспользуются, поэтому чужим они не достанутся,
  но строки лежат.
- Блок «Контента» и запись, выбранные в свойстве, удалить не мешают: проверка «где
  подключён» у блоков ищет только маркеры в разметке, у записей её нет. Файл удалить
  можно — его значения у записей стираются вместе с ним.
- Разрешение изображения на сервере не проверяется (см. выше).
- Колонки свойств не сортируются и поиск по ним не идёт: поиск — по номеру, коду
  и колонкам раздела с `isSearch`, видны они или спрятаны.
- Колонка, которую раздел добавит в код, у пользователя с сохранённым видом не появится
  сама — она будет в шторке спрятанной (или после «По умолчанию»).
- Значения свойств таблица берёт те, что пришли при первом показе списка, плюс правки
  из своей же карточки; чужая правка видна после перезагрузки страницы.

## Настройки

Своих переменных окружения нет. Схема приводится к моделям при старте
(`synchronize: true`), отдельных миграций нет. Визуальный редактор — пакет `quill` (2.x)
во фронте; подгружается только в браузере.
