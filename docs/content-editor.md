# Редактор контента

Универсальный компонент для управления списками записей: **таблица + шторка редактирования**.
Один на всю панель — разделы отличаются описанием полей, а не своим экраном. Первый
потребитель — [«Страницы»](pages.md); следом на него сядут инфоблоки и контент.

Редактор ничего не знает о разделе: раздел отдаёт ему **Api** (где лежат записи)
и **описание** (как они выглядят). Всё остальное — загрузка, состояние, значения
карточки, сохранение, удаление, история — делает сам редактор, одинаково для всех
разделов. Данные всех списков лежат в одном срезе `state.lists`, по ключу списка.

Сама форма — общий слой панели: поля описываются данными, а рисуют их одни и те же
компоненты и в шторке, и на отдельных экранах. Контракт полей и состояние формы —
в [`docs/editor-form.md`](editor-form.md).

## Контракт раздела

```tsx
<ContentEditor
  api={featureApi}
  list={{ title: 'Записи раздела', addLabel: 'Добавить запись', columns }}
  form={{ fields, tabs }}
  history={{ fieldLabels: FEATURE_HISTORY_LABELS }}
  settings={{ key: ListKey.feature }}
/>
```

### Api — где лежат записи

`EditorApi` (`logic/contentEditor/editorApi.ts`) — единственное, что раздел рассказывает
о данных:

| Метод | Зачем |
|-------|-------|
| `key` | ключ списка: ячейка в `state.lists` и ключ настроек списка |
| `list()` | весь список записей |
| `create(payload)` / `update(id, payload)` | запись; создание отличается только отсутствием ключа |
| `remove?(id)` | не задан — удалять нельзя (так у «Пользователей») |

Журнала в Api нет намеренно: история — отдельная сущность, общая на всю панель,
и редактор читает её сам по `key` (`logic/contentEditor/listHistory.ts`).

Ключ записи у Api строковый — тот же, что в адресе страницы и в журнале (`2`, `form-1`,
`element-3`). Перевод в номер или в путь с владельцем — внутри Api раздела: это
единственное место, где такие подробности остались.

### Описание — как записи выглядят

| Проп | Что отдаёт раздел |
|------|-------------------|
| `list` | `title`, `addLabel`, `columns`, `readOnly?`, `supportsNesting?`, `removeKeepsChildren?` |
| `form` | `fields`, `tabs`, `derive?`, `deriveNew?` |
| `actions?` | `canRemove?(record)`, `rowAction?` |
| `history?` | `fieldLabels?`, `canOpenRecord?` |
| `settings?` | `{ key, appliesTo? }` — ключ списка и у каких записей есть свойства |

Своих `valuesOf` и `emptyValues` у раздела нет: значения карточки редактор читает
**по описанию полей** (`recordValues`), приведение выводится из типа поля —
выключатель через `!== false`, число через `Number`, текст через `String`. У новой
записи значения берутся из `defaultValue` поля, а порядок редактор считает сам —
за последней записью списка. Тело запроса собирается так же (`recordPayload`):
у необязательного поля (`nullable`) пустая строка уходит как `null`.

Слоты для разделов, которые не сводятся к плоскому списку:

| Слот | Зачем | Пример |
|------|-------|--------|
| `form.fields` функцией | описание зависит от самого списка | «Родитель» перечисляет остальные страницы |
| `form.derive(record, items)` | значение не лежит в записи | — |
| `form.deriveNew(parentId, items)` | то же у новой записи | адрес будущей страницы, порядок среди будущих соседей |

**Дерево раздел не строит.** `list.supportsNesting` — и редактор собирает строки
по `parentId` самой записи (`useListData`), тем же способом, что и дерево из настроек
списка. У «Страниц» своего осталось только описание полей функцией и `deriveNew`:
адрес сохранённой страницы считает её Api при чтении списка, и дальше он лежит
в записи как обычное поле.

`actions.rowAction` нужен разделам, где запись сама открывает список: у инфоблока это его записи,
и вести к ним должна строка, а не панель рядом. Разметку действие не несёт — раздел задаёт
имя иконки (`EditorRowActionIcon`), подсказку и обработчик, а у каких строк действие есть,
решает `visible(record)`. Переход идёт через ту же очередь, что открытие и создание:
несохранённые правки он не теряет. Пример — [«Инфоблоки»](infoblocks.md).

Колонка тоже описывается данными (`EditorColumnDef`): `dataIndex` или `value(record)` —
что показать, `hint(record)` — вторая строка мелким шрифтом, `variant` — как выглядит:
`text`, `code` (моноширинный — коды и адреса), `tag`, `flag` (да/нет меткой) и `image`
(превью по адресу из значения; значение пустое — таблица рисует значок файла, так что
раздел сам решает, у каких строк превью есть — см. [медиатеку](files.md)).

Иконок у действия две: `enter` — внутрь записи, к её собственному списку; `open` — открыть
во внешней вкладке то, на что запись ссылается (файл медиатеки). Что именно делать, решает
`run(record)` раздела.

`settings` — у списка есть [настройки](list-settings.md): в шапке появляется кнопка
«Настройки» (имя, код, древовидная структура, свойства записей). Раздел называет только
ключ своего списка (`ListKey` из `logic/listSettings`) — остальное редактор делает сам
(`logic/contentEditor/useListProperties.ts`): подмешивает поля свойств и вкладку «Свойства»,
значения в `valuesOf`/`emptyValues`, подписи в историю, имя из настроек в заголовок;
у плоского списка с включённым деревом собирает строки в дерево по родителям, включает
«добавить внутрь» и поле «Родитель». Свойства и родитель сохраняются отдельным запросом
после `save` раздела — с ключом, который тот вернул. `appliesTo(values)` нужен, когда
в списке две сущности: в «Веб-формах» свойства есть у форм, но не у их полей.

`removeKeepsChildren` — удаление записи не уносит вложенные, они поднимаются на уровень
выше: так ведёт себя дерево из настроек списка. Подтверждение удаления говорит об этом,
а не про «удалится всё, что внутри». Раздел сам это поле не задаёт.

`readOnly` — раздел открыт только на просмотр: кнопок «добавить», «сохранить» и
«Настройки» нет. Права решает сам раздел (в [«Пользователях»](users.md) правит только
`root`) — редактор лишь убирает то, чем всё равно нельзя воспользоваться; сами поля раздел
гасит через `disabled` у поля, чтобы форма осталась читаемой.

Подключение раздела — одна строка на экране: контроллер приходит **пропсом**.

```tsx
export default function PagesScreen() {
  useLoadPages();                                  // данные раздела — один раз на экран
  const controller = usePagesController();

  return <ContentEditor controller={controller} />;
}
```

## Откуда что приходит

У редактора ровно два источника, и сходятся они в одном файле —
`components/contentEditor/ContentEditor.tsx`:

| Что | Откуда | Почему так |
|-----|--------|-----------|
| **Контроллер раздела**: данные, описание полей, сохранение | пропс `controller` | в нём функции (`save`, `valuesOf`, `options(values)`) — в сторе им не место |
| **Состояние**: что открыто, что набрано в форме, что изменено | стор, `state.contentEditor` | источник один и видимый: в devtools сразу понятно, какая запись открыта и чем форма отличается от сохранённой |
| **Свойства из настроек списка** | `useListProperties` подмешивает их к полям контроллера | дальше таблица и шторка о свойствах не знают ничего |

Своего контекста у редактора нет: `ContentEditor.tsx` раздаёт частям ровно то, что они
рисуют, и это видно в их сигнатурах — `<ContentEditorTable rows columns selectedId onOpen actions />`,
`<ContentEditorDrawer open title tabs … />`. Читая любой файл редактора, видно, откуда
пришли его данные; `useSelector` в компонентах нет — он в
`logic/contentEditor/useEditorState.ts`, как и требуют
[правила слоёв](../webSite/frontend/CLAUDE.md).

Единственный контекст внутри — `EditorFormProvider` общего слоя форм: поля лежат
глубоко внутри вкладок и групп, и значения туда идут через него (тот же механизм
используют «Настройки» и окно настроек списка).

Что умеет строка таблицы, собрано в один объект `actions` (`EditorRowActions`):
удаление, «добавить внутрь», переход внутрь записи. Отдельными пропсами это была бы
россыпь из девяти штук на каждую строку.

Срез один на все разделы и переживает уход с экрана, поэтому у каждого захода в редактор
свой `sessionId`: пока в срезе лежит состояние прошлого раздела, редактор работает с пустым.
Чистит срез эффект, то есть кадром позже, — без этой сверки новый раздел на первом кадре
рисовал бы чужой журнал или чужую шторку «Новая запись» и успевал бы отправить лишний запрос.

Форма читается прямо из записи тот кадр, пока стор не догнал смену открытой записи, —
иначе шторка моргала бы пустыми полями при каждом открытии.

После сохранения исходными становятся **отправленные** значения, а не те, что лежат в форме
в момент ответа сервера: пока запрос летел, пользователь мог продолжить править, и эти правки
на сервер не ушли — форма обязана остаться изменённой.

## Поля формы

Поля описываются данными общего слоя форм — `EditorFieldDef` и `EditorFieldGroup`
(`logic/editorForm/`), полный контракт в [`docs/editor-form.md`](editor-form.md):
`type`, `required`, `note`, `options`, `hidden(values)`, `disabled(values)`,
`onChange(value, values)`, `validate(value, values)`.

Ключ поля — плоская строка, в том числе с точкой (`props.title`). Вложенных объектов в
значениях формы нет: превращение в тело запроса — забота контроллера раздела.

Редактор добавляет к этому вкладки: группы полей раскладываются по `EditorTabDef`,
вкладка «История» добавляется сама. Пустые группы и вкладки не показываются.

## Подстановка переменных

Поле-шаблон (`variables`) показывает список переменных, предпросмотр подстановки и
предупреждение о незнакомых именах — это тоже общий слой форм,
см. [`docs/editor-form.md`](editor-form.md#подстановка-переменных).

## Несохранённые правки

Форма считается изменённой, пока значения отличаются от тех, с которыми её открыли
(`isChanged` из состояния формы).
Любое переключение — закрытие шторки, выбор другой записи, добавление новой — при
несохранённых правках сначала спрашивает подтверждение (`UnsavedChangesModal`).
Само окно живёт в компонентах, решение о нём — в `useEditorState`: logic-слой разметку не рисует.

## Журнал изменений

Таблица `history` общая на все разделы: `entity` (раздел), `entityId` (запись строкой),
`action` (`create` / `update` / `delete`), `changes` (изменённые поля с «было/стало»),
`snapshot` (состояние записи целиком), автор (`authorId`, `authorName`, `authorEmail`,
`authorIp`) и дата.

- Изменённые поля считаются сравнением плоских снимков; `update` без единого отличия
  в журнал **не попадает** — иначе его заполнили бы «открыл и сохранил».
- Ключи снимка совпадают с ключами полей формы, поэтому в истории видно «Цена
  (price)», а не «изменились свойства». Подписи даёт раздел через `historyFieldLabels`.
- Автор берётся из JWT, IP — из запроса; из тела запроса они не читаются никогда.
- **Журнал — отдельная сущность с отдельным Api**, общая на все разделы:
  `GET /api/infoblocks/history/:listKey` (журнал списка) и `GET /api/infoblocks/history/:listKey/:recordId`
  (история одной записи); очистка — `DELETE` по тем же адресам, отвечает
  `{ deleted }` — сколько строк стёрто. Ключ списка переводится в тип записей через `list-kinds`,
  тем же механизмом, что и настройки списка. У списка без журнала (медиатека) —
  400, а не пустой ответ: пустой не отличить от «правок ещё не было».
- Раздел о журнале не рассказывает ничего: ни в Api, ни в описании его нет.
  Редактор знает ключ списка — этого достаточно.
- **Журнал включают и выключают в настройках списка** — галочка «История изменений»
  (`isHistoryEnabled` в `infoblock_settings`, по умолчанию включена). Выключенный
  журнал сервер не пишет: `HistoryService.record` перед записью сверяется с настройками
  списка (тип записи в журнале и есть ключ списка), поэтому выключить его нельзя
  «только на экране». Записанное раньше не стирается — включат снова, и оно на месте.
  У списка без журнала вовсе (файлы, хранилища, домены) переключатель закрывает раздел,
  как и остальное своё: `blockedSettings={{ isHistoryEnabled: false }}` — в окне он виден,
  выключен и подписан «Задано разделом и не меняется». Сервер такой список и так
  не журналирует (`hasJournal: false`). Раздел может убрать журнал и у включённого (`isHistoryHidden`) — так его
  прячут от тех, кому сервер его не отдаст (не-`root` в «Пользователях» и «Ролях»).
- Право на журнал — правило списка, а не редактора: журнал «Пользователей» видит
  только `root` (`isRootOnly` у вида списка), как и сам раздел.

В новом редакторе (`components/contentEditorNew/history/`) два вида, оба только при
включённой истории: переключатель «Таблица / История изменений» в шапке
(`ContentEditorHistory` — все правки списка, по 20 на страницу; название записи — ссылка
в её карточку, если запись ещё есть в таблице) и вкладка «История» в карточке
сохранённой записи (`RecordHistory`). Таблица правок у них общая (`HistoryTable`):
когда, действие, кто, что изменилось; строка раскрывается в «было / стало» по каждому
полю. «Очистить историю» (`ClearHistoryButton`, с подтверждением) у журнала списка стоит
над таблицей и стирает весь журнал списка; в карточке — справа в строке вкладок, только
пока открыта «История», и стирает историю только этой записи (после очистки карточка
пересобирает вкладку). Право на очистку то же, что на чтение: стираются строки того, кто чистит
(журнал и читается по его `userId`), у списков `isRootOnly` — только `root`. Пока
история включена, новые правки после очистки снова пишутся. Подписи полей — из полей карточки раздела и свойств списка (`props.<код>` →
имя свойства, `historyFormat.ts`). Журнал в стор не кладётся: он растёт с каждой
правкой, поэтому читается при каждом показе (`useHistory.ts`, thunks
`loadEditorJournalThunk` / `loadEditorRecordHistoryThunk`).

## Символьный код записи

Поля `name` и `code` есть у записи любого раздела, поэтому их правила редактор применяет
сам, по настройкам списка (`logic/contentEditor/codePolicy.ts`):

- **код собирается из названия** — одинаково во всех разделах
  (`logic/slug.ts`: «Акции и скидки» → `akcii-i-skidki`). У новой записи код идёт
  за названием, у сохранённой подставляется, только если его ещё нет: менять код
  сохранённой записи нельзя — по нему её открывает сайт;
- **«Нет»** в настройках — поле `code` скрыто и колонка с кодом убрана из таблицы,
  но код записи по-прежнему собирается из названия: разделы требуют его непустым
  (у блоков и форм это проверка сервера), и без него новую запись было бы не создать;
- **«Обязательный»** добавляет полю `required`, **«Обязательный и уникальный»** — ещё
  и проверку по кодам остальных записей списка (и подстановку `-2` у повтора).

Правила раздела при этом остаются: своя `validate` поля кода вызывается первой,
а каскад (`onChange` поля `code` — у страниц от кода считается адрес) отрабатывает
и на подставленный код.
