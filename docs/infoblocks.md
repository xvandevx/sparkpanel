# Инфоблоки

Раздел `/admin/infoblocks`: списки однотипных записей — новости, товары, отзывы.
Уровней три, и у каждого своя страница:

- **Тип инфоблоков** — группировка списков по назначению («Контент сайта», «Магазин»).
  Своих записей у типа нет.
- **Инфоблок** — сам список: собственного контента он не хранит, только описание.
- **Элемент** — одна запись списка: «Новость 1», «Новость 2».

Все три экрана — универсальный редактор контента, см. [`docs/content-editor.md`](content-editor.md).

> **Тип в интерфейсе — «раздел» в коде и в базе.** Сущность называется
> `infoblock_sections` (`sectionId` в API и в формах), а пользователю показывается
> как «тип инфоблоков»: переименование сделано только в подписях. Помните об этом,
> читая модель ниже.

## Модель данных

### `infoblock_sections` — типы инфоблоков

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `userId` | `INTEGER` | владелец; изоляция данных идёт по нему |
| `position` | `INTEGER` | порядок среди типов, шаг 100 |
| `code` | `STRING` | код типа |
| `name` | `STRING` | название для админки |
| `description` | `TEXT \| null` | заметка: что складывают в этот тип |

Индексы: `userId`, `infoblock_sections_user_code` (`UNIQUE (userId, code)`).

Справочник плоский: типа внутри типа не бывает.

### `infoblocks` — инфоблоки

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `userId` | `INTEGER` | владелец |
| `sectionId` | `INTEGER` | тип; обязателен — «ничьих» списков нет |
| `position` | `INTEGER` | порядок внутри типа, шаг 100 |
| `code` | `STRING` | код, по которому список подключают на странице |
| `name` | `STRING` | название для админки |
| `description` | `TEXT \| null` | заметка: где список используется |
| `elementName` | `STRING` | как называется одна запись («Новость»); по умолчанию `Элемент` |
| `isActive` | `BOOLEAN` | неактивный остаётся в админке, но не выводится на сайт |

Индексы: `userId`, `sectionId`, `infoblocks_user_code` (`UNIQUE (userId, code)`).

Код уникален **у пользователя целиком**, а не внутри типа: им список подключают
в вёрстке, и после переноса инфоблока в соседний тип шаблон звал бы уже не тот список.

### `infoblock_elements` — элементы

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | порядковый номер |
| `userId` | `INTEGER` | владелец |
| `infoblockId` | `INTEGER` | инфоблок, которому принадлежит запись |
| `position` | `INTEGER` | порядок внутри инфоблока, шаг 100 |
| `code` | `STRING` | сегмент адреса записи на сайте |
| `name` | `STRING` | название записи |
| `preview` | `TEXT \| null` | анонс: то, что видно в списке на сайте |
| `content` | `TEXT \| null` | текст записи (HTML) |
| `image` | `STRING \| null` | адрес картинки |
| `date` | `DATEONLY \| null` | дата записи (`ГГГГ-ММ-ДД`) |
| `isActive` | `BOOLEAN` | неактивная запись на сайт не выводится |
| `props` | `JSONB` | зарезервировано; всегда `{}` — свойства записей хранятся в настройках списка |

Индексы: `userId`, `infoblockId`, `infoblock_elements_block_code` (`UNIQUE (infoblockId, code)`).

Набор полей **общий на все инфоблоки**: и у новости, и у товара это код, название, анонс,
текст, картинка и дата. Свои свойства у каждого списка (цена, артикул) задаются в его
[настройках](list-settings.md) — кнопка «Настройки» над таблицей записей, ключ списка
`infoblock-elements.<id инфоблока>`. Их значения лежат в `property_values`, а не в `props`:
так свойства одинаково заводятся у любого списка панели.

### `history` — журнал изменений

Общий на все разделы панели (`entity` = `infoblocks`). Все три сущности пишутся под одним
типом, а что именно поменяли, видно по приставке идентификатора: `section-1`, `block-2`,
`element-3`. Описан в [`docs/content-editor.md`](content-editor.md#журнал-изменений).

## API

Все маршруты требуют авторизации, `userId` берётся из JWT.

| Метод | Путь | Что делает |
|-------|------|-----------|
| `GET` | `/api/infoblocks` | структура: типы вместе с их инфоблоками |
| `GET` | `/api/infoblocks/history?limit&offset` | общий журнал изменений раздела |
| `GET` | `/api/infoblocks/history/:entityId` | история одной записи (`section-1`, `element-3`) |
| `POST` | `/api/infoblocks/sections` | создать тип |
| `PATCH` | `/api/infoblocks/sections/:id` | изменить тип |
| `DELETE` | `/api/infoblocks/sections/:id` | удалить тип с инфоблоками и их элементами |
| `POST` | `/api/infoblocks/blocks` | создать инфоблок в типе |
| `PATCH` | `/api/infoblocks/blocks/:id` | изменить инфоблок; `sectionId` в теле — перенос |
| `DELETE` | `/api/infoblocks/blocks/:id` | удалить инфоблок вместе с элементами |
| `GET` | `/api/infoblocks/blocks/:blockId/elements` | элементы инфоблока по порядку |
| `POST` | `/api/infoblocks/blocks/:blockId/elements` | создать элемент |
| `PATCH` | `/api/infoblocks/blocks/:blockId/elements/:id` | изменить элемент |
| `DELETE` | `/api/infoblocks/blocks/:blockId/elements/:id` | удалить элемент |

Голого `:id` в корне контроллера нет специально: все пути идут через приставку
(`sections`, `blocks`, `history`) — иначе Nest принял бы `history` за идентификатор.

Элемент адресуется **вместе со своим инфоблоком** (`blocks/:blockId/elements/:id`): без
этого по чужому номеру элемента можно было бы править чужой список своим же запросом.

Коды ответов: `404` — записи нет, `409` — код занят, `400` — не прошла проверка полей.

## Интерфейс

Три уровня — три страницы, на каждой плоский список в универсальном редакторе
контента. Дерева нет нигде: вложенность показана переходом, а не отступом.

| Адрес | Что показывает | Кнопка перехода в строке |
|-------|----------------|--------------------------|
| `/admin/infoblocks` | типы инфоблоков | → к инфоблокам типа |
| `/admin/infoblocks/2` | инфоблоки типа 2 | → к записям инфоблока |
| `/admin/infoblocks/2/3` | записи инфоблока 3 | — |

Уровни — **настоящие страницы, а не параметры запроса**: по ним строится подменю
слева, и подсветка активного пункта работает обычным сравнением путей.

- **Типы дублируются в левом меню**: пункт «Инфоблоки» разворачивается в подменю со
  списком типов, клик по самому названию ведёт на страницу со всеми типами. Список
  подменю — те же данные, что и на первой странице, поэтому структура грузится один
  раз на сессию, а не на каждой странице раздела.
- **Открытая запись живёт в адресе** (`?id=block-2`), как и в остальных разделах.
  Ключ записи — с приставкой (`section-1`, `block-2`, `element-3`): ровно такие ключи
  пишет журнал изменений, и совпадение даёт ссылкам журнала работать без перевода.
- **Путь и «Назад»** показаны над таблицей на втором и третьем уровне.
- **Вкладки шторки записи**: «Параметры» (идентификатор, код, название, дата, порядок,
  активность), «Контент» (картинка, анонс, текст), «История». Заголовок группы полей —
  то, как инфоблок называет одну запись (`elementName`): в списке новостей открывается
  «Новость», а не безличный «Элемент».
- **Перенос инфоблока** в другой тип — поле «Тип» в его форме; после сохранения он
  пропадает из текущего списка и появляется в выбранном.

Журнал изменений — **общий на весь раздел**: в нём правки всех трёх уровней, потому что
тип записи в журнале один (`infoblocks`). На каждом экране ссылкой отмечены только те
строки журнала, которые в этой таблице есть; остальные показаны текстом — ссылка на них
вела бы в никуда.

## Правила и ограничения

- **Инфоблок всегда внутри типа.** `sectionId` обязателен и проверяется на своего
  владельца; перенос в другой тип — тот же `PATCH`.
- **Код инфоблока уникален у пользователя**, код элемента — внутри своего инфоблока,
  код типа — у пользователя. Гарантия — уникальные индексы, а не только проверка
  в сервисе: два параллельных запроса прошли бы её оба.
- **Удаление уносит всё, что ниже** — в транзакции: тип уносит инфоблоки, инфоблок —
  элементы. Каждая удалённая запись попадает в журнал отдельной строкой.
- **Журнал общий на весь раздел**: в нём и правки структуры, и правки записей всех списков.
  Иначе изменения самой структуры не попали бы в админке никуда.

## Настройки

Своих переменных окружения у раздела нет. Схема приводится к моделям при старте
(`synchronize: true`), отдельных миграций нет.
