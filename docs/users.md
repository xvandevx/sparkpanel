# Пользователи и роли

Учётные записи, под которыми входят в SparkPanel, и их роли. В меню — пункт «Пользователи»
с двумя подпунктами: «Пользователи» (`/admin/users`) и «Роли» (`/admin/users/roles`).
Оба — списки нового редактора контента (`components/contentEditorNew/`).

Первая запись (главный администратор) заводится не здесь, а экраном первичной настройки —
см. [«Доступ и учётные записи»](auth.md). Этот раздел добавляет остальных, управляет доступом
и назначает роли.

**Две разные «роли».** `users.isRoot` — системный признак главного
администратора: он один, через API не меняется и решает, кто управляет панелью. Роли из
списка «Роли» — справочник, который заводит сам администратор («Редактор», «SEO-специалист»);
пользователю их назначают свойством «Роль». Права по ним пока не проверяются — это следующий шаг.

## Модель данных

Таблица `users` — та же, что обслуживает вход в систему; поля описаны в [`auth.md`](auth.md).
Раздел добавил к ней своё:

| Поле | Тип | Описание |
|------|-----|----------|
| `passwordChangedAt` | timestamptz null | когда пароль меняли в последний раз |
| `sort` | integer, по умолчанию 500 | «Сортировка» |

Зачем отдельное поле: пароль хранится хэшем, сравнивать «было/стало» нечего, а факт смены
в журнале виден быть обязан. `passwordChangedAt` — единственное, что о пароле попадает
в снимок истории; сам пароль не попадает туда никогда.

**Учётные записи — сущность панели без `userId`.** Они не принадлежат тенанту,
они его и определяют, поэтому изоляции по `userId` здесь нет; её место занимает проверка роли.

### Роли — `infoblock_roles`

Модуль `infoblocks/roles/` — список редактора контента с ключом `roles`, как страницы
и хранилища. Владельца нет: роли, как и учётные записи, общие на всю панель.

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | serial | номер роли; он же ключ записи в привязке |
| `name` | string | название для админки |
| `isActive` | boolean, по умолчанию `true` | неактивная роль остаётся у пользователей, но прав не даёт |
| `sort` | integer, по умолчанию 500 | «Сортировка» |

Кода у роли нет: назначают её по номеру, а проверок прав по коду пока нет.
Описания своей колонкой тоже нет — понадобится, его заведут свойством в настройках
списка ролей, как у любого списка.

### Роль пользователя — системное свойство

Своей колонки или таблицы связи у роли пользователя нет. Это **системное свойство** списка
`users`: код `role`, тип «Привязка к контенту» к списку `roles`, одно значение. Значение
лежит в `infoblock_values` (`json` = `{ "listKey": "roles", "recordId": "3" }`), как у любого
свойства, — подробности в [`infoblock-settings.md`](infoblock-settings.md#системные-свойства).

Свойство заводит сам сервер (перечень `infoblocks/settings/properties/system-properties.ts`),
поменять или удалить его нельзя. **Настройки списков `users` и `roles` общие на сайт**
(владелец `0`), а не у каждого свои: иначе роль одного и того же пользователя у каждого,
кто на него смотрит, была бы своей.

## API

Все маршруты требуют `Authorization: Bearer <token>`.

| Метод | Назначение | Доступ |
|-------|-----------|--------|
| `GET /api/users` | все учётные записи | любой авторизованный |
| `GET /api/users/{id}` | одна запись | любой авторизованный |
| `POST /api/users` | завести запись: `{ email, password, name?, isActive?, sort? }` | только `root` |
| `PATCH /api/users/{id}` | изменить: любое подмножество тех же полей | только `root` |
| `DELETE /api/users/{id}` | удалить запись (кроме главного администратора), 204 | только `root` |
| `GET /api/users/{id}/history` | история одной записи | только `root` |
| `GET /api/users/history` | общий журнал раздела, страницами | только `root` |

Наружу запись отдаётся через `UserDto` (`id`, `email`, `name`, `isRoot`, `isActive`, `isBlocked`,
`sort`, `createdAt`, `passwordChangedAt`) — хэш пароля физически не может попасть в ответ.
`isBlocked` — запись нельзя удалить: он равен `isRoot`.

Коды ответов:

| Ситуация | Ответ |
|----------|-------|
| Правка не главным администратором | 403 «Управлять пользователями может только главный администратор» |
| Email занят | 409 «Пользователь с таким email уже есть» |
| Попытка отключить `root` | 409 «Главного администратора нельзя отключить» |
| Попытка удалить `root` | 409 «Главного администратора удалить нельзя» |
| Записи нет | 404 «Пользователь не найден» |
| Пароль короче 6 символов, битый email | 400, массив сообщений по полям |

**Удаление.** Удалить можно любую учётную запись, кроме главного администратора.
Вместе с ней уходят значения её свойств (роль — `PropertyValuesService.remove`
у владельца сайта, список общий) и её вид таблиц (`infoblock_settings_columns` с её `userId`).
Журнал не трогается: в чужих журналах автор записан снимком (имя, email), а само удаление
пишется в журнал раздела. **Данные тенанта** (страницы, товары, контент, разделы файлов,
настройки списков с её `userId`) удаление не сносит — сейчас все они у `root`, у обычных
пользователей своих записей нет. Забрать доступ, не удаляя, — выключатель `isActive`:
такой пользователь не проходит ни `login`, ни `/auth/me`. Уже выданный токен удалённого
(как и отключённого) работает до истечения: гард проверяет только подпись.

**Поля `isRoot` в теле запроса нет** — ни при создании, ни при правке. `root` в системе ровно
один и заводится первичной настройкой; через этот раздел появляются только обычные
пользователи. Поле `isRoot` в контракте означало бы, что второго `root` можно попросить у API.
Роль из справочника назначают не здесь, а значением свойства:
`PATCH /api/infoblocks/users/values/{id}` с `[{ propertyId, value: { listKey: 'roles', recordId } }]`.

### Роли

| Метод | Назначение | Доступ |
|-------|-----------|--------|
| `GET /api/infoblocks/roles` | все роли; назначенная приходит с `isBlocked: true` | любой авторизованный |
| `POST /api/infoblocks/roles` | завести: `{ name, isActive?, sort? }` | только `root` |
| `PATCH /api/infoblocks/roles/{id}` | изменить: любое подмножество тех же полей | только `root` |
| `DELETE /api/infoblocks/roles/{id}` | удалить роль, которую никому не назначили, вместе со значениями её свойств | только `root` |
| `GET /api/infoblocks/history/roles` | журнал раздела (общий маршрут журнала) | только `root` |

| Ситуация | Ответ |
|----------|-------|
| Правка не главным администратором | 403 «Управлять ролями может только главный администратор» |
| Удаление назначенной роли | 409 «Роль назначена пользователям — сначала снимите её» |
| Роли нет | 404 «Роль не найдена» |

«Назначена» — значит, на неё ведёт хоть одна привязка к контенту в любом списке, а не
только свойство «Роль»: роль могли выбрать и в своём свойстве другого списка.

### Настройки и значения списков `users` и `roles`

Читать их может любой авторизованный, а **править — только `root`**: настройки, вкладки,
свойства и значения записей (`ListEditGuard` на контроллерах `infoblocks/settings`,
`…/properties`, `…/tabs`, `infoblocks/:listKey/values`; 403 «Этот список правит только
главный администратор»). Иначе любой пользователь назначил бы себе роль, поправив значение.

## Интерфейс

Пункт меню «Пользователи» только раскрывает подменю — своей страницы у него нет
(`config/navigation.ts`: раздел с `children`). Оба подпункта — экраны на редакторе контента:
раздел отдаёт код списка, Api и описание полей (`components/users/`, `logic/users/`).

**«Пользователи»** (`/admin/users`, `UsersScreen`): таблица — email, имя, отметка «Главный
администратор» (колонка `isRoot`, `rootMark` в `logic/users/userLabels.ts`), вход разрешён
или отключён, сортировка. У email главного администратора — золотая метка «Главный
администратор» (`badge` колонки: колонку `isRoot` могут спрятать в виде таблицы). Карточка — имя, email, пароль, «Доступ в панель» и «Сортировка»; у сохранённой записи **пустой пароль означает «оставить прежний»** — Api раздела
(`logic/users/usersApi.ts`) просто не кладёт его в тело. Ниже — свойства списка, первым
системное «Роль»: выбор из ролей (`FieldType.Link`). Удаляют корзиной в строке, «Удалить»
в карточке или быстрым действием над отмеченными; главный администратор приходит
с `isBlocked` — у него замок.

**«Роли»** (`/admin/users/roles`, `RolesScreen`): таблица — роль, активность,
сортировка. Карточка — название, «Активность», «Сортировка» (символьный код записей
раздел закрыл «Нет»); ниже — свойства списка, если их завели. Назначенная роль
приходит с `isBlocked` — вместо корзины замок.

**Кто что видит.** Всё открыто всем авторизованным, правит только `root`. Остальным раздел
отдаёт Api только с `list` (`useUsersAccess`): без `create`/`update`/`remove` редактор сам
убирает «Добавить», «Сохранить», «Удалить» и корзину, поля карточки закрыты. Журнал
и «Настройки» списка им тоже скрыты — это часть управления.

## Правила и ограничения

- Управлять учётными записями может только `root`; признак `isRoot` читается из JWT,
  подделать его запросом нельзя.
- Отключить и удалить главного администратора нельзя — войти после этого было бы некому,
  а включить обратно некому тем более.
- `users.isRoot` (главный администратор) не меняется через API вообще; роль из справочника
  меняется значением свойства «Роль» — и только руками `root`.
- Системное свойство «Роль» не правится и не удаляется (409); роль, на которую ведёт
  привязка, не удаляется (409).
- Email хранится нормализованным (без пробелов, в нижнем регистре) — иначе `Ivan@x.ru`
  и `ivan@x.ru` стали бы разными логинами одного человека.
- В журнал попадают email, имя, признак главного администратора, доступ, сортировка и дата
  смены пароля (роль из справочника — правкой значения свойства). Сам пароль — никогда.
