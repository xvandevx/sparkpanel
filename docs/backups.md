# Резервные копии

Два вида копий: **копия списка** — один список редактора контента, из его шторки,
и **копия сайта** — вся база целиком, в «Настройках» ([ниже](#копия-всего-сайта)).

## Назначение

Снимок одного списка редактора контента — его настроек, записей, значений свойств
и черновиков — и возврат списка к этому снимку. Кнопка «Резервные копии» в шапке
редактора открывает шторку: создать копию, загрузить её из файла, скачать, удалить
и восстановить. Перед восстановлением панель сама снимает копию того, что есть, —
поэтому любое восстановление можно отменить, вернув эту копию.

Копии есть у списков: **«Страницы»** (`pages`), **элементы типа контента**
(`content-items.<номер>`; у самих типов — нет), **«Товары»** (`products`),
**«Категории»** (`product-categories`), **«Пользователи»** (`users`) и **«Роли»**
(`roles`). Копия всей базы — [ниже](#копия-всего-сайта).

## Модель данных

### `infoblock_backups` — копия списка

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | |
| `settingsId` | `INTEGER` | список — строка `infoblock_settings` (у общих списков — владельца `0`); `ON DELETE CASCADE` |
| `listKey` | `STRING` | ключ списка (`products`, `content-items.8`) |
| `kind` | `STRING` | `manual` — кнопкой, `before-restore` — сняло восстановление, `upload` — из файла |
| `note` | `TEXT` | подпись; у загруженной — имя файла |
| `recordsCount`, `propertiesCount`, `size` | `INTEGER` | для списка копий, чтобы не читать `data`; `size` — байт |
| `authorId`, `authorEmail` | | кто снял — из JWT |
| `data` | `JSONB` | сама копия (формат ниже) |
| `createdAt`, `updatedAt` | | |

Копии привязаны к настройкам списка, как и всё внутри него: у общего списка
(пользователи, роли) копии общие, у своего — свои.

### Формат копии (`data`, он же файл «Скачать»)

`backups/backup-data.ts`, `version: 1`. Строки таблиц — как их отдаёт база:

| Ключ | Откуда |
|------|--------|
| `listKey` | ключ списка; файл другого списка не загружается (400) |
| `settings` | правила записей списка: `useCode`, `codeRequired`, `codeUnique`, `maxDepth`, `isHistoryEnabled`, `isDraftEnabled`. Имени и кода нет — их задаёт раздел |
| `tabs`, `properties`, `options`, `filters` | вкладки, свойства, варианты «Списка», поля фильтра |
| `rows` | записи из таблицы раздела (`infoblock_pages`, `users`…) — все поля, у пользователей и хэш пароля |
| `records`, `values` | `infoblock_records` и `infoblock_values` — значения свойств записей |
| `drafts` | черновики записей |

Вида таблицы (`infoblock_settings_columns`) в копии нет — он у каждого пользователя свой.
Журнала изменений тоже нет.

## API

Все маршруты — `/api/infoblocks/backups/:listKey`. У списка без копий — 400,
у чужого или несуществующего типа контента — 404. Копии **пользователей и ролей —
только у главного администратора, и на чтение тоже** (`BackupAccessGuard`): в копии
пользователей лежат хэши паролей.

| Метод | Путь | Что |
|-------|------|-----|
| `GET` | `/` | копии списка, новые сверху, без `data` → `BackupDto[]` |
| `POST` | `/` | `{ note? }` — снять копию сейчас → `BackupDto` |
| `POST` | `/upload` | `{ note?, data }` — загрузить копию из файла: `data` — содержимое файла «Скачать» → `BackupDto`; 400 — не копия или копия другого списка |
| `GET` | `/:id/file` | копия целиком — для файла |
| `GET` | `/:id/check` | что изменится → `BackupCheckDto` |
| `POST` | `/:id/restore` | `{ mode, isRecords, isSettings }` — вернуть копию → копия «перед восстановлением»; 409 — номера в копии чужие |
| `DELETE` | `/:id` | удалить копию |

`BackupCheckDto`: записей и свойств сейчас и в копии; `removedRecords` — есть сейчас,
в копии нет (удалятся при замене); `keptRecords` — то же, но защищены и останутся;
`returnedRecords` — есть в копии, сейчас нет (вернутся); `changedRecords` — есть в обоих,
но отличаются полями или значениями; `removedProperties` — названия свойств, которых
в копии нет; `missingFiles` — значений «Файл»/«Изображение» в копии на удалённые файлы.

## Восстановление

Одна транзакция: снимается копия «перед восстановлением», потом список
переписывается. Упало на середине — список остаётся прежним, копии нет.

- **`mode: 'replace'`** — список становится ровно таким, как в копии.
  - `isSettings` — правила записей, вкладки, свойства с вариантами и поля фильтра.
    Чего в копии нет, удаляется; свойство — вместе со значениями (каскад). Имя и код
    списка не трогаются.
  - `isRecords` — записи раздела, значения и черновики. Записи, которых нет в копии,
    удаляются, **кроме защищённых** (`isBlocked`: категория с привязками, главный
    администратор, назначенная роль) — их раздел не удаляет, и копия это не отменяет.
- **`mode: 'missing'`** — возвращаются только записи копии, которых сейчас нет,
  со своими значениями и черновиками; остальное не трогается. Настройки в этом
  режиме не возвращаются (`isSettings` игнорируется).

**Номера.** Сохраняются номера записей раздела (их видно в адресе, на них ссылаются
привязки других списков), вкладок, свойств и вариантов (на варианты смотрят привязки
к значениям списка). Строки дерева, значений, черновиков и полей фильтра заводятся
заново: на их номера никто не ссылается. Поэтому перед записью сервер проверяет, что
под номерами из копии нет строк чужого списка или чужого пользователя (409) — файл
копии могли подложить, а таблицы у всех общие. Владелец записи и списка — всегда тот,
чей это список, что бы ни было в файле.

**Что не возвращается.** Значение свойства или варианта, которого в списке нет
(восстанавливают только записи, а свойство с тех пор удалили), — его некуда положить.
Запись, чей родитель пропал, поднимается в корень. Значения на удалённые файлы
возвращаются как есть — файла нет, поле пустое (окно об этом предупреждает).

Восстановление идёт мимо сервисов разделов: проверки раздела (адрес страницы,
уникальность кода) и журнал изменений не срабатывают — копия уже была проверенным
состоянием списка. В «Истории изменений» восстановление не видно.

## Интерфейс

`components/contentEditorNew/backups/`. Кнопка «Резервные копии» — у экранов,
где раздел включил её (`settings.isBackupShown`), у «Пользователей» и «Ролей» — только
главному администратору.

- **Шторка** (`BackupsDrawer`): поле подписи и «Создать копию», «Загрузить из файла»
  (`.json`), таблица копий — дата, метка вида (`Tag`), подпись, записи, свойства,
  размер, автор; в строке «Восстановить», «Скачать файлом», корзина с подтверждением.
  Список копий в стор не кладётся — читается при каждом открытии (`useBackups`).
- **Окно восстановления** (`RestoreDialog`): сначала `GET …/check`, потом три счётчика
  (записи и свойства «сейчас → в копии», изменятся или вернутся записи), «Как»
  (заменить / только вернуть удалённые), «Что вернуть» (записи; настройки — только при
  замене), предупреждения проверки и строка о копии «перед восстановлением».
- После восстановления редактор перечитывает настройки, вкладки, свойства, поля
  фильтра, страницу таблицы и, если грузили, весь список; известные значения
  и черновики записей сбрасываются (`NEW_EDITOR_RESTORED`).

## Правила и ограничения

- Копии «перед восстановлением» старше 30 дней удаляются, когда у списка снимают
  следующую копию; остальные живут, пока их не удалят.
- Копия хранит **скрытые** свойства (`isHidden`) со значениями — в отличие от остальных
  маршрутов, файл копии их отдаёт. Среди списков с копиями таких свойств сейчас нет
  (они у хранилищ).
- Новый список с копиями — строка в `BackupsService.sources` (таблица раздела и какие
  строки в ней этот список) и `isBackupShown` в экране раздела.

## Копия всего сайта

Пункт меню «Настройки» → «Резервные копии» (`/admin/settings/backups`). Копия —
**вся база данных**, кроме самих копий сайта; файлов медиатеки в ней нет. Экран
и маршруты — **только главному администратору**, и на чтение тоже (`RootOnlyGuard`;
другим пункта в меню нет, по адресу — `Result 403`): в копии хэши паролей и ключи
хранилищ.

### Модель данных

`site_backups` — модуль `backend/src/backups/`:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | `SERIAL` | |
| `kind` | `STRING` | `manual`, `before-restore`, `upload` — как у копий списка |
| `note` | `TEXT` | у загруженной — имя файла, у остальных пусто |
| `tablesCount`, `rowsCount` | `INTEGER` | сколько таблиц и строк в копии |
| `size` | `INTEGER` | размер сжатой копии, байт — столько весит и скачанный файл |
| `authorId`, `authorEmail` | | кто снял — из JWT |
| `data` | `BYTEA` | сама копия: JSON, сжатый gzip |
| `createdAt`, `updatedAt` | | |

Внешних ключей у таблицы нет: восстановление стирает все остальные таблицы разом,
и ссылка на пользователя не дала бы этого сделать.

**Формат** (`backups/site-dump.ts`): `{ format: "sparkpanel-site", version: 1,
tables: { <таблица>: [строки] } }` — строки каждой таблицы схемы `public`, как их
отдаёт `json_agg`. В копию идёт всё, что лежит в базе: и живые разделы, и отложенные
в `to_delete/`, и старые таблицы (`zz_legacy_*`), журнал изменений и копии списков.
**Схемы в копии нет** — её задают модели, база приводится к ним при старте.

### API

`/api/site-backups`, все маршруты — только `root` (иначе 403).

| Метод | Путь | Что |
|-------|------|-----|
| `GET` | `/` | `{ items, databaseSize }`: копии, новые сверху, без данных, и сколько весят таблицы базы без копий сайта |
| `POST` | `/` | снять копию сейчас → `SiteBackupDto` |
| `POST` | `/upload` | multipart, поле `file`: `.json.gz` или `.json` — то, что выдаёт «Скачать» → `SiteBackupDto`; 400 — не копия сайта. Не больше 25 МБ (столько пропускает nginx) |
| `GET` | `/:id/file` | копия файлом: `application/gzip`, `sparkpanel-site-<дата>-<номер>.json.gz` |
| `POST` | `/:id/restore` | вернуть базу к копии → копия «перед восстановлением»; 400 — копия не легла, база не изменилась |
| `DELETE` | `/:id` | удалить копию |

### Снятие и восстановление

- **Копия** снимается в одной транзакции `REPEATABLE READ` — правка, пришедшая
  посреди копии, не попадёт в неё наполовину. JSON собирает сама база (`json_agg`).
- **Восстановление** — одна транзакция:
  1. снимается копия «перед восстановлением»;
  2. все таблицы, кроме копий сайта, стираются (`TRUNCATE … RESTART IDENTITY`);
  3. строки копии заливаются таблица за таблицей — та, на которую ссылаются, раньше
     ссылающейся (`tableOrder` по внешним ключам). Строку в типы колонок переводит база
     (`json_populate_recordset`), тем же текстом, каким её выдал `json_agg`;
  4. счётчики номеров (`SERIAL`) выставляются за последний номер.

  Упало на любом шаге — база прежняя, копии «перед восстановлением» нет, ответ 400
  с причиной от базы.
- Строки ложатся **по колонкам, которые есть и в копии, и в базе**: колонку, которой
  в копии нет, база заполняет значением по умолчанию; колонки и таблицы, которых нет
  в базе, пропускаются. Копия старой версии, где новой колонке `NOT NULL` нечем
  заполниться, не возвращается (400).
- После восстановления сервер сверяет системные свойства с перечнем — как при старте
  (`SystemPropertiesService`): копия могла быть снята до того, как перечень поменялся.
- Номера строк сохраняются как в копии. Сессии не сбрасываются: токен остаётся
  в силе, пока его пользователь есть в базе; удалило его восстановление — следующий
  запрос вернёт на экран входа.
- Копии «перед восстановлением» старше 30 дней удаляются при каждом сохранении копии.

### Интерфейс

`components/settings/backups/` + `logic/siteBackups/`, подписи видов и размера —
общие с копиями списка (`logic/backupLabels.ts`).

- **Экран** (`SiteBackupsScreen`): справа от заголовка «Загрузить копию» и «Создать
  копию сейчас»; карточка «Что входит в копию» — размер базы и предупреждение про
  хэши паролей; карточка «Копии» — всего копий и их вес, таблица: «Создана», «Как»
  (`Tag`), «Файл», «Размер», «Автор», действия «Восстановить», «Скачать», корзина
  с подтверждением. Список копий в стор не кладётся (`useSiteBackups`).
- **Окно восстановления** (`SiteRestoreDialog`): строка о копии, предупреждение
  «База данных заменится копией целиком», строка о копии «перед восстановлением»
  и поле, куда вводят слово **ВОССТАНОВИТЬ** — без него кнопка «Восстановить сайт»
  неактивна. Пока сервер работает, окно не закрыть. После успеха страница загружается
  заново: устарело всё, что панель держала в сторе.
